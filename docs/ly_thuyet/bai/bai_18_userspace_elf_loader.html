Bài 18 - Userspace & ELF Loader

Status doneTags step, elf, pt_load, pt_interp, auxv, argv, ring 3, run, bash

Hàm: run() (utilities/shell/shell.c), elfExecute(), elfProcessLoad(), elf_check_file() (utilities/elf.c), stackGenerateUser() (multitasking/stack.c) · Phụ thuộc: gần như mọi bài trước: đọc file (Bài 15), PML4 riêng (Bài 6), selector ring 3 (Bài 7), task và scheduler (Bài 12), syscall (Bài 16), FPU (Bài 17).

Mục đích

Đích của cả khoá học: chạy một chương trình thật của người dùng, ở ring 3.

Dòng cuối của _start() là while (1) run("/bin/bash", true, 0, 0);. Để làm được việc đó, kernel phải đọc file /bin/bash từ ổ đĩa, hiểu định dạng ELF, đặt từng phần của nó vào đúng địa chỉ trong một không gian địa chỉ mới, dựng stack ban đầu đúng như chương trình Linux chờ đợi (argc, argv, envp, auxv), rồi để scheduler đưa nó vào ring 3. Bài này đọc từng bước đó trong cavOS.

Nói thật đơn giản

File ELF giống một bộ đồ nội thất đóng thùng, kèm tờ hướng dẫn lắp (program header): "thùng 1 đặt ở phòng khách, địa chỉ 0x400000, chỉ để xem không được sửa; thùng 2 đặt ở phòng làm việc, có phần ghi 'để trống, tự trải thảm' (.bss)". Kernel là thợ lắp: dọn một căn nhà trống (PML4 mới), đặt từng thùng đúng chỗ, trải thảm phần để trống.

Rồi thợ để lại trên bàn một tờ giấy cho chủ nhà (stack ban đầu): "có 3 tham số, đây là tên từng cái; đây là biến môi trường; còn đây là vài thông tin về căn nhà" (auxv). Chủ nhà (chương trình) vào nhà, đọc tờ giấy đó trước tiên, rồi mới bắt đầu làm việc.

Cần biết trước

Ba ý về file ELF và stack ban đầu; mọi phần cơ chế đã có ở các bài trước.

  • ELF header và program header. 64 byte đầu file là ELF header: magic 7F 'E' 'L' 'F', lớp 64 bit, kiến trúc, loại (ET_EXEC = 2, ET_DYN = 3), điểm vào e_entry, và vị trí bảng program header. Mỗi program header loại PT_LOAD nói: lấy p_filesz byte từ offset p_offset của file, đặt ở địa chỉ p_vaddr, chiếm p_memsz byte (phần thừa xoá về 0), với quyền p_flags (R, W, X). PT_INTERP ghi đường dẫn của trình nạp động (chương trình dùng thư viện chia sẻ).
  • Stack ban đầu theo ABI x86-64. Lúc vào _start, RSP trỏ vào argc; ngay trên là argv[0..argc-1], một số 0, envp[...], một số 0, rồi các cặp auxv (loại, giá trị) kết thúc bằng AT_NULL. Chuỗi thật nằm cao hơn nữa.
  • auxv. "Auxiliary vector": kernel gửi thông tin cho libc và trình nạp động. AT_PHDR (bảng program header trong bộ nhớ), AT_PHENT/AT_PHNUM (cỡ, số lượng), AT_ENTRY (điểm vào của chương trình), AT_BASE (nơi nạp trình nạp động), AT_PAGESZ, AT_RANDOM (16 byte ngẫu nhiên cho stack canary).
  • Đã gặp: đọc file qua VFS ở Bài 15; PageDirectoryAllocate, VirtualMap ở Bài 6; khung iretq đầu tiên của task ở Bài 12; selector 0x53/0x4b ở Bài 16.

Đọc code cavOS

run() gọi elfExecute(); hàm này đọc file, dựng không gian địa chỉ, tạo task và stack; run() nối stdin/stdout/stderr rồi chờ.

File: entry/kernel.c, utilities/shell/shell.c, utilities/elf.c, multitasking/stack.c, multitasking/task.c, include/elf.h (cavOS 2ba0edb).

1. Vị trí trong _start()

c
// entry/kernel.c:_start()
  initiateSSE();
  testingInit();
  if (!systemDiskInit)
    printf("[warning] System disk has not been detected!\n");
  printf("==     Cave-Like Operating System      ==\n");
  ...

Kernel thread đầu tiên (task 0) trở thành "init": chạy bash, chờ bash thoát, rồi chạy lại. Từ đây mọi thứ người dùng thấy là chương trình ring 3 gọi syscall.

2. run(): nạp, nối IO, chờ

c
bool run(char *binary, bool wait, int _argc, char **_argv) {
  char *argv[] = {binary};
  Task *task = 0;
  if (_argc > 0)
    task = elfExecute(binary, _argc, _argv, 0, 0, false);
  else
    task = elfExecute(binary, 1, argv, 0, 0, false);
  if (!task)
    return false;

  task->parent = currentTask;
  int stdin = fsUserOpen(task, "/dev/stdin", O_RDWR | O_APPEND, 0);
  int stdout = fsUserOpen(task, "/dev/stdout", O_RDWR | O_APPEND, 0);
  int stderr = fsUserOpen(task, "/dev/stderr", O_RDWR | O_APPEND, 0);
  ...
  fdStdin->id = 0;
  fdStdout->id = 1;
  fdStderr->id = 2;

  taskCreateFinish(task);

  if (task && wait) {
    currentTask->waitingForPid = task->id;
    currentTask->state = TASK_STATE_WAITING_CHILD_SPECIFIC;
    handControl();
  }
  return true;
}

Task mới ở trạng thái CREATED cho tới khi fd 0, 1, 2 được mở vào /dev/stdin, /dev/stdout, /dev/stderr; chỉ khi đó nó mới READY. Người gọi chuyển sang chờ đúng con đó; khi con chết, taskKill đánh thức cha.

3. elfExecute(): đọc, kiểm, dựng không gian địa chỉ

c
Task *elfExecute(char *filepath, uint32_t argc, char **argv, uint32_t envc,
                 char **envv, bool startup) {
  // Open & read executable file
  OpenFile *dir = fsKernelOpen(filepath, O_RDONLY, 0);
  ...
  size_t filesize = fsGetFilesize(dir);
  uint8_t *out = (uint8_t *)VirtualAllocate(outSize);
  fsRead(dir, out, filesize);
  fsKernelClose(dir);

  Elf64_Ehdr *elf_ehdr = (Elf64_Ehdr *)(out);
  if (!elf_check_file(elf_ehdr)) { ... return 0; }   // magic, ELFCLASS64, x86-64

  // Create a new page directory which is later used by the process
  uint64_t *oldpagedir = GetPageDirectory();
  uint64_t *pagedir = PageDirectoryAllocate();
  ChangePageDirectory(pagedir);

  size_t interpreterEntry = 0;
  size_t interpreterBase = 0x100000000000; // todo: not hardcode
  size_t executableBase = 0;               // modified later if needed
  for (int i = 0; i < elf_ehdr->e_phnum; i++) {
    Elf64_Phdr *elf_phdr = ...;
    if (elf_phdr->p_type == 3) {            // PT_INTERP: e.g. musl's ld.so
      ... read the interpreter file, load its PT_LOADs at interpreterBase ...
      interpreterEntry = interpreterEhdr->e_entry;
      continue;
    }
    if (elf_phdr->p_type != PT_LOAD)
      continue;
    if (elf_ehdr->e_type == 3)              // ET_DYN (PIE)
      executableBase = 0x50000000000;
    elfProcessLoad(elf_phdr, out, executableBase);
  }

  ChangePageDirectory(oldpagedir);
  Task *target = taskCreate(id,
                 interpreterEntry ? (interpreterBase + interpreterEntry)
                                  : (executableBase + elf_ehdr->e_entry),
                 false, pagedir, argc, argv);
  ...
  stackGenerateUser(target, argc, argv, envc, envv, out, filesize, elf_ehdr,
                    interpreterEntry ? 0x100000000000 : 0, executableBase);
  VirtualFree(out, outSize);
  ...
  return target;
}
  • Cả file được đọc vào bộ nhớ kernel trước, rồi mới phân tích.
  • PML4 mới chép nửa kernel từ PML4 mẫu (Bài 6). cavOS tạm đổi CR3 sang PML4 mới để memcpy thẳng vào địa chỉ của chương trình, rồi đổi lại.
  • Chương trình động (có PT_INTERP, như bash dùng musl động): cavOS nạp luôn trình nạp động (ld.so) ở 0x100000000000 và cho task bắt đầu ở điểm vào của trình nạp; trình nạp tự tìm chương trình qua auxv (AT_PHDR, AT_ENTRY, AT_BASE) và nạp thư viện.
  • Chương trình PIE (ET_DYN) được đặt ở 0x50000000000; chương trình thường (ET_EXEC) ở đúng địa chỉ link.

4. elfProcessLoad(): một đoạn PT_LOAD

c
void elfProcessLoad(Elf64_Phdr *elf_phdr, uint8_t *out, size_t base) {
  // Map the (current) program page
  size_t   startRounded = (elf_phdr->p_vaddr & ~0xFFF);
  uint64_t pagesRequired = DivRoundUp(
      (elf_phdr->p_vaddr - startRounded) + elf_phdr->p_memsz, 0x1000);
  for (int j = 0; j < pagesRequired; j++) {
    size_t vaddr = (elf_phdr->p_vaddr & ~0xFFF) + j * 0x1000;
    if (VirtualToPhysical(base + vaddr))
      continue;
    size_t paddr = PhysicalAllocate(1);
    VirtualMap(base + vaddr, paddr, PF_USER | PF_RW);
  }

  // Copy the required info
  memcpy((void *)(base + elf_phdr->p_vaddr), out + elf_phdr->p_offset,
         elf_phdr->p_filesz);

  // wtf is this? (needed)
  if (elf_phdr->p_memsz > elf_phdr->p_filesz)
    memset((void *)(base + elf_phdr->p_vaddr + elf_phdr->p_filesz), 0,
           elf_phdr->p_memsz - elf_phdr->p_filesz);
}
  • Đoạn có thể bắt đầu giữa trang, nên số trang tính từ đầu trang chứa p_vaddr. Trang đã có (hai đoạn chung một trang) thì giữ nguyên.
  • Câu hỏi trong comment ("wtf is this?") có câu trả lời: p_memsz > p_filesz là .bss, biến toàn cục chưa khởi tạo. Chúng không chiếm chỗ trong file, và C hứa chúng bằng 0.
  • Mọi trang được map PF_USER | PF_RW, bất kể p_flags nói gì (xem Đọc thêm).

Thứ tự đẩy ngược với thứ tự đọc: AT_NULL đẩy đầu tiên nên nằm cuối danh sách auxv; argc đẩy cuối cùng nên RSP trỏ vào nó. Khi scheduler chọn task này lần đầu, khung iretq dựng sẵn (CS 0x53, SS 0x4b, RIP = điểm vào, RSP = chỗ argc, IF = 1) đưa CPU xuống ring 3 ngay tại _start.

Tự kiểm tra

Năm câu.

Một đoạn PT_LOAD có p_filesz = 4, p_memsz = 0x1020. Loader phải làm gì với 0x101C byte còn lại?

Map đủ trang cho cả 0x1020 byte và xoá phần đó về 0. Đó là .bss: biến toàn cục chưa khởi tạo, không có trong file, nhưng C bảo đảm chúng bằng 0.

Vì sao run() mở /dev/stdin, /dev/stdout, /dev/stderr trước taskCreateFinish()?

Vì chương trình có thể write(1, ...) ngay lệnh đầu tiên. Nếu task đã READY trước khi fd 1 tồn tại, lần ghi đầu có thể trả -EBADF.

Bash của cavOS là chương trình động (có PT_INTERP). Lệnh đầu tiên chạy ở ring 3 thuộc về ai?

Của trình nạp động (ld.so của musl), nạp ở 0x100000000000. Task bắt đầu ở interpreterBase + interpreterEntry; trình nạp đọc auxv để biết bash nằm đâu, nạp thư viện, rồi mới nhảy tới AT_ENTRY của bash.

Đổi thứ tự đẩy trong stackGenerateUser: đẩy argc trước, auxv sau. Chương trình đọc được gì?

RSP sẽ trỏ vào một cặp auxv chứ không vào argc. Chương trình (và libc) đọc số đầu tiên làm argc, các số kế tiếp làm con trỏ argv: rác, thường là page fault ngay trong _start.

Task 0 gọi run("/bin/bash", true, ...) trong while (1). Điều gì xảy ra khi người dùng gõ exit trong bash?

Bash thoát, taskKill đánh thức cha (task 0 đang WAITING_CHILD_SPECIFIC), run() trả về, vòng lặp gọi run() lần nữa: một bash mới mở ra.

Đọc thêm

Câu hỏi của dàn ý cũ, những chỗ loader của cavOS khác với ABI và với cách làm an toàn, và chỗ tra trong spec.

Câu hỏi mở (đã trả lời)

  • auxv là gì, chứa entry nào? Mảng cặp (loại, giá trị) ngay trên envp. cavOS đưa 10 loại: AT_PHDR, AT_HWCAP, AT_FLAGS, AT_BASE, AT_ENTRY, AT_PHENT, AT_PHNUM, AT_SECURE, AT_PAGESZ, AT_RANDOM, rồi AT_NULL (Lab 0x0c in đủ, đúng thứ tự đó).
  • Vào ring 3 bằng iret hay sysret? Lần đầu bằng iretq: task là một khung ngắt dựng sẵn với CS/SS ring 3, scheduler iretq vào nó như mọi lần đổi task (Bài 12). Các lần về sau từ syscall thì bằng sysret (Bài 16).
  • Stack ban đầu layout ra sao? argc, argv[], 0, envp[], 0, auxv, AT_NULL (sơ đồ ở mục 5).
  • Dynamic linking? Có: PT_INTERP → nạp ld.so của musl ở 0x100000000000, AT_BASE = địa chỉ đó; PIE ở 0x50000000000.

Mọi đoạn đều ghi được, và không kiểm vị trí

  • elfProcessLoad map mọi trang PF_USER | PF_RW, bỏ qua p_flags: đoạn code cũng ghi được, và vì cavOS chưa dùng NX (Bài 6), đoạn data cũng chạy được. Cách an toàn: map theo p_flags (R-X cho code, RW- + NX cho data), sau khi đã chép xong.
  • Loader không kiểm p_vaddr/p_memsz có nằm trọn trong nửa user hay không. Loader cẩn thận từ chối mọi PT_LOAD ra ngoài vùng user, như lab 0x0c làm.

AT_PHDR được tính, không được tìm

AT_PHDR phải là địa chỉ của bảng program header trong bộ nhớ. cavOS tính bằng vaddr thấp nhất của các PT_LOAD + e_phoff (PIE: executableBase + e_phoff). Công thức chỉ đúng khi đoạn PT_LOAD đầu tiên chứa cả phần đầu file (offset 0), như mọi chương trình do linker mặc định tạo ra. Linux dùng PT_PHDR nếu có. Lab 0x0c đặt FILEHDR PHDRS vào đoạn code để công thức này cho 0x400000 + 0x40 = 0x400040.

Bash nhận envp rỗng

run() gọi elfExecute(binary, ..., 0, 0, false): envc = 0. Bash do task 0 khởi động không nhận biến môi trường nào từ kernel: ngay sau argv là hai số 0 liền nhau. Các chương trình bash chạy tiếp (qua execve) thì nhận envp do bash truyền.

RSP lúc vào không luôn căn 16 byte

ABI x86-64 yêu cầu RSP chia hết cho 16 lúc vào _start. cavOS bắt đầu từ đỉnh stack (đã căn) và đẩy 25 + argc + envc qword, không thêm qword đệm. Khi argc + envc chẵn, RSP lệch 8: Lab 0x0c đo được RSP % 16 = 8 với argc = 2, envc = 2. Chương trình musl không bị ảnh hưởng vì _start của musl tự căn lại trước khi gọi C; chương trình tự viết _start mà không căn có thể hỏng ở lệnh SSE đòi địa chỉ căn 16.
