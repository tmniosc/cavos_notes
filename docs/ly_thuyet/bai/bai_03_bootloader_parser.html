Bài 3 - Bootloader Parser

Status doneTags step, boot

Mục đích

Gom mọi câu trả lời của Limine vào một struct dùng chung.

Bài này đọc các response Limine đã điền và chép vào struct toàn cục bootloader. Từ Bài 4 trở đi, các hệ con tra struct này thay vì đụng thẳng vào API Limine: bộ quản lý RAM cần bản đồ RAM, paging cần độ lệch HHDM, ACPI cần địa chỉ RSDP.

Nói thật đơn giản

Lúc giao máy, Limine để lại một tập giấy tờ về phần cứng: RAM ở đâu, kernel nằm chỗ nào, có mấy CPU, bảng ACPI ở đâu. Bài này gom hết vào một bìa hồ sơ (struct bootloader) để cả kernel về sau lấy ra dùng. Không tính toán gì phức tạp: chỉ đọc, kiểm vài điều kiện, và chép lại một lần.

Cần biết trước

Ba khái niệm mới, một đã gặp.

  • Request / response — đã gặp ở Bài 1: kernel khai biến request có magic, Limine điền con trỏ .response.
  • HHDM (Higher Half Direct Map) — Limine map toàn bộ RAM vật lý vào một vùng ở nửa cao, bắt đầu tại một độ lệch cố định. Nhờ vậy muốn đọc địa chỉ vật lý (PA) nào chỉ cần cộng: VA = PA + hhdmOffset. Kernel không thể đọc thẳng PA vì paging đã bật, mọi truy cập đều là địa chỉ ảo. Đọc sâu: HHDM.
  • Memory map — danh sách các vùng địa chỉ vật lý, mỗi vùng có base, length và loại (RAM trống, RAM bootloader mượn tạm, kernel, framebuffer, vùng cấm...). Firmware dựng danh sách này; Limine chỉ chuyển lại. Đọc sâu: Boot Protocol & Limine (mục 5b).
  • SMP và BSP — SMP (Symmetric Multi-Processing) là máy có nhiều nhân CPU. Lúc boot chỉ một nhân chạy, gọi là BSP (Bootstrap Processor); các nhân khác chờ được đánh thức. Mỗi nhân có một số LAPIC ID riêng. Đa nhân sẽ học ở Bài 12.

Đọc code cavOS

Một file, một hàm: src/kernel/entry/bootloader.c → initialiseBootloaderParser(), gọi ngay sau serial trong _start().

Sơ đồ: response nào thành trường nào, ai dùng

Sáu request được khai báo

Đầu entry/bootloader.c, đúng thứ tự trong file:

c
static volatile struct limine_paging_mode_request liminePagingreq = {
    .id = LIMINE_PAGING_MODE_REQUEST,
    .revision = 0,
    .mode = LIMINE_PAGING_MODE_X86_64_4LVL};

static volatile struct limine_kernel_address_request limineKrnreq = {
    .id = LIMINE_KERNEL_ADDRESS_REQUEST, .revision = 0};

static volatile struct limine_hhdm_request limineHHDMreq = {
    .id = LIMINE_HHDM_REQUEST, .revision = 0};

static volatile struct limine_memmap_request limineMMreq = {
    .id = LIMINE_MEMMAP_REQUEST, .revision = 0};

static volatile struct limine_smp_request limineSmpReq = {
    .id = LIMINE_SMP_REQUEST, .revision = 0};

static volatile struct limine_rsdp_request limineRsdpReq = {
    .id = LIMINE_RSDP_REQUEST, .revision = 0};

Mỗi biến chỉ có .id (magic) và .revision; trường .response mặc định là NULL cho tới khi Limine điền. Riêng paging_mode còn gửi kèm mong muốn: .mode = 4LVL (bảng trang 4 tầng).

Đọc từng response: initialiseBootloaderParser()

① Paging mode. Kiểm Limine có cho đúng 4 tầng không; không thì dừng hẳn, vì code paging ở Bài 6 chỉ biết 4 tầng.

c
struct limine_paging_mode_response *liminePagingres = liminePagingreq.response;
if (liminePagingres->mode != LIMINE_PAGING_MODE_X86_64_4LVL) {
  debugf("[paging] We explicitly asked for level 4 paging!\n");
  panic();
}

② HHDM và ③ địa chỉ kernel. Chép thẳng ba con số.

c
bootloader.hhdmOffset = limineHHDMres->offset;
bootloader.kernelVirtBase = limineKrnres->virtual_base;
bootloader.kernelPhysBase = limineKrnres->physical_base;

④ Memory map và tổng RAM. Giữ con trỏ tới mảng entry, rồi cộng length của mọi vùng không phải RESERVED.

c
bootloader.mmEntries = mm_response->entries;
bootloader.mmEntryCnt = mm_response->entry_count;

bootloader.mmTotal = 0;
for (int i = 0; i < mm_response->entry_count; i++) {
  struct limine_memmap_entry *entry = mm_response->entries[i];
  // entry->type != LIMINE_MEMMAP_FRAMEBUFFER &&
  if (entry->type != LIMINE_MEMMAP_RESERVED)
    bootloader.mmTotal += entry->length;
}

Nên mmTotal không phải "RAM trống": nó tính cả vùng bootloader mượn, vùng kernel, cả framebuffer. Cũng không phải "địa chỉ cao nhất": lỗ MMIO ở địa chỉ cao bị bỏ qua. Bài 5 dùng nó để tính kích thước bitmap.

⑤ SMP. Giữ con trỏ tới danh sách CPU, rồi tìm vị trí của BSP bằng cách so LAPIC ID.

c
bootloader.smp = smp_response;
bootloader.smpBspIndex = (uint64_t)(-1);
for (int i = 0; i < smp_response->cpu_count; i++) {
  struct limine_smp_info *entry = smp_response->cpus[i];
  if (entry->lapic_id == smp_response->bsp_lapic_id)
    bootloader.smpBspIndex = i;
}
if (bootloader.smpBspIndex == (uint64_t)(-1)) {
  debugf("[bootloader] Couldn't find bootstrap core!\n");
  panic();
}

⑥ RSDP. RSDP là bảng đầu tiên của ACPI (bảng mô tả bo mạch). Với base revision 2, Limine trả về địa chỉ ảo trong HHDM, nên cavOS trừ hhdmOffset để lưu địa chỉ vật lý; uacpi_kernel_get_rsdp() ở Bài 8 cần đúng PA này.

c
// todo: revision >= 3 and it's not virtual!
struct limine_rsdp_response *rsdp_response = limineRsdpReq.response;
bootloader.rsdp = (size_t)rsdp_response->address - bootloader.hhdmOffset;

Struct đích: include/bootloader.h

c
typedef struct Bootloader {
  size_t hhdmOffset;            // ② ảo ↔ vật lý
  size_t kernelVirtBase;        // ③ kernel ở đâu
  size_t kernelPhysBase;

  size_t rsdp;                  // ⑥ ACPI (PA)

  size_t   mmTotal;             // ④ tổng các vùng không RESERVED
  uint64_t mmEntryCnt;
  LIMINE_PTR(struct limine_memmap_entry **) mmEntries;  // ④ bản đồ RAM
  LIMINE_PTR(struct limine_smp_response *) smp;         // ⑤ danh sách CPU
  uint64_t smpBspIndex;
} Bootloader;

Bootloader bootloader;

Bootloader bootloader; nằm ngay trong header, nên mọi file .c include nó đều "định nghĩa" một bản. Link vẫn được vì Makefile có -fcommon: các định nghĩa không có giá trị đầu gộp lại thành một biến duy nhất.

Các con số này nghĩa là gì

  • ② hhdmOffset (0xffff800000000000 trong mọi lần chạy đã ghi lại): cộng vào PA bất kỳ ra VA đọc/ghi được ngay. Xem HHDM, Paging ý #5.
  • ③ kernel_address: kernel có virt (0xffffffff80000000, địa chỉ link) và phys (nơi Limine chọn đặt kernel trong RAM; không được hard-code). Cùng một frame kernel vì thế có 2 VA (qua HHDM và qua mapping kernel) trỏ về 1 PA: đó là aliasing. Về KASLR: KASLR & PIE Kernel.
  • ④ memmap: chỉ entry LIMINE_MEMMAP_USABLE mới được cấp phát; đây là đầu vào sống còn của Bài 5.
  • ⑥ rsdp: lưu dạng PA thuần; muốn đọc bảng ACPI phải + hhdmOffset lại.

Tự kiểm tra

Bấm vào câu hỏi để xem đáp án.

Vì sao cavOS trừ hhdmOffset khỏi địa chỉ RSDP rồi mới lưu?

Với base revision 2, Limine trả RSDP dưới dạng địa chỉ ảo trong HHDM. uACPI muốn địa chỉ vật lý, nên cavOS trừ độ lệch để về PA. Comment todo nhắc rằng từ revision 3 Limine trả PA sẵn, khi đó phép trừ sẽ sai.

mmTotal có bằng lượng RAM cấp phát được không?

Không. Nó cộng mọi vùng không phải RESERVED, kể cả vùng bootloader, kernel và framebuffer. Trong lab: USABLE = 254 MiB nhưng non-RES = 259 MiB.

Nếu Limine không trả lời một request (.response == NULL) thì cavOS làm gì?

cavOS không kiểm; nó đọc thẳng qua con trỏ NULL và sẽ lỗi ngay. Lab thì kiểm response != NULL trước khi in, đó là cách an toàn nên làm.

Vì sao hhdm và virt giống hệt nhau giữa các lần chạy lab, còn phys thì không nên hard-code?

virt là địa chỉ link trong linker.ld (lab link không PIE nên không thể dời). HHDM là độ lệch Limine chọn; mọi lần chạy đã ghi lại đều là 0xffff800000000000, nhưng code vẫn đọc từ response chứ không viết cứng. phys là chỗ Limine tìm được RAM trống, phụ thuộc kích thước kernel và memmap: lần chạy 2026-05-28 là 0x0ffb2000, lần 2026-09-03 là 0x0ff42000.

Vì sao gom vào struct bootloader thay vì để mỗi file tự đọc response?

Chỉ một chỗ phụ thuộc vào API Limine; RSDP được đổi sang PA một lần; BSP được tìm một lần. Đổi bootloader sau này chỉ phải sửa một file.

Hai "vùng cấm" của isProtectedMemory()

Hai trường hhdmOffset và kernelVirtBase cũng được dùng làm vùng cấm trong cpu/system.c. Vùng kernel được coi là 256 MiB (268435456) tính từ kernelVirtBase, rộng hơn nhiều so với khoảng 1 MiB thật của ảnh kernel:

c
bool isProtectedMemory(uint64_t virt) {
  if (virt > bootloader.hhdmOffset &&
      virt < (bootloader.hhdmOffset + bootloader.mmTotal))
    return true;
  else if (virt > bootloader.kernelVirtBase &&
           virt < bootloader.kernelVirtBase + 268435456) {
    return true;
  }

  return false;
}

Hai vùng này giữ nguyên địa chỉ suốt quá trình chạy, vì cavOS dùng lại bảng trang của Limine (Bài 6). Khái niệm: kernel mapping và direct map.
