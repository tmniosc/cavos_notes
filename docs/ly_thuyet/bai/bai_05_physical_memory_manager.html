Bài 5 - Physical Memory Manager

Status doneTags step, memory

Files: memory/pmm.c, utilities/data_structures/bitmap.c, include/bitmap.h, include/pmm.h
Đầu vào: memmap + mmTotal + hhdmOffset từ Bài 3 - Bootloader Parser
Thực hành: Lab 0x03 - PMM & VMM (nửa PMM)

Mục đích

Sau bài này kernel biết ô RAM vật lý nào còn trống, và cấp/thu hồi được từng ô.

Memmap của Limine chỉ nói RAM nào tồn tại. PMM (Physical Memory Manager) theo dõi ô nào đang có người dùng. Mọi thứ cần bộ nhớ về sau đều bắt đầu bằng PhysicalAllocate(); việc đầu tiên là Bài 6 - Virtual Memory & Paging xin ô RAM để làm page table.

Nói thật đơn giản

PMM giống một quyển sổ giữ kho RAM. RAM được chia thành rất nhiều ô 4 KiB, gọi là frame. Sổ có một bit cho mỗi ô: 1 là đang dùng, 0 là trống. Cả quyển sổ gọi là bitmap. Ai cần bộ nhớ thì xin "một ô trống" (PhysicalAllocate), xong thì trả lại (PhysicalFree); PMM tra sổ, sửa bit, đưa địa chỉ.

Có một chuyện "con gà và quả trứng": bản thân quyển sổ cũng phải nằm trong RAM. Nên PMM tự tìm chỗ đặt sổ, rồi tự đánh dấu chỗ đó là "đang dùng" để không bao giờ cấp nó cho ai. Lúc khởi tạo, PMM đánh dấu mọi ô là đang dùng, rồi chỉ mở đúng những vùng Limine báo là dùng được. Ô nào lạ thì cứ coi là đang dùng, không bao giờ cấp nhầm.

Cần biết trước

Memmap và HHDM đã có từ Bài 3; mới ở đây là frame 4 KiB và cấu trúc bitmap.

  • Memmap, các loại vùng (USABLE, RESERVED, BOOTLOADER_RECLAIMABLE...) và mmTotal — đã gặp ở Bài 3 - Bootloader Parser.
  • HHDM, địa chỉ vật lý (PA) và địa chỉ ảo (VA) — đã gặp ở Bài 3 - Bootloader Parser, dùng lại ở Bài 4 - Framebuffer & Console. Nhắc lại một dòng: CPU chỉ đọc/ghi qua VA; có PA trong tay thì cộng hhdmOffset để ra VA dùng được. Đọc sâu: HHDM.
  • Frame (khung trang) 4 KiB. Phần cứng paging của x86_64 chia bộ nhớ thành trang 4 KiB, nên RAM vật lý cũng được chia thành ô cùng cỡ, gọi là frame. Frame thứ k bắt đầu ở PA k × 4096. Đây là đơn vị nhỏ nhất PMM cấp ra. Đọc sâu: Paging - trang 4 KiB.
  • Bitmap (cấu trúc dữ liệu). Một mảng byte, dùng mỗi bit cho một phần tử. Phần tử k nằm ở byte k / 8, bit k % 8. Một byte theo dõi được 8 frame, nên 256 MiB RAM (65 536 frame) chỉ cần 8 KiB sổ. Code cavOS ở mục bên dưới.

Đọc code cavOS

Từ con số tổng RAM, qua initiatePMM(), tới hai hàm cấp và trả frame.

Trong entry/kernel.c:_start(), ngay sau phần màn hình của Bài 4:

c
// None of the two depend on paging

initiateVMM();   // memory/vmm.c — Bài 6

1. Đầu vào: tổng RAM mmTotal (entry/bootloader.c)

c
// Total memory
bootloader.mmTotal = 0;
for (int i = 0; i < mm_response->entry_count; i++) {
  struct limine_memmap_entry *entry = mm_response->entries[i];
  // entry->type != LIMINE_MEMMAP_FRAMEBUFFER &&
  if (entry->type != LIMINE_MEMMAP_RESERVED)
    bootloader.mmTotal += entry->length;
}

mmTotal là tổng độ dài các vùng không phải RESERVED, không phải "địa chỉ cao nhất". Lý do nằm ở sơ đồ dưới: RAM không phải một dải liền từ 0. Không gian địa chỉ vật lý là một bản đồ chung; RAM chỉ chiếm vài mảnh, xen giữa là vùng BIOS/ACPI và MMIO của thiết bị (Bài 4). Lấy địa chỉ cao nhất sẽ làm bitmap phình theo các lỗ đó.

  • RAM có lỗ: vùng BIOS quanh 0x9fc00, PCI hole quanh 0xfd000000.
  • Địa chỉ cao không phải RAM: 0xfd000000 (framebuffer) và 0xfd00000000 là MMIO.
  • Dòng comment cho thấy tác giả từng tính bỏ cả FRAMEBUFFER, nhưng code hiện tại vẫn cộng nó (chỉ loại RESERVED).

2. Cấu trúc DS_Bitmap (include/bitmap.h, include/pmm.h)

c
typedef struct DS_Bitmap {
  uint8_t *Bitmap;
  size_t   BitmapSizeInBlocks; // CEIL(x / BLOCK_SIZE)
  size_t   BitmapSizeInBytes;  // CEIL(blockSize / 8)
  size_t allocatedSizeInBlocks;
  size_t lastDeepFragmented;   // optimization(1), xem mục 5
  size_t mem_start;
  bool   ready; // has been initiated
} DS_Bitmap;

#define BLOCKS_PER_BYTE 8 // using uint8_t
#define BLOCK_SIZE 4096
#define INVALID_BLOCK ((size_t)-1)

// include/pmm.h
DS_Bitmap physical;

"Block" trong code chính là frame 4 KiB. physical là biến toàn cục nên mọi trường khởi đầu bằng 0, trong đó mem_start = 0. Vì vậy block k ứng đúng với PA k × 4096, và địa chỉ PhysicalAllocate trả về là PA dùng thẳng được.

3. initiatePMM() — dựng quyển sổ (memory/pmm.c)

c
void initiatePMM() {
  DS_Bitmap *bitmap = &physical;
  bitmap->ready = false;

  // (1) cỡ sổ: số frame, rồi số byte
  physical.BitmapSizeInBlocks = DivRoundUp(bootloader.mmTotal, BLOCK_SIZE);
  physical.BitmapSizeInBytes = DivRoundUp(physical.BitmapSizeInBlocks, 8);

  // (2) tìm vùng USABLE đầu tiên đủ chỗ chứa sổ
  struct limine_memmap_entry *mm = 0;
  for (int i = 0; i < bootloader.mmEntryCnt; i++) {
    struct limine_memmap_entry *entry = bootloader.mmEntries[i];
    if (entry->type != LIMINE_MEMMAP_USABLE ||
        entry->length < physical.BitmapSizeInBytes)
      continue;
    mm = entry;
    break;
  }
  if (!mm) { debugf("[pmm] Not enough memory: ..."); panic(); }

  // (3) đặt sổ ở đầu vùng đó, truy cập qua HHDM
  size_t bitmapStartPhys = mm->base;
  physical.Bitmap = (uint8_t *)(bitmapStartPhys + bootloader.hhdmOffset);

  // (4) đóng hết, mở USABLE, đóng lại phần không phải USABLE
  memset(physical.Bitmap, 0xff, physical.BitmapSizeInBytes);
  for (...) if (entry->type == LIMINE_MEMMAP_USABLE)
      MarkRegion(bitmap, (void *)entry->base, entry->length, 0);
  for (...) if (entry->type != LIMINE_MEMMAP_USABLE)
      MarkRegion(bitmap, (void *)entry->base, entry->length, 1);

  // (5) tự đánh dấu chỗ của chính quyển sổ
  MarkRegion(bitmap, (void *)bitmapStartPhys, physical.BitmapSizeInBytes, 1);
  physical.allocatedSizeInBlocks = 0;

  debugf("[pmm] Bitmap initiated: bitmapStartPhys{0x%lx} size{%lx}\n", ...);
  bitmap->ready = true;
}
  • Bước 2–3: sổ không cần allocator nào khác; nó tự chiếm đầu vùng USABLE đầu tiên đủ lớn. Ghi vào sổ qua VA HHDM, vì CPU không ghi thẳng bằng PA được.
  • Bước 4: memset 0xff làm mọi frame thành "đang dùng". Sau đó chỉ vùng USABLE được mở. Frame nằm trong lỗ địa chỉ không thuộc entry nào, nên giữ nguyên 1 mãi mãi. Vòng thứ ba đánh dấu lại mọi vùng non-USABLE là đang dùng, cho chắc.
  • Bước 5: nếu thiếu bước này, frame đầu tiên được cấp chính là chỗ đang chứa sổ.

Log thật khi boot cavOS (QEMU -m 4g, lab/outputs/cavos-boot-2026-09-03.txt):

text
[pmm] Bitmap initiated: bitmapStartPhys{0x60000} size{20050}

%lx in hex không có tiền tố: 0x20050 = 131 152 byte ≈ 128 KiB, đúng cỡ cho khoảng 4 GiB (4 GiB / 4 KiB / 8 = 131 072 byte). Sổ nằm ở 0x60000, đầu một vùng USABLE thấp.

4. Đọc/ghi một bit, đổi địa chỉ ↔ block (bitmap.c)

c
int BitmapGet(DS_Bitmap *bitmap, size_t block) {
  size_t addr = block / BLOCKS_PER_BYTE;
  size_t offset = block % BLOCKS_PER_BYTE;
  return (bitmap->Bitmap[addr] & (1 << offset)) != 0;
}
void BitmapSet(DS_Bitmap *bitmap, size_t block, bool value) {
  ... if (value) Bitmap[addr] |= (1 << offset);
      else       Bitmap[addr] &= ~(1 << offset);
}

void *ToPtr(DS_Bitmap *bitmap, size_t block)       // block → địa chỉ
  { return (void *)(bitmap->mem_start + block * BLOCK_SIZE); }
size_t ToBlock(DS_Bitmap *bitmap, void *ptr)       // địa chỉ → block, làm tròn xuống
  { return (size_t)(ptr - mem_start) / BLOCK_SIZE; }
size_t ToBlockRoundUp(DS_Bitmap *bitmap, void *ptr) // địa chỉ → block, làm tròn lên
  { return DivRoundUp((size_t)(ptr - mem_start), BLOCK_SIZE); }

Comment đầu bitmap.c viết 10000000 -> first block is allocated: chuỗi đó đọc từ trái sang theo thứ tự block. Còn bên trong một byte, block nhỏ nhất là bit 0 (bit thấp nhất).

MarkRegion(base, sizeBytes, isUsed) đánh dấu cả một vùng, và làm tròn khác nhau tuỳ chiều:

c
if (isUsed) {
  base = ToBlock(bitmap, basePtr);              // tròn xuống
  size = DivRoundUp(sizeBytes, BLOCK_SIZE);     // tròn lên
} else {
  base = ToBlockRoundUp(bitmap, basePtr);       // tròn lên
  size = sizeBytes / BLOCK_SIZE;                // tròn xuống
}
MarkBlocks(bitmap, base, size, isUsed);
  • Đánh dấu "dùng": phủ rộng ra, chỉ cần frame có một byte bị dùng là đóng cả frame.
  • Đánh dấu "trống": co hẹp lại, chỉ mở frame nằm trọn trong vùng. Mở nhầm một frame chỉ trống một nửa là cấp đè dữ liệu của người khác.

5. Tìm chỗ trống: FindFreeRegion và lastDeepFragmented

c
size_t FindFreeRegion(DS_Bitmap *bitmap, size_t blocks) {
  size_t currentRegionStart = bitmap->lastDeepFragmented;
  size_t currentRegionSize = 0;
  for (size_t i = currentRegionStart; i < bitmap->BitmapSizeInBlocks; i++) {
    if (BitmapGet(bitmap, i)) {          // gặp frame đang dùng: đếm lại từ frame sau
      currentRegionSize = 0;
      currentRegionStart = i + 1;
    } else {
      if (blocks == 1)                    // optimization(1)
        bitmap->lastDeepFragmented = currentRegionStart + 1;
      currentRegionSize++;
      if (currentRegionSize >= blocks)    // đủ số frame liền nhau
        return currentRegionStart;
    }
  }
  return INVALID_BLOCK;
}
  • First-fit: lấy dải trống liền nhau đầu tiên đủ dài, không tìm dải vừa khít nhất.
  • lastDeepFragmented: mốc mà mọi frame phía dưới đều đang dùng. Cấp một frame xong, mốc nhảy tới ngay sau frame đó, nên lần sau khỏi quét lại từ đầu. Khi trả một frame thấp hơn mốc, MarkBlocks kéo mốc xuống. Cấp từng frame một trong vòng lặp là kiểu dùng phổ biến nhất, nên tối ưu này đáng giá.
  • BitmapAllocate(bitmap, blocks) gọi hàm này, đánh dấu dải tìm được là 1, rồi trả ToPtr(...); không tìm thấy thì trả 0.

6. API cho cả kernel: PhysicalAllocate / PhysicalFree (memory/pmm.c)

c
size_t PhysicalAllocate(int pages) {
  spinlockAcquire(&LOCK_PMM);
  size_t phys = (size_t)BitmapAllocate(&physical, pages);
  spinlockRelease(&LOCK_PMM);
  if (!phys) {
    debugf("[vmm::alloc] Physical kernel memory ran out!\n");
    panic();
  }
  return phys;
}

void PhysicalFree(size_t ptr, int pages) {
  spinlockAcquire(&LOCK_PMM);
  MarkRegion(&physical, (void *)ptr, pages * BLOCK_SIZE, 0);
  spinlockRelease(&LOCK_PMM);
}
  • Trả về PA của pages frame liền nhau. Muốn đọc/ghi nội dung thì cộng hhdmOffset.
  • Hết RAM thì panic, không lặng lẽ trả NULL.
  • Spinlock LOCK_PMM giữ cho hai CPU không sửa sổ cùng lúc (SMP về sau).

Tự kiểm tra

Bấm vào câu hỏi để xem đáp án.

Vì sao initiatePMM() đặt mọi bit thành 1 trước, rồi mới mở vùng USABLE, chứ không làm ngược lại?

Vì những frame không thuộc entry nào (lỗ địa chỉ) sẽ không bao giờ được vòng lặp nào chạm tới. Bắt đầu bằng 1 thì chúng mặc định "đang dùng" và không bao giờ bị cấp; bắt đầu bằng 0 thì chúng sẽ bị coi là trống.

PhysicalAllocate(1) trả 0x56000. Muốn xoá trắng frame đó, kernel phải memset vào địa chỉ nào?

Vào 0x56000 + hhdmOffset = 0xffff800000056000. CPU coi mọi địa chỉ là địa chỉ ảo và dịch qua page table; PA phải được đổi sang VA trong HHDM trước khi dùng.

Khi đánh dấu "trống", MarkRegion làm tròn base lên và size xuống. Nếu làm ngược lại thì sao?

Một vùng có mép không chia hết 4 KiB sẽ mở luôn frame chỉ trống một phần. Frame đó có thể bị cấp cho người khác trong khi phần còn lại vẫn đang chứa dữ liệu, hai bên ghi đè nhau.

QEMU cấp 256 MiB (65 536 frame) nhưng lab in total frames = 66405. Phần dư từ đâu ra?

mmTotal cộng mọi vùng không phải RESERVED, kể cả FRAMEBUFFER (4000 K = 1000 frame), BOOT_REC (217 frame) và KERNEL (4 frame). 65 184 USABLE + 217 + 4 + 1000 = 66 405. Sổ vì thế hơi to hơn số RAM thật, đổi lại code tính tổng đơn giản.

Vì sao FindFreeRegion được phép bắt đầu quét từ lastDeepFragmented mà không bỏ sót frame trống nào?

Vì mốc đó chỉ dời lên ngay sau một frame vừa cấp, khi mọi frame phía dưới đều đang dùng; và mỗi lần trả một frame thấp hơn, MarkBlocks kéo mốc xuống lại. Nên phía dưới mốc luôn không có frame trống.

Lỗi thật đã gặp khi làm lab, chỗ cavOS không chặn biên, và các liên hệ.

Lab 0x03 đã vá một lỗi làm tròn khi đánh dấu bitmap

Bản đầu của bm_mark trong lab tính số frame bằng n = len / PAGE, tức làm tròn xuống. Mọi vùng memmap đều dài bội số của 4 KiB nên không sao; chỉ riêng lần tự đánh dấu bitmap (8301 byte, không chia hết) là lộ lỗi.

Ở lần chạy cũ (2026-06-01, lab/outputs/lab-0x03-run.txt), bitmap nằm ở 0x60000–0x6206d, trải 3 frame nhưng chỉ 2 frame được đánh dấu. Frame thứ ba 0x62000 vẫn "trống" trong khi đang chứa 109 byte cuối của bitmap, và đúng là alloc #1 PA = 0x62000:

text
[pmm] bitmap at PA = 0x0000000000060000  (block #96)  VA = 0xffff800000060000
[pmm] free frames  = 65196
[pmm] alloc #1 PA  = 0x0000000000062000

Lần đó không sập chỉ vì may. Frame 0x62000 được paging_init dùng làm PML4 mới và chép đủ 512 entry từ PML4 của Limine vào. Theo trang lab, PML4 này chỉ có entry 192/256/511 khác 0 (từ byte 1536 trở đi; entry 192 do vmap thêm sau), nên 109 byte đầu bị ghi đè bằng số 0. 109 byte đó là bit của block 65 536 trở lên, tức PA từ 0x10000000: phía trên 256 MiB RAM, không có RAM thật. Sổ vì thế báo khoảng 869 frame "ảo" là trống. Lab chỉ cấp vài frame ở vùng thấp nên chưa bao giờ chạm tới chúng; một chương trình cấp nhiều hơn sẽ nhận về địa chỉ không có RAM phía sau. Bản sửa dùng DivRoundUp(len, PAGE_SIZE); lần chạy 2026-09-03 ở mục Tự làm cho thấy frame cấp đầu tiên nằm ngay sau frame cuối của bitmap. cavOS không dính lỗi này vì nhánh "dùng" của MarkRegion đã làm tròn lên.

cavOS không chặn biên trong MarkBlocks

MarkBlocks lặp BitmapSet từ start tới start + size mà không so với BitmapSizeInBlocks. Vòng "đóng non-USABLE" có chạm những entry ở địa chỉ rất cao, như framebuffer 0xfd000000 hay vùng RESERVED 0xfd00000000. Chỉ số block của chúng lớn hơn nhiều so với số block mà sổ có (sổ chỉ tính theo mmTotal), nên các bit đó rơi ra ngoài sổ, ghi vào RAM nằm sau sổ qua HHDM. Lab thêm một dòng chặn trong bm_mark:

c
for (uint64_t i = 0; i < count; i++) {
    if (first + i >= blocks)   // GUARD: không ghi ra ngoài bitmap
        break;
    ...
}

Trước đó lab còn từng tính cỡ sổ theo "địa chỉ cuối cao nhất" thay vì mmTotal, làm bitmap phình tới khoảng 33 MB vì entry 0xfd00000000. Đổi sang cách cộng dồn của cavOS thì còn 8 KB.

Câu hỏi mở cũ (đã trả lời)

  • Bitmap đặt ở đâu? Ngay đầu vùng USABLE đầu tiên đủ lớn (mm->base), truy cập qua HHDM; tự MarkRegion chính nó là đang dùng.
  • Vùng reserved/ACPI/framebuffer xử lý sao? memset 0xff (mặc định đang dùng) rồi chỉ mở USABLE; non-USABLE được đánh dấu lại là đang dùng thêm một lần.
