Bài 12 - Multitasking & Scheduler

Status doneTags step, scheduler, tasks, context switch

Hàm: initiateTasks() (multitasking/task.c), initiateKernelThreads() (entry/kernel_helper.c), schedule() (multitasking/schedule.c) · Phụ thuộc: tick 1 ms từ Bài 10 - APIC & Timer, khung ngắt từ Bài 9 - IDT & Interrupts, RSP0 của TSS từ Bài 7 - GDT & TSS, PML4/CR3 từ Bài 6 - Virtual Memory & Paging. Thông tin SMP từ Bài 3 - Bootloader Parser có được đọc, nhưng cavOS chỉ chạy trên một CPU.

Mục đích

Kernel chạy nhiều việc "cùng lúc" trên một CPU.

Từ bài này cavOS có task: mỗi task là một dòng chạy riêng, có thanh ghi, stack và không gian địa chỉ (PML4) của nó. Timer của Bài 10 bắn mỗi 1 ms, và mỗi lần bắn, scheduler cướp CPU khỏi task đang chạy để trao cho task kế tiếp. Đây cũng là lúc mov cr3 thật sự được dùng để đổi không gian địa chỉ (Bài 6). Các bài sau đều cần nó: driver mạng chạy trong thread riêng, chương trình userspace (Bài 18 - Userspace & ELF Loader) là task, và read() bàn phím (Bài 11) chờ bằng cách cho task "ngủ".

Nói thật đơn giản

Một đầu bếp (CPU) phải nấu nhiều món (task). Mỗi món có một tấm thẻ ghi đang làm tới bước nào. Trong bếp có cái chuông reo mỗi mili giây (timer). Chuông reo thì đầu bếp ghi bước hiện tại vào thẻ của món đang làm, lấy thẻ của món kế tiếp trong hàng, và làm tiếp đúng chỗ thẻ đó ghi. Món nào đang chờ nước sôi (ngủ) hay chờ khách gọi (chờ phím) thì bỏ qua, khỏi phí lượt. Đổi món nhanh tới mức nhìn từ ngoài như mọi món được nấu cùng lúc.

Ở cavOS, "tấm thẻ" chính là cái khung thanh ghi mà CPU và isr_common vừa đẩy lên stack khi chuông (ngắt) reo. Đổi món = cất khung đó đi, dựng khung của món kế tiếp, rồi iretq: CPU "quay về" món kia như thể nó vừa bị ngắt ở đó.

Cần biết trước

Hai ý mới; mọi thứ khác đã có ở Bài 6, 7, 9, 10, 11.

  • Task và ngữ cảnh. Một task là một dòng chạy mà kernel có thể dừng rồi cho chạy tiếp. Muốn vậy phải giữ lại ngữ cảnh của nó: mọi thanh ghi đa dụng, RIP, RSP, RFLAGS, CS/SS, và CR3 (không gian địa chỉ). Mỗi task cần stack riêng, vì hàm đang chạy dở của nó còn nằm trên stack. cavOS gọi cả thread kernel lẫn process userspace là "task".
  • Preemptive và cooperative. Cooperative: task tự nhường CPU (gọi hàm "yield"); task nào quên nhường là chiếm luôn CPU. Preemptive: một ngắt timer lấy CPU lại bất kể task muốn hay không. cavOS dùng cả hai: tick 1 ms để cướp, và handControl() để task tự nhường khi đang chờ.
  • Đã gặp: khung AsmPassedInterrupt, isr_common, iretq, interrupt gate xoá IF ở Bài 9; TSS chỉ để giữ RSP0 ở Bài 7 (đọc sâu: GDT); timerTick → schedule() ở Bài 10; PML4, CR3, HHDM ở Bài 6 (đọc sâu: Paging); kbIrq và kbTaskRead ở Bài 11.

Đọc code cavOS

Dựng task 0 và task dummy, tạo thread helper, rồi mỗi tick schedule() cất khung ngắt của task cũ và iretq vào khung của task mới.

2. struct Task và danh sách task

Mỗi task là một struct Task (include/task.h). Phần cho đa nhiệm (struct thật dài hơn nhiều: signal, file, termios, FPU…):

c
struct Task {
  uint64_t id;
  ...
  bool     kernel_task;
  uint8_t  state;

  AsmPassedInterrupt registers;     // ngữ cảnh đã cất: đúng hình khung ngắt (Bài 9)
  uint64_t whileTssRsp;             // đỉnh stack nạp vào TSS.rsp0 khi task chạy
  uint64_t whileSyscallRsp;         // đỉnh stack cho lệnh syscall (Bài 16)

  uint64_t *pagedirOverride;        // PML4 tạm thời (xem mục 4)
  bool systemCallInProgress;
  bool schedPageFault;              // handControl() đang cố tình gây page fault (mục 8)
  ...
  uint64_t fsbase;                  // TLS của userspace
  uint64_t gsbase;
  size_t forcefulWakeupTimeUnsafe;  // != 0: đánh thức khi timerTicks tới giá trị này
  ...
  TaskInfoPagedir *infoPd;          // infoPd->pagedir = PML4 của task
  ...
  __attribute__((aligned(16))) uint8_t fpuenv[512];
  ...
  Task *parent;
  Task *next;                       // danh sách liên kết đơn
};

Task *firstTask;    // đầu danh sách = task 0
Task *currentTask;  // task đang chạy
Task *dummyTask;    // task "không có ai" (idle)
bool tasksInitiated;
  • Không có run queue riêng. Mọi task, kể cả đang ngủ hay đã chết chờ dọn, nằm trên một danh sách liên kết đơn firstTask → next → … → NULL. Task mới nối vào cuối (taskListAllocate). Scheduler duyệt danh sách để tìm task READY.
  • Ngữ cảnh = một khung ngắt. registers có kiểu AsmPassedInterrupt, chính là hình mà isr_common để lại trên stack: DS, 15 thanh ghi, số vector, error code, rồi RIP, CS, RFLAGS, RSP, SS do CPU đẩy. Không có struct "context" riêng.
  • Các state (enum TASK_STATE): DEAD=0, READY=1, IDLE=2, WAITING_INPUT=3, CREATED=4, WAITING_CHILD=5, WAITING_CHILD_SPECIFIC=6, WAITING_VFORK=7, BLOCKED=8, SIGKILLED=9, FUTEX=10, DUMMY=69. Không có state "RUNNING": task đang chạy vẫn là READY, chỉ khác là nó bằng currentTask.

3. initiateTasks(): task 0 và task dummy

c
// multitasking/task.c
void kernelDummyEntry() {
  while (true)
    asm volatile("pause");
}

void initiateTasks() {
  firstTask = (Task *)malloc(sizeof(Task));
  memset(firstTask, 0, sizeof(Task));

  currentTask = firstTask;
  currentTask->id = KERNEL_TASK_ID;             // 0
  currentTask->state = TASK_STATE_READY;
  currentTask->infoPd = taskInfoPdAllocate(false);
  currentTask->infoPd->pagedir = GetPageDirectory();
  currentTask->kernel_task = true;
  ...
  taskNameKernel(currentTask, entryCmdline, sizeof(entryCmdline));   // "kernel"

  void  *tssRsp = VirtualAllocate(USER_STACK_PAGES);
  size_t tssRspSize = USER_STACK_PAGES * BLOCK_SIZE;
  memset(tssRsp, 0, tssRspSize);
  currentTask->whileTssRsp = (uint64_t)tssRsp + tssRspSize;
  ...
  tasksInitiated = true;

  // task 0 represents the execution we're in right now

  // create a dummy task in case the scheduler has nothing to do
  dummyTask = taskCreateKernel((uint64_t)kernelDummyEntry, 0);
  dummyTask->state = TASK_STATE_DUMMY;
  taskNameKernel(dummyTask, dummyCmdline, sizeof(dummyCmdline));
}
  • Task 0 là chính _start(). Không tạo stack hay thanh ghi mới cho nó: nó đang chạy rồi. Thanh ghi của nó sẽ được cất lần đầu khi tick kế tiếp đổi task. Nó vẫn chạy trên stack boot của Limine, với PML4 hiện tại.
  • Task dummy có state DUMMY nên vòng tìm task READY không bao giờ chọn nó; schedule() chỉ dùng nó khi không tìm được ai. Nó quay pause chứ không hlt, nên CPU không thật sự nghỉ.
  • tasksInitiated = true phải đặt trước taskCreateKernel, vì PageDirectoryAllocate() panic nếu chưa có task ("Tried to allocate pd without tasks initiated").

void stackGenerateKernel(Task *target, uint64_t parameter) {
  void *oldPagedir = GetPageDirectory();
  ...

  ...
  stackGenerateMutual(target);                  // map USER_STACK_PAGES trang ngay dưới USER_STACK_BOTTOM
  target->registers.rdi = parameter;

  • Khung iretq đầu tiên được viết tay. Thread chưa từng bị ngắt, nhưng taskCreate điền registers y như một khung ngắt: RIP = hàm thread, CS/SS kernel, RFLAGS = 0x200 (chỉ bit IF), RDI = tham số (đối số đầu tiên theo SysV ABI). Lần đầu được chọn, iretq đưa CPU vào đầu hàm.
  • PML4 riêng = chép 512 entry PML4 của task 0. Chép entry, không chép bảng con: nửa cao (kernel, HHDM) dùng chung bảng con nên mọi task thấy cùng kernel. Ô còn trống ở nửa thấp là của riêng task.
  • Stack chạy nằm ở nửa thấp, ngay dưới USER_STACK_BOTTOM = 0x800000000000 (ô PML4 255), map trong PML4 của task. Mọi kernel thread có stack ở cùng một VA nhưng khác frame vật lý; Lab 0x07 in ra điều này. Muốn map vào PML4 khác, stackGenerateKernel phải tạm ChangePageDirectory sang nó rồi đổi lại.
  • taskKernelReturn nằm ở đỉnh stack, đúng chỗ một lệnh call để lại địa chỉ trả về. Hàm thread ret là rơi vào taskKill. RSP bắt đầu ở 0x7ffffffffff8: lệch 8 so với bội 16, đúng như ngay sau một call.
  • pagedirOverride tồn tại vì ChangePageDirectory tạm thời đó: nó ghi PML4 tạm vào currentTask->pagedirOverride, và schedule() nạp pagedirOverride nếu có. Không có nó, một tick giữa hai lệnh ChangePageDirectory sẽ làm task quay về với PML4 cũ của nó, và phần còn lại của stack mới bị map nhầm vào PML4 của task đang tạo.
  • Giá của một kernel thread: 2048 trang TSS stack + 2048 trang syscall stack (VirtualAllocate = PhysicalAllocate liền khối + HHDM) + 2048 trang stack chạy (stackGenerateMutual cấp từng trang) = 24 MiB, đều được memset về 0 ngay.

  • Mỗi tick đều đổi task (nếu có task READY khác): lát thời gian của mỗi task là 1 tick = 1 ms.

6. schedule(): chọn task kế tiếp

c
// multitasking/schedule.c
void schedule(uint64_t rsp) {
  if (!tasksInitiated)
    return;

  // try to find a next task
  AsmPassedInterrupt *cpu = (AsmPassedInterrupt *)rsp;
  Task               *next = currentTask->next;
  if (!next)
    next = firstTask;

  int fullRun = 0;
  while (next->state != TASK_STATE_READY) {
    if (signalsRevivableState(next->state) && signalsPendingQuick(next)) {
      ...                                       // có signal: dậy để syscall trả -EINTR
      next->state = TASK_STATE_READY;
      break;
    }
    if (next->forcefulWakeupTimeUnsafe &&
        next->forcefulWakeupTimeUnsafe <= timerTicks) {
      // no race! the task has to already have been suspended to end up here
      next->state = TASK_STATE_READY;
      next->extras |= EXTRAS_INVOLUTARY_WAKEUP;
      next->forcefulWakeupTimeUnsafe = 0;
      ...
      break;
    }
    next = next->next;
    if (!next) {
      fullRun++;
      if (fullRun > 2)
        break;
      next = firstTask;
    }
  }

  // found no task
  if (!next)
    next = dummyTask;
  • Round-robin: bắt đầu từ task sau task hiện tại, đi vòng tròn. Task hiện tại cũng nằm trong vòng, nên nếu chỉ còn nó READY thì nó được chọn lại.
  • Đánh thức theo giờ nằm ngay trong vòng tìm: task ngủ có hẹn (forcefulWakeupTimeUnsafe) được đổi về READY và chọn luôn khi tới giờ. Không có hàng đợi hẹn giờ riêng.
  • Không ai READY: sau hơn hai vòng (fullRun > 2), next là NULL và dummy được chọn.
  • Phần giữa hàm (bỏ qua ở đây) lo signal cho task userspace, itimer SIGALRM, nhả spinlockQueueEntry, và đổi FS/GS base qua MSR.

asm
; cpu/isr.asm
asm_finalize:
  ; rdi = switch stack pointer
  ; rsi = next pagedir

  mov rsp, rdi
  mov cr3, rsi

  pop rbp
  ; mov ds, ebp
  mov es, ebp

  pop r15
  ...                ; cùng đoạn pop như cuối isr_common
  pop rax

  add rsp, 16      ; pop error code and interrupt number
  iretq            ; pops (CS, EIP, EFLAGS) and also (SS, ESP) if privilege change occurs
  • Lưu ở đâu: cả hai. Ngắt đẩy thanh ghi lên stack của task (CPU đẩy 5 qword, stub 2, isr_common 16). schedule() chép khung đó vào TCB (Task.registers). Khi chạy lại, chép ngược từ TCB xuống đỉnh TSS stack của task rồi iretq từ đó.
  • Vì sao dựng khung ở đỉnh whileTssRsp? Đó là chỗ chắc chắn trống: task không chạy nên không ai dùng TSS stack của nó. Với task userspace bị ngắt ở ring 3, CPU chuyển sang TSS.rsp0, và cả khung (5 + 2 + 16 = 23 qword = sizeof(AsmPassedInterrupt)) nằm đúng ở whileTssRsp - sizeof(AsmPassedInterrupt): chỗ schedule() dựng khung lần sau.
  • TSS.rsp0 theo từng task (Bài 7): mỗi lần đổi task, cavOS ghi tssPtr->rsp0 = next->whileTssRsp. Ngắt từ ring 3 nhờ vậy luôn rơi vào stack kernel của đúng task đang chạy. Với kernel thread (ring 0), CPU không đổi stack khi ngắt nên không đọc rsp0; whileTssRsp chỉ còn là chỗ dựng khung iretq.
  • CR3 theo từng task: asm_finalize nạp PML4 của task mới. Nó đổi RSP trước CR3: khung nằm ở HHDM (nửa cao), PML4 nào cũng thấy; còn stack cũ ở nửa thấp sắp không còn map.
  • Không tick nào chen vào được. schedule() chạy trong ngắt qua interrupt gate, nên IF = 0 từ lúc vào tới iretq. iretq nạp RFLAGS của task mới (IF = 1) cùng lúc với RIP và RSP.
  • FPU/SSE chỉ được cất/nạp cho task userspace (fxsave/fxrstor); kernel thread không được dùng SSE (Bài 17).

8. Tự nhường CPU: handControl() và page fault "ma thuật"

c
// cpu/system.c
void handControl() {
  if (!tasksInitiated)
    return;
  assert(checkInterrupts()); // no volatile contexts
  currentTask->schedPageFault = true;
  volatile uint8_t _drop = *(uint8_t *)(SCHED_PAGE_FAULT_MAGIC_ADDRESS);   // 0x5FFFFFFFF000
  (void)(_drop);
}

// cpu/isr.c:handle_interrupt(), nhánh exception
    // To drop the current execution and give control to the scheduler, set this
    // variable and generate a page fault onto the magic address
    if (currentTask->schedPageFault && cpu->interrupt == 14) {
      uint64_t errorLocation = 0;
      asm volatile("movq %%cr2, %0" : "=r"(errorLocation));
      if (errorLocation == SCHED_PAGE_FAULT_MAGIC_ADDRESS) {
        currentTask->schedPageFault = false;
        cpu->rip++;
        schedule((uint64_t)cpu);
        return;
      }
    }
  • Muốn gọi schedule() thì phải có một khung ngắt. Thay vì viết đường gọi riêng, cavOS cố tình đọc một địa chỉ không map: CPU sinh page fault, đẩy khung như mọi ngắt, và handler thấy cờ schedPageFault cùng CR2 (địa chỉ gây lỗi) đúng địa chỉ ma thuật thì gọi schedule().
  • Page fault là fault: RIP trong khung trỏ vào chính lệnh đọc. Không sửa RIP thì task chạy lại sẽ đọc lại và fault mãi. cavOS cộng 1 vào RIP: xem Đọc thêm vì sao chuyện này chạy được nhờ may.
  • assert(checkInterrupts()): không được nhường CPU từ trong IRQ handler hay vùng cli.
  • Người gọi: sleep(), spinlockAcquire, readHandler, semaphoreWait, taskCallReaper, vòng lặp của thread helper, networking (ipv4.c, lwIP sys_arch.c)…

9. Ngủ và chờ

c
// cpu/timer.c — task vẫn READY, chỉ nhường CPU mỗi vòng
uint32_t sleep(uint32_t time) {
  uint64_t target = timerTicks + (time);
  while (target > timerTicks)
    handControl();
  return 0;
}

// syscalls/linux/syscalls_clock.c:syscallNanosleep — task BLOCKED, scheduler đánh thức
  size_t ms = duration->tv_sec * 1000 + duration->tv_nsec / 1000000;
  currentTask->forcefulWakeupTimeUnsafe = timerTicks + ms;
  currentTask->state = TASK_STATE_BLOCKED;
  do
    handControl();
  while (currentTask->forcefulWakeupTimeUnsafe > timerTicks);

// syscalls/io.c:readHandler — chờ phím
  kbTaskRead(currentTask->id, (char *)kernelBuff, limit, true);   // state = WAITING_INPUT
  asm volatile("sti"); // leave this task/execution (awaiting return)
  while (currentTask->state == TASK_STATE_WAITING_INPUT) {
    handControl();
  }

// drivers/kb.c — gọi từ kbIrq khi có Enter (ICANON) hoặc mỗi ký tự (không ICANON)
void kbFinaliseStream() {
  Task *task = taskGet(kbTaskId);
  if (task) {
    task->tmpRecV = kbCurr;
    task->state = TASK_STATE_READY;
  }
  kbReset();
}
  • Hai kiểu ngủ. sleep() của kernel giữ task READY: mỗi vòng round-robin nó được chọn, kiểm giờ, nhường tiếp. nanosleep (và poll, futex, lwIP) đặt BLOCKED + giờ hẹn: scheduler bỏ qua task cho tới giờ hẹn. Lab 0x07 đo: 50 ms sleep() được chọn 17–19 lần, 50 ms BLOCKED được chọn đúng 1 lần.
  • Chờ sự kiện (phím) dùng một state riêng (WAITING_INPUT) mà chỉ IRQ của sự kiện đó đổi lại. Task chờ vẫn lặp handControl(), nhưng vì không READY nên vòng lặp đó chỉ chạy một lần mỗi lần được đánh thức.

  • Task không tự dọn được mình: nó đang đứng trên stack sắp trả, và PML4 của nó đang nằm trong CR3. Nên taskKill chỉ đặt DEAD và giao task cho reaper. Nếu task tự giết mình, nó sti rồi lặp rỗng cho tới tick kế tiếp: state DEAD nên không bao giờ được chọn lại.
  • helperReaper (trong thread helper, ngữ cảnh khác) trả TSS stack và syscall stack (VirtualFree), bỏ phần thông tin fs, rồi taskListDestroy gỡ task khỏi danh sách và free struct. Bảng file và PML4 userspace đã được taskKill trả trước đó (taskInfoFilesDiscard, taskInfoPdDiscard).
  • initiateKernelThreads chỉ tạo đúng một thread kernel này. lwIP tạo thêm thread của nó sau đó qua sys_thread_new → taskCreateKernel (networking/lwip/sys_arch.c).

11. Spinlock trên một CPU

c
// utilities/spinlock.c
void spinlockAcquire(Spinlock *lock) {
  while (atomic_flag_test_and_set_explicit(lock, memory_order_acquire))
    handControl();
}
  • cavOS không khởi động CPU phụ, nhưng vẫn cần khoá: tick có thể đổi task giữa hai lệnh bất kỳ, kể cả giữa lúc task đang sửa một danh sách.
  • Bận thì nhường CPU chứ không quay tại chỗ. Trên một CPU, người đang giữ khoá chỉ chạy tiếp được khi ta nhường; quay tại chỗ chỉ đốt hết lát thời gian.

Tự kiểm tra

Năm câu kiểm tra hiểu, không phải nhớ.

Task 0 không có taskCreate nào. Thanh ghi của nó được cất vào firstTask->registers lúc nào?

Ở tick đầu tiên sau initiateTasks() làm đổi task: schedule() chép khung ngắt (đang nằm trên stack boot của Limine) vào old->registers, với old là task 0. Trước đó registers của nó toàn số 0, và không ai cần đọc.

Vì sao handle_interrupt phải gửi EOI trước khi gọi timerTick?

Vì schedule() thường không return: nó iretq thẳng sang task khác. Code sau lời gọi handler không chạy với tick đó; nếu EOI nằm ở đó, LAPIC coi ngắt timer chưa xong và không gửi tick mới.

Hai kernel thread có biến cục bộ ở cùng địa chỉ 0x7fffffffffa8. Vì sao không đè lên nhau?

Mỗi task có PML4 riêng, và ô PML4 255 (nửa thấp, nơi đặt stack) của mỗi PML4 trỏ tới bảng và frame riêng. asm_finalize nạp CR3 của task mới, nên cùng VA dịch ra frame khác tuỳ task đang chạy.

Một kernel thread gọi sleep(100) và một thread khác gọi nanosleep 100 ms. Ai tốn CPU hơn trong lúc ngủ?

Thread gọi sleep(): nó vẫn READY, nên mỗi vòng round-robin được chọn một lần chỉ để thấy chưa tới giờ rồi nhường tiếp. Thread nanosleep ở BLOCKED, scheduler bỏ qua nó cho tới giờ hẹn.

Hàm của một kernel thread chạy tới dấu } cuối. Chuyện gì xảy ra tiếp theo, và ai trả stack của nó?

Lệnh ret lấy địa chỉ taskKernelReturn mà stackGenerateKernel đã đặt ở đỉnh stack, nên vào taskKill: task được giao cho reaper, đặt DEAD, rồi lặp chờ tick. Thread helper (helperReaper) trả stack và gỡ task khỏi danh sách, vì task không thể tự trả stack nó đang đứng.

Câu hỏi mở (đã trả lời)

  • Lưu/khôi phục register ở đâu (trên stack hay TCB)? Cả hai, theo thứ tự: ngắt đẩy lên stack của task (CPU + stub + isr_common), schedule() chép vào TCB (Task.registers, memcpy 184 byte), khi chạy lại thì chép từ TCB xuống đỉnh TSS stack của task và iretq. Không có hàm switch_to kiểu Linux (chỉ cất callee-saved rồi đổi RSP); cavOS cất toàn bộ khung ngắt.
  • Đồng bộ giữa core (spinlock)? cavOS chỉ chạy một core: entry/bootloader.c đọc phản hồi SMP của Limine (số CPU, CPU nào là BSP) nhưng không đánh thức CPU phụ (không ghi goto_address, không gửi INIT-SIPI). Spinlock (utilities/spinlock.c) vẫn cần vì preemption, và khi bận thì nhường CPU thay vì quay. Có thêm SpinlockCnt (đếm người đọc, -1 = có người ghi) cho danh sách liên kết như TASK_LL_MODIFY.
  • Scheduler round-robin? Đúng, round-robin trên danh sách liên kết, không có độ ưu tiên, lát thời gian 1 tick = 1 ms.
  • Bring-up các AP core (SMP): cavOS không làm (xem trên). Phần lý thuyết INIT-SIPI-SIPI để ở Ánh xạ spec.
  • Hàm initiateTasking() của dàn ý cũ không tồn tại; tên thật là initiateTasks(), cộng initiateKernelThreads() ngay sau nó.

Bỏ qua lệnh gây page fault bằng rip++ (cpu/isr.c)

Handler bỏ qua lệnh đọc địa chỉ ma thuật bằng cpu->rip++, tức giả định lệnh đọc dài 1 byte. Nhưng lệnh đọc là do compiler chọn từ dòng C, và nó không dài 1 byte. Disassembly của handControl trong target/boot/kernel.bin (cavOS build trên máy này, objdump -d):

text
ffffffff8003b534:  48 b8 00 f0 ff ff ff 5f 00 00   movabs $0x5ffffffff000,%rax
ffffffff8003b53e:  0f b6 00                         movzbl (%rax),%eax     <- fault ở đây (3 byte)
ffffffff8003b541:  88 45 ff                         mov    %al,-0x1(%rbp)
ffffffff8003b544:  0f b6 45 ff                      movzbl -0x1(%rbp),%eax

RIP + 1 rơi vào giữa lệnh, ở byte b6 00. Giải mã từ đó (objdump -D -b binary trên đúng các byte này):

text
   0:  b6 00       mov    $0x0,%dh
   2:  88 45 ff    mov    %al,-0x1(%rbp)

Tình cờ b6 00 là một lệnh hợp lệ 2 byte (mov $0, %dh), và sau nó CPU lại khớp nhịp với lệnh kế tiếp. Giá phải trả là ghi đè byte thứ hai của RDX, vô hại vì handControl không dùng RDX và RDX không phải thanh ghi callee-saved. Nó chạy được chỉ vì GCC ở -O0 (Makefile của cavOS không có cờ -O) sinh đúng movzbl (%rax),%eax. Đổi cờ tối ưu hay compiler là có thể ra lệnh khác, ví dụ movb (%rax),%al = 8a 00: RIP + 1 rơi vào byte 00, mở đầu một lệnh add lấy byte sau làm toán hạng. Cách chắc chắn: viết lệnh đọc bằng asm với độ dài biết trước, như Lab 0x07 (8a 00, rip += 2), hoặc dùng một vector int riêng. (Kết luận từ disassembly; chưa thử build cavOS với cờ khác.)

Khe "mất lần đánh thức" trong kbTaskRead (drivers/kb.c)

readHandler chạy trong syscall với ngắt bật: syscallHandler gọi sti ngay đầu ("do other task stuff while we're here!", syscalls/syscalls.c). Trong kbTaskRead, cavOS giao bộ đệm cho IRQ trước rồi mới đặt state:

c
  kbBuff = buff;         // từ đây kbIrq đã ghi vào bộ đệm và có thể kbFinaliseStream()
  kbCurr = 0;
  kbMax = limit;
  kbTaskId = taskId;

  if (changeTaskState)
    task->state = TASK_STATE_WAITING_INPUT;

Nếu IRQ1 tới giữa kbTaskId = taskId và dòng đổi state, và phím đó kết thúc lần đọc (Enter ở chế độ ICANON, hoặc bất kỳ phím nào khi tắt ICANON), thì kbFinaliseStream đặt READY rồi kbReset() (kbBuff = 0). Ngay sau đó kbTaskRead đặt WAITING_INPUT. Task chờ mãi: lần đánh thức đã đi qua, và vì kbBuff = 0 nên mọi phím sau bị kbIrq bỏ (if (!kbBuff || !out || !tasksInitiated) return;). WAITING_INPUT cũng không nằm trong signalsRevivableState, nên signal không cứu được. Khe chỉ vài lệnh nên rất hiếm. Sửa: đặt state trước khi giao kbBuff, hoặc làm cả đoạn trong cli. Lab 0x07 tái hiện đúng kiểu race này bằng một khe kéo dài 300 ms: phím h nằm trong ring 1187 ms cho tới khi phím kế tiếp đánh thức thread. (Trên cavOS: kết luận từ đọc code, chưa tái hiện.)

IRQ bàn phím lấy khoá danh sách task (drivers/kb.c)

kbIrq gọi taskGet(kbTaskId), và taskGet lấy khoá đọc TASK_LL_MODIFY (spinlockCntReadAcquire). Nếu đúng lúc đó một task đang giữ khoá ghi, ví dụ taskListAllocate giữ nó trong lúc malloc + memset với ngắt còn bật, thì spinlockCntReadAcquire gọi handControl() để chờ, mà handControl assert(checkInterrupts()) trong IRQ (IF = 0) → _assert → panic(). Cùng chuỗi đó với kbFinaliseStream (cũng gọi taskGet). Muốn trúng thì phải gõ phím đúng lúc một task được tạo (fork, thread lwIP). (Kết luận từ đọc code, chưa tái hiện.)

Vòng giải phóng dsSysIntr trong helperReaper (entry/kernel_helper.c)

c
    TaskSysInterrupted *intrBrowse =
        (TaskSysInterrupted *)reaperTask->dsSysIntr.firstObject;
    while (intrBrowse) {
      TaskSysInterrupted *next = (TaskSysInterrupted *)intrBrowse->_ll.next;
      free(next); // quick n dirty
      intrBrowse = next;
    }

Vòng lặp free(next) rồi gán intrBrowse = next, nên lượt sau đọc intrBrowse->_ll.next từ vùng vừa free (use-after-free), và phần tử đầu tiên không bao giờ được free. Đúng phải là free(intrBrowse). Chỉ chạy tới khi task chết lúc còn syscall bị ngắt ghi trong danh sách đó. (Kết luận từ đọc code.)

Task dummy gần như không bao giờ chạy

kernelHelpEntry lặp handControl() mãi và không bao giờ đổi state, nên thread helper luôn READY. Vòng tìm của schedule() vì vậy luôn tìm được ít nhất một task, và nhánh next = dummyTask không bao giờ tới (trừ khi chính helper bị chặn). Thời gian CPU rảnh được tiêu vào vòng "helper chạy, page fault, schedule(), quay về helper"; CPU không bao giờ hlt, và dummy cũng chỉ pause. Lab 0x07 bản HELPER_SPIN làm y như vậy và đo được: dummy 0 tick, helper 2141 tick trong 2291 ms.
