Bài 7 - GDT & TSS

Status doneTags step, cpu

Mục đích

Khai báo cho CPU biết đâu là code kernel (ring 0), đâu là code user (ring 3), và lấy stack nào khi đổi ring.

Bài này dựng GDT (bảng các segment code/data kernel và user) và TSS (chỗ CPU lấy stack kernel RSP0 khi đang chạy user mà bị ngắt). Long mode gần như bỏ segmentation, nhưng CPU vẫn đòi selector hợp lệ và đọc mức đặc quyền từ đó. Bài 9 cần selector kernel code cho mỗi cổng ngắt (Bài 9 - IDT & Interrupts), Bài 16 cần thứ tự segment user cho sysret (Bài 16 - Fast Syscalls).

Nói thật đơn giản

GDT là một danh sách thẻ ra vào. Mỗi thẻ ghi "đây là thẻ code hay thẻ data, và người cầm thẻ là kernel hay user". Ngày xưa thẻ còn ghi "được vào phòng nào, rộng bao nhiêu" (base/limit); ở 64-bit phần đó bị bỏ qua, mọi thẻ đều mở cả toà nhà. Chỉ còn cấp bậc là quan trọng.

TSS ở 64-bit chỉ còn giữ địa chỉ phòng trực của kernel (RSP0). Khi chương trình user bị ngắt, CPU nhảy vào kernel và cần ngay một stack sạch của kernel; nó lấy địa chỉ stack đó trong TSS.

Cần biết trước

Bốn khái niệm về segment trên x86, mỗi cái vài câu.

  • Segment register trong long mode. CPU có các thanh ghi đoạn CS (code), SS (stack), DS/ES/FS/GS (data). Ở 64-bit, CPU coi base = 0 và bỏ kiểm limit cho CS/DS/ES/SS (base của FS/GS lấy từ MSR). Nhưng CS vẫn quyết định đang chạy ring mấy và đang chạy code 64-bit hay không. Đọc sâu: x86 Segmentation, Long Mode.
  • GDT, descriptor và GDTR. GDT là mảng trong RAM, mỗi phần tử (descriptor) 8 byte mô tả một segment. Descriptor hệ thống như TSS dài 16 byte vì phải chứa địa chỉ 64-bit. Thanh ghi GDTR giữ địa chỉ và kích thước bảng, nạp bằng lệnh lgdt. Đọc sâu: GDT §2, §3, từng bit ở §4, TSS ở §7.
  • Selector. Giá trị nạp vào thanh ghi đoạn là một selector 16 bit: bit 15–3 là chỉ số descriptor, bit 2 (TI) chọn GDT (0) hay LDT (1), bit 1–0 là RPL. Vì descriptor dài 8 byte, selector với RPL = 0 chính là offset byte trong GDT: 0x28 = descriptor số 5. Đọc sâu: GDT §8.
  • Ring: CPL, DPL, RPL. CPL là ring đang chạy (2 bit thấp của CS), DPL là ring ghi trong descriptor, RPL là ring ghi trong selector. Kernel chạy ring 0, user ring 3; CPU so các số này để chặn user dùng segment của kernel. Đọc sâu: GDT §9.

Đọc code cavOS

Một hàm initiateGDT(): điền bảng, nạp bảng, đổi CS, rồi nạp TSS.

File: cpu/gdt.c, include/gdt.h. Trong entry/kernel.c:_start(), initiateGDT() chạy ở dòng 59, sau initiateVMM() (Bài 6) và trước initiateACPI()/initiateISR(). Spec: Intel SDM Vol.3.

1. Cấu trúc bảng (gdt.h)

c
typedef struct GDTEntry {      // 8 byte
  uint16_t limit; uint16_t base_low; uint8_t base_mid;
  uint8_t  access; uint8_t granularity; uint8_t base_high;
} __attribute__((packed)) GDTEntry;

typedef struct GDTEntries {
  GDTEntry descriptors[11];   // segment code/data: kernel + user, 16/32/64-bit
  TSSEntry tss;               // descriptor TSS, 16 byte vì chứa địa chỉ 64-bit
} __attribute__((packed)) GDTEntries;

typedef struct GDTPtr { uint16_t limit; uint64_t base; } __attribute__((packed)) GDTPtr; // nạp vào GDTR

Bảng dài 11 × 8 + 16 = 104 byte. Trong granularity, nửa byte cao là cờ (G, D/B, L); nửa thấp là bit 16–19 của limit. Ở long mode chỉ access và cờ L còn ý nghĩa với segment code.

2. Điền các descriptor (initiateGDT)

cavOS khai cả segment 16/32-bit (di sản) lẫn 64-bit (thật sự dùng). Offset = chỉ số × 8:

16kernel data 16100100100di sản
24kernel code 321001101011001111di sản (G=1 trang 4 KiB, D/B=1 32-bit)
32kernel data 321001001011001111di sản

Giải mã byte access (bit 7 → 0):

bittênnghĩa
7Ppresent, phải = 1
6–5DPL00 = ring 0, 11 = ring 3
4S1 = segment code/data, 0 = segment hệ thống (TSS, LDT)
3E1 = code, 0 = data
1RWcode: được đọc; data: được ghi
0Aaccessed, CPU tự bật lên 1 khi nạp segment

Vậy 10011010 = present, ring 0, code, đọc được (kernel code); 11111010 = như trên nhưng DPL = 3 (user code); 11110010 = present, ring 3, data, ghi được (user data). Code 64-bit đặt granularity = 0b00100000, tức cờ L = 1: segment này chạy lệnh 64-bit. Data không cần cờ L.

Thứ tự lạ: user data ở 72, user code ở 80. Đây là bắt buộc của sysret: lệnh này lấy SS = STAR[63:48] + 8 và CS = STAR[63:48] + 16 (Intel SDM, lệnh SYSRET). cpu/fastSyscall.c ghi STAR[63:48] = GDT_USER_CODE - 16 = 64, nên SS = 72, CS = 80 (Bài 16). Comment trong gdt.c ghi ngược ("User code 64. (72)" trên descriptors[10]), nhưng chỉ số 10 là offset 80; tin chỉ số, đừng tin comment.

3. Nạp bảng và đổi CS (gdt_reload)

initiateGDT() đặt gdtr.limit = sizeof(GDTEntries) - 1 (= 0x67) và gdtr.base = &gdt, rồi gọi:

asm
lgdt gdtr                 ; nạp địa chỉ + giới hạn GDT vào GDTR
push $0x28                ; 0x28 = 40 = kernel code 64 (CS mới)
lea 1f(%rip), %rax
push %rax                 ; địa chỉ quay về = nhãn 1
lretq                     ; far return: pop RIP rồi pop CS -> CS = 0x28
1: mov $0x30, %eax        ; 0x30 = 48 = kernel data 64
   mov %eax, %ds / %es / %fs / %gs / %ss
  • lgdt chỉ đổi GDTR. Thanh ghi đoạn giữ bản sao descriptor cũ (phần ẩn) cho tới khi được nạp lại, nên phải nạp lại từng cái.
  • Không có lệnh mov vào CS. Cách phổ biến ở 64-bit là đẩy CS mới và địa chỉ đích lên stack rồi lretq (far return). Đọc sâu: GDT §11.
  • DS/ES/FS/GS/SS nạp 0x30. Ở long mode base/limit của chúng bị bỏ qua, nhưng selector vẫn phải trỏ descriptor hợp lệ.

4. TSS: chỉ để giữ RSP0 (gdt_load_tss)

TSS 64-bit không còn lưu thanh ghi của task. Nó chỉ chứa các con trỏ stack:

c
typedef struct TSSPtr {
  uint32_t unused0;
  uint64_t rsp0, rsp1, rsp2;      // stack dùng khi vào ring 0/1/2; cavOS chỉ cần rsp0
  uint64_t unused1;
  uint64_t ist1, ..., ist7;       // IST: 7 stack riêng, cổng ngắt nào chọn thì dùng
  uint64_t unused2;
  uint32_t iopb;
} __attribute__((packed)) TSSPtr; // 104 byte
  • Cuối initiateGDT(): memset(&tss, 0, ...) rồi gdt_load_tss(&tss). Hàm này điền địa chỉ tss vào descriptor ở offset 88 (base_low/mid/high/upper32), đặt flags1 = 0b10001001 (P = 1, DPL = 0, type = 1001 = "available 64-bit TSS"), rồi ltr 0x58 (nạp Task Register).
  • Lúc này rsp0 = 0: chưa có task user nên chưa cần. Từ Bài 12, mỗi lần đổi task scheduler ghi tssPtr->rsp0 = next->whileTssRsp (multitasking/schedule.c), tức stack kernel của task sắp chạy (Bài 12 - Multitasking & Scheduler).
  • cavOS không dùng IST: cpu/idt.c:set_idt_gate() ghi idt[n].ist = 0 cho mọi cổng.

5. Ai dùng các selector này về sau

  • cpu/idt.c: mỗi cổng ngắt có kernel_cs = GDT_KERNEL_CODE (Bài 9).
  • multitasking/task.c: task user có cs = GDT_USER_CODE | DPL_USER (= 0x53), ds/ss = GDT_USER_DATA | DPL_USER (= 0x4b), với DPL_USER = 3 (Bài 12).
  • cpu/fastSyscall.c: thanh ghi MSR STAR lấy GDT_KERNEL_CODE và GDT_USER_CODE - 16 (Bài 16).

Đối chiếu với code:

  • GDT= ... 00000067: limit 0x67 = 103 = sizeof(GDTEntries) - 1. Base nằm trong ảnh kernel (0xffffffff8...) vì gdt là biến static.
  • CS =0028: selector 0x28 = chỉ số 5, RPL 0. Thuộc tính 00209b00 có 0x20 = cờ L (CS64) và 9b = access 10011010 với bit A đã được CPU bật.
  • Các word ở offset 0x28, 0x30, 0x48, 0x50 là ...9b..., ...93..., ...f3..., ...fb...: đúng access trong bảng mục 2 cộng bit A. User code/data cũng có bit A, vì lúc chụp các chương trình user đã chạy.
  • TR =0058, base ffffffff800bd880, limit 0x68: khớp descriptor 16 byte ở offset 0x58 (0x80008b0bd8800068 + 0x00000000ffffffff → limit 0x0068, base 0xffffffff_80_0b_d880). Type đã thành b (busy) dù code ghi 1001 (available): ltr tự bật bit busy.
  • FS =0000, GS =0000 dù gdt_reload nạp 0x30. Đường vào ngắt cpu/isr.asm (dòng 129–134) chỉ nạp lại 0x30 cho DS/ES/SS; hai dòng nạp FS/GS bị comment, nên chúng giữ giá trị từ lúc chạy ring 3.
  • Word cuối 0xffff800bd8000067 không thuộc GDT: đó là biến gdtr (limit 0x0067 + base) nằm ngay sau bảng.

Thử tự giải mã: lấy word 0x0020fb0000000000 ở offset 0x50, tách byte access và nửa byte cờ, rồi nói nó là segment gì, ring mấy.

Tự kiểm tra

Năm câu kiểm tra hiểu, không phải nhớ.

Long mode bỏ base/limit. Vậy sao kernel vẫn phải dựng GDT?

CPU vẫn đọc từ descriptor của CS ring đang chạy (DPL) và cờ L (chạy code 64-bit hay 32-bit). CS/SS phải trỏ descriptor hợp lệ, và iretq/sysret/cổng ngắt đều nạp selector từ GDT.

Vì sao gdt_reload phải dùng lretq thay vì mov $0x28, %cs?

x86 không có lệnh mov vào CS; CS chỉ đổi qua lệnh nhảy/gọi/trả về xa, ngắt hoặc sysret. lretq pop RIP rồi pop CS từ stack, nên đẩy sẵn 0x28 và địa chỉ nhãn là đổi được CS mà vẫn chạy tiếp ngay dòng sau.

Selector 0x53 trỏ tới descriptor nào, ring mấy?

0x53 = 0101 0011: chỉ số = 0x53 >> 3 = 10 (offset 80), TI = 0 (GDT), RPL = 3. Đó là user code 64, CS của chương trình ring 3.

Nếu đổi chỗ, để user code ở 72 và user data ở 80, cái gì hỏng?

sysret luôn lấy CS = STAR[63:48] + 16 và SS = STAR[63:48] + 8. Không chọn được giá trị STAR nào để CS rơi vào 72 còn SS rơi vào 80, nên sau syscall CPU sẽ nạp sai loại segment cho CS/SS và chương trình user sẽ lỗi.

Điều gì xảy ra nếu một task user bị ngắt khi tss.rsp0 vẫn là 0?

Khi đổi từ ring 3 sang ring 0, CPU nạp RSP = rsp0 rồi đẩy khung ngắt vào ngay dưới địa chỉ 0, một vùng không được map. Việc đẩy đó gây page fault ngay lúc đang vào ngắt, thường dẫn tới double fault rồi máy reset. Vì vậy scheduler phải ghi rsp0 trước khi chạy task user.

Câu hỏi mở (đã trả lời)

  • Long mode bỏ base/limit nhưng vẫn cần descriptor, vì sao? CPU vẫn cần biết CPL (ring 0/3), loại segment (code/data) và cờ L. Selector CS/SS phải trỏ descriptor hợp lệ; iretq/sysret cần các segment user/kernel ở đúng offset.
  • IST dùng cho fault nào? Cho fault mà stack hiện tại có thể hỏng: double fault, NMI, machine check. IST cho CPU một stack đã biết là tốt. Trong cavOS hiện tại thì chưa dùng: mọi cổng IDT có ist = 0 (cpu/idt.c), nên một double fault do stack hỏng sẽ không có stack dự phòng (Bài 9).

Chi tiết lặt vặt trong source

  • gdt.h có #define GDT_TSS 80, nhưng selector TSS thật là 0x58 = 88 (hằng viết thẳng trong ltr). Grep toàn kernel không thấy chỗ nào dùng GDT_TSS, nên lỗi này không gây hại.
  • NUM_GDT_ENTRIES 7 trong gdt.h là số cũ, bảng thật có 11 descriptor + TSS. Struct GDTPointer (base 32-bit) cũng không được dùng; GDTR nạp từ GDTPtr (base 64-bit).
  • gdt.tss.length = 104 là trường limit, còn TSSPtr dài đúng 104 byte, nên limit chuẩn là 103. Dư 1 byte không gây hại (Intel chỉ yêu cầu limit TSS 64-bit tối thiểu 0x67). QEMU in TR ... 00000068 khớp giá trị này.
  • Selector của user có RPL 3 (| DPL_USER), của kernel RPL 0. Vì vậy schedule.c kiểm "đang ở kernel" bằng registers.cs & GDT_KERNEL_CODE: 0x28 & 0x28 ≠ 0, còn 0x53 & 0x28 = 0.

Liên hệ

  • Nền tảng spec chuyên sâu về GDT (descriptor từng bit, selector, CPL/DPL/RPL, 32 vs 64-bit): GDT.
  • IDT/interrupt dùng selector kernel code + RSP0 (và IST nếu có): Bài 9 - IDT & Interrupts.
  • syscall/sysret dùng segment user/kernel: Bài 16 - Fast Syscalls.
  • RSP0 cập nhật mỗi lần đổi task: Bài 12 - Multitasking & Scheduler.
  • Các chế độ 16/32/64-bit mà các descriptor di sản ứng với, và cờ L trong long mode: Long Mode.

Ánh xạ spec

  • Intel SDM Vol.3 §3 (segmentation, descriptor), §7 (TSS, LTR, bit busy), §5 (privilege CPL/DPL/RPL), cờ L của code segment IA-32e.
  • Intel SDM Vol.2, lệnh SYSRET: CS = STAR[63:48] + 16, SS = STAR[63:48] + 8, RPL ép về 3.
