Thực hành: Lab 0x02 - Framebuffer

Mục đích

Sau bài này, printf của kernel hiện chữ lên màn hình, không chỉ ra cổng serial.

Kernel lấy vùng nhớ màn hình mà Limine chuẩn bị sẵn, học cách tô một pixel, rồi xây dần lên: hình chữ nhật → chữ cái → console có con trỏ và cuộn dòng. Bài 5 (quản lý RAM) không cần màn hình, nhưng từ đây mọi thông báo printf của các bài sau đều có chỗ hiện.

Nói thật đơn giản

Màn hình giống một tờ giấy kẻ ô li, mỗi ô là một pixel. Tờ giấy này nằm trong bộ nhớ dưới dạng một mảng byte gọi là framebuffer. Ghi mấy byte màu vào đúng ô là điểm đó sáng lên. Limine đưa cho kernel địa chỉ của mảng này, dùng được ngay.

Từ "tô một ô" đi lên: tô nhiều ô thành hình chữ nhật; tô theo một khuôn chấm có sẵn (font) thành chữ cái; nhớ chỗ đang viết (con trỏ), biết xuống dòng và đẩy cả trang lên khi hết chỗ thì thành console. Chỉ có một bẫy: mỗi hàng ô trong bộ nhớ có thể dài hơn số ô nhìn thấy, nên phải nhảy hàng bằng đúng độ dài hàng (pitch).

Cần biết trước

Ba ý mới: MMIO, cách một pixel nằm trong bộ nhớ, và font bitmap.

  • HHDM và cơ chế request/response của Limine — đã gặp ở Bài 3 - Bootloader Parser. Bài này thêm một request nữa, limine_framebuffer_request, khai riêng trong drivers/vga.c. Đọc sâu: Limine Protocol, HHDM.
  • MMIO (memory-mapped I/O). Có những địa chỉ vật lý không dẫn tới RAM mà dẫn tới một thiết bị. Ghi vào đó là gửi dữ liệu cho thiết bị, không phải cất dữ liệu. Framebuffer là vùng nhớ của card màn hình nằm ở một địa chỉ như vậy (trên QEMU là 0xfd000000). Limine đã map nó vào HHDM, nên kernel ghi qua một địa chỉ ảo bình thường. Đọc sâu: HHDM - dùng VA nào.
  • Pixel format và pitch. Ở chế độ 32 bpp (bit per pixel), mỗi pixel chiếm 4 byte. Thứ tự byte ở đây là B, G, R, X (xanh dương, lục, đỏ, một byte bỏ trống). Các pixel trong một hàng nằm liền nhau; pitch là số byte từ đầu hàng này tới đầu hàng sau, có thể lớn hơn width × 4 nếu phần cứng đệm thêm byte cuối hàng. Đọc sâu: Danh mục tài liệu (Limine PROTOCOL.md, phần framebuffer).
  • Font bitmap. Mỗi chữ cái lưu sẵn thành một lưới chấm, mỗi hàng của lưới là một byte, mỗi bit là một chấm bật/tắt. cavOS dùng định dạng PSF1 (PC Screen Font, bản 1): chữ luôn rộng 8 chấm, chiều cao ghi trong header. Phần đọc code bên dưới đi vào chi tiết.

Đọc code cavOS

Ba lời gọi trong _start(), đọc theo đúng thứ tự chạy.

Trong entry/kernel.c:_start() (xem Bài 0 - Bắt đầu ở đây), ngay sau bootloader parser:

c
// Framebuffer doesn't depend on paging, limine prepares it anyways
initiateVGA();       // drivers/vga.c       — lấy framebuffer từ Limine
initiateConsole();   // graphical/console.c — nạp font, đặt con trỏ về (0,0)
clearScreen();       // graphical/console.c — tô nền, vẽ con trỏ

Comment của tác giả nói đúng ý: Limine đã bật paging và map framebuffer trước khi nhảy vào _start(), nên bước này chạy được trước cả PMM (Bài 5) và paging của kernel (Bài 6).

1. initiateVGA() — hỏi Limine màn hình ở đâu (drivers/vga.c)

c
static volatile struct limine_framebuffer_request limineFBreq = {
    .id = LIMINE_FRAMEBUFFER_REQUEST, .revision = 0};

void initiateVGA() {
  struct limine_framebuffer *framebufferRes =
      limineFBreq.response->framebuffers[0];
  fb.virt = (uint8_t *)framebufferRes->address;          // VA, đã nằm trong HHDM
  fb.phys = (size_t)fb.virt - bootloader.hhdmOffset;     // trừ offset → PA
  fb.height = framebufferRes->height;
  fb.width = framebufferRes->width;
  fb.pitch = framebufferRes->pitch;
  fb.bpp = framebufferRes->bpp;
  fb.red_shift = framebufferRes->red_mask_shift;         // ... green_*, blue_* tương tự
  ...
  debugf("[graphics] Resolution fixed: fb{%lx} dim(xy){%dx%d} bpp{%d}\n", ...);
}
  • Chỉ lấy màn hình đầu tiên (framebuffers[0]) rồi chép thông số vào biến toàn cục fb để cả kernel dùng.
  • address là địa chỉ ảo trong HHDM. Ghi fb.virt[i] là ghi thẳng vào VRAM.
  • fb.phys tính ngược bằng cách trừ hhdmOffset. Kernel không cần nó để vẽ; nó dành cho lúc userspace xin map framebuffer (xem Đọc thêm).

Dòng log thật khi boot cavOS (QEMU -m 4g -vga vmware, file lab/outputs/cavos-boot-2026-09-03.txt):

text
[graphics] Resolution fixed: fb{ffff8000fd000000} dim(xy){1024x768} bpp{32}

0xffff8000fd000000 − 0xffff800000000000 = 0xfd000000: đúng địa chỉ vật lý của framebuffer cộng HHDM offset.

2. Struct Framebuffer và macro drawPixel (include/fb.h)

c
typedef struct Framebuffer {
  uint8_t *virt;
  size_t   phys;
  size_t width, height, bpp, pitch;     // pitch = số BYTE mỗi hàng
  size_t red_shift, red_size;
  size_t green_shift, green_size;
  size_t blue_shift, blue_size;
} Framebuffer;

#define drawPixel(x, y, r, g, b)                         \
  do {                                                   \
    fb.virt[((x) + (y) * fb.width) * 4] = (b);           \
    fb.virt[((x) + (y) * fb.width) * 4 + 1] = (g);       \
    fb.virt[((x) + (y) * fb.width) * 4 + 2] = (r);       \
    fb.virt[((x) + (y) * fb.width) * 4 + 3] = 0;         \
  } while (0)

Một pixel = 4 byte theo thứ tự B, G, R, X. Đọc 4 byte đó như một số uint32_t little-endian thì được 0x00RRGGBB. Sơ đồ dưới cho thấy pixel (x, y) nằm ở đâu:

Bẫy pitch: drawPixel tính địa chỉ bằng (x + y*width)*4, tức coi như pitch == width*4. Trên QEMU điều đó đúng (Lab 0x02 đo được pitch 5120 = 1280×4), nên không thấy lỗi. Trên máy có byte đệm cuối hàng, mỗi hàng sẽ lệch thêm một đoạn và ảnh bị xô chéo. Cách tổng quát: nhảy hàng bằng y * pitch, nhảy cột bằng x * 4.

3. drawRect — tô hình chữ nhật (graphical/fb.c)

c
void drawRect(int x, int y, int w, int h, int r, int g, int b) {
  unsigned int offset = (x + y * fb.width) * 4;   // điểm bắt đầu: vẫn theo width
  for (int i = 0; i < h; i++) {
    for (int j = 0; j < w; j++) {                 // tô từng pixel trong hàng
      fb.virt[offset + j * 4] = b;
      fb.virt[offset + j * 4 + 1] = g;
      fb.virt[offset + j * 4 + 2] = r;
      fb.virt[offset + j * 4 + 3] = 0;
    }
    offset += fb.pitch;                           // sang hàng kế: theo pitch
  }
}

Hàm này nhảy hàng đúng bằng pitch, nhưng điểm bắt đầu vẫn tính theo width nên vẫn dính bẫy ở trên khi y > 0. Nó được dùng để xoá màn (clearScreen), vẽ và xoá con trỏ, và tô dòng trống khi cuộn.

4. Font PSF1 và psfPutC (utilities/psf.c)

c
// include/psf.h
#define PSF1_MAGIC 0x0436
typedef struct PSF1Header {
  uint16_t magic;
  uint8_t  mode;
  uint8_t  height; // width is always 8px
} PSF1Header;

initiateConsole() gọi psfLoadDefaults(), hàm này trỏ psf vào mảng u_vga16_psf nhúng sẵn trong include/gohufont.h. psfLoad() kiểm magic 0x0436 và kiểm cờ mode có PSF1_MODE512 hoặc PSF1_MODEHASTAB. Bốn byte đầu của mảng là 0x36, 0x04, 0x03, 0x0e: magic 0x0436 (little-endian), mode 0x03, height 0x0e = 14. Log boot khớp:

text
[console] Initiated with font: dim(xy){8x14}

Vẽ một ký tự:

c
void psfPutC(char c, uint32_t x, uint32_t y, uint32_t r, uint32_t g, uint32_t b) {
  uint8_t *targ =
      (uint8_t *)((size_t)psf + sizeof(PSF1Header) + c * psf->height);
  for (int i = 0; i < psf->height; i++) {     // mỗi hàng của chữ = 1 byte
    for (int j = 0; j < 8; j++) {              // 8 bit = 8 cột
      if (targ[i] & (1 << (8 - j))) // NOT little endian
        drawPixel(x + j, y + i, r, g, b);      // bit bật → màu chữ
      else
        drawPixel(x + j, y + i, bg_color[0], bg_color[1], bg_color[2]); // bit tắt → màu nền
    }
  }
}
  • Glyph của ký tự c nằm ngay sau header, ở vị trí c * height: mỗi chữ chiếm height byte liên tiếp.
  • Byte thứ i là hàng chấm thứ i. Bit cao là cột bên trái, nên code đọc bit từ cao xuống thấp.
  • Ô chữ tô cả nền, nên viết đè lên chữ cũ không cần xoá trước.

5. Console — con trỏ, xuống dòng, cuộn (graphical/console.c)

Hai biến toàn cục width và height trong console.c là vị trí con trỏ tính bằng pixel (không phải số ô chữ). CHAR_WIDTH = 8, CHAR_HEIGHT = psf->height. Màu chữ mặc định trắng, nền đen (textcolor, bg_color).

drawCharacter(c) làm theo thứ tự:

  1. Đưa ký tự qua ansiHandle() (graphical/ansi.c): nếu là một phần của chuỗi escape ANSI (bắt đầu bằng 0x1B, ví dụ đổi màu) thì xử lý ở đó và dừng.
  2. Tràn lề phải (width > fb.width - CHAR_WIDTH) thì về đầu dòng, height += CHAR_HEIGHT.
  3. Gọi scrollConsole(true): nếu con trỏ đã chạm đáy thì cuộn.
  4. Xử lý ký tự theo bảng dưới, rồi updateBull() vẽ lại con trỏ.
Ký tựViệc làm
\nxoá con trỏ, width = 0, height += CHAR_HEIGHT
\r (0xd)xoá con trỏ, width = 0 (về đầu dòng)
\blùi một ô và tô nền ô đó
\tgọi lại drawCharacter(' ') 4 lần
còn lạipsfPutC(c, width, height, ...) rồi width += CHAR_WIDTH

Cuộn màn hình:

c
bool scrollConsole(bool check) {
  if (check && !(height >= (fb.height - CHAR_HEIGHT)))
    return false;                                   // chưa chạm đáy
  for (int y = CHAR_HEIGHT; y < fb.height; y++) {   // chép từng hàng pixel lên trên CHAR_HEIGHT hàng
    void *dest = (void *)(((size_t)fb.virt) + (y - CHAR_HEIGHT) * fb.pitch);
    const void *src = (void *)(((size_t)fb.virt) + y * fb.pitch);
    memcpy(dest, src, fb.width * 4);
  }
  drawRect(0, fb.height - CHAR_HEIGHT, fb.width, CHAR_HEIGHT, bg...); // xoá dòng cuối
  height -= CHAR_HEIGHT;
  return true;
}

Vòng chép dùng pitch cho cả nguồn lẫn đích, nên phần này đúng kể cả khi có byte đệm. Con trỏ là một khối đặc cỡ một ô chữ: updateBull() vẽ bằng màu chữ, eraseBull() tô lại bằng màu nền.

6. Từ printf tới màn hình

c
void printfch(char character) {
  spinlockAcquire(&LOCK_CONSOLE);   // một luồng vẽ tại một thời điểm
  drawCharacter(character);
  spinlockRelease(&LOCK_CONSOLE);
}

// printf.c uses this
void putchar_(char c) { printfch(c); }

drivers/printf.c là một thư viện printf nhỏ; nó cần người dùng tự viết hàm putchar_ để xuất từng ký tự. cavOS viết hàm đó trong console.c, nên mọi printf đi tới màn hình. Còn debugf (Bài 2) vẫn đi ra serial. Khoá LOCK_CONSOLE để khi có nhiều CPU (sau này) hai luồng không vẽ chen nhau.

Tự kiểm tra

Bấm vào câu hỏi để xem đáp án.

Vì sao initiateVGA() chạy được trước cả PMM và paging của kernel?

Vì Limine đã bật paging và map framebuffer vào HHDM trước khi nhảy vào _start(). Kernel chỉ cần đọc địa chỉ trong response và ghi vào đó, không phải cấp phát hay map gì thêm.

Nếu pitch = width*4 + 64, pixel (0, 10) mà drawPixel ghi sẽ lệch bao nhiêu byte so với chỗ đúng?

Chỗ đúng là 10 * pitch, còn drawPixel ghi ở 10 * width * 4: thấp hơn 10 * 64 = 640 byte (160 pixel). Hàng càng thấp càng lệch nhiều, nên ảnh bị xô chéo.

Đổi chỗ hai dòng ghi (b) và (r) trong drawPixel thì màu thay đổi thế nào?

Đỏ thành xanh dương và ngược lại; xanh lục, trắng, đen giữ nguyên. Đây là cách nhanh để chứng minh thứ tự byte là BGRX.

Với font 8×14 trên màn 1024×768, console chứa được bao nhiêu cột và bao nhiêu dòng chữ?

1024 / 8 = 128 cột. Dòng thứ k bắt đầu ở height = 14k; scrollConsole cuộn khi height >= 768 - 14 = 754, tức khi k = 54. Vậy có 54 dòng (k = 0..53).

Trong psfPutC, khi j = 0 code kiểm targ[i] & (1 << 8). Kết quả là gì và ảnh hưởng ra sao?

targ[i] chỉ có 8 bit (bit 0 tới 7) nên phép AND với bit 8 luôn bằng 0: cột đầu của mỗi ô chữ luôn là màu nền. Cột j hiện bit 8 - j, nên chữ dịch phải 1 pixel và bit 0 không bao giờ được vẽ.

Đọc thêm

Những thứ có ích nhưng không cần để đi tiếp sang Bài 5.

Framebuffer cho userspace (fb0 trong graphical/fb.c)

Sau này chương trình người dùng (ví dụ Xorg) muốn tự vẽ. fb.c export VfsHandlers fb0 để userspace gọi ioctl/mmap trên framebuffer, theo kiểu /dev/fb0 của Linux:

  • FBIOGET_VSCREENINFO / FBIOGET_FSCREENINFO: trả độ phân giải, bitfield màu, và smem_start = fb.phys.
  • fbUserMmap: map fb.phys vào địa chỉ ảo userspace 0x150000000000 với cờ PF_RW | PF_USER | PF_CACHE_WC (write-combining: gom nhiều lần ghi nhỏ thành ghi lớn, hợp với VRAM).

Đây là lý do initiateVGA() lưu cả fb.phys. Liên quan: Bài 6 - Virtual Memory & Paging (VirtualMap), Bài 18 - Userspace & ELF Loader.

Các trường *_shift/*_size không được drawPixel dùng

Limine báo vị trí và độ rộng bit của từng kênh màu (red_mask_shift, red_mask_size, ...). initiateVGA() chép chúng vào fb, nhưng drawPixel và drawRect không đọc: chúng giả định cứng thứ tự B, G, R, X. Trên QEMU thì đúng; một framebuffer có thứ tự kênh khác sẽ ra sai màu.

Câu hỏi mở cũ (đã trả lời)

  • Framebuffer ở địa chỉ ảo nào? Địa chỉ HHDM (framebufferRes->address); fb.phys = virt − hhdmOffset.
  • Định dạng pixel? 32 bpp BGRX (0x00RRGGBB), kèm red/green/blue_shift + size từ Limine.
  • Cuộn màn hình thế nào? scrollConsole: memcpy dịch ảnh lên một dòng chữ, xoá dòng đáy.

Ánh xạ spec

  • Limine framebuffer response (address, pitch, bpp, *_mask_shift/size): Danh mục tài liệu.
  • PSF1 font format (magic 0x0436, header 4 byte, glyph 8×height): PSF spec.
  • Pixel BGRX/GOP: UEFI GOP PixelBlueGreenRedReserved8BitPerColor.
