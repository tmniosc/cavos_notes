Bài 1 - Boot & Limine

Status doneTags step, boot

Mục đích

Từ lúc bật nguồn tới dòng C đầu tiên của kernel.

Bài này đưa CPU từ lúc bật máy tới hàm _start() của cavOS, và cho thấy file kernel được xếp vào bộ nhớ ra sao. Bài 2 cần điểm xuất phát này: việc đầu tiên _start() làm là bật cổng serial. (Cách cài môi trường và bản đồ cả khoá học: Bắt đầu.)

Nói thật đơn giản

Bật máy lên, CPU chưa biết kernel của bạn là gì. Phải có người đọc file kernel từ đĩa, đưa CPU vào chế độ 64-bit, bật bộ nhớ ảo, rồi nhảy vào hàm đầu tiên của kernel. Việc này dài và toàn assembly. cavOS thuê sẵn Limine (một bootloader có sẵn) làm hết, rồi "giao chìa khoá" ở hàm _start.

Giống chuyển nhà có dịch vụ trọn gói: bạn đưa bản thiết kế (link.ld nói đồ nào đặt phòng nào, phòng nào khoá), đội chuyển nhà (Limine) bày đồ đúng chỗ theo bản thiết kế. Bạn còn dán sẵn vài phiếu hỏi trong thùng đồ ("nhà có mấy phòng?"); đội chuyển nhà điền câu trả lời vào, Bài 3 sẽ đọc chúng.

Cần biết trước

Bốn ý đủ để đọc tiếp; mỗi ý có trang riêng nếu muốn đào sâu.

  • ELF — định dạng file chương trình chuẩn trên Linux/Unix; kernel cavOS (kernel.bin) là một file ELF64. Trong file có ELF header (điểm vào ở đâu), program headers (các segment: khối cần nạp vào RAM, kèm quyền đọc/ghi/chạy) và section headers (các section như .text, .data: chỉ linker và debugger cần). Đọc sâu: PE, ELF và quy ước gọi hàm.
  • Long Mode — chế độ 64-bit của CPU x86. Muốn vào phải bật paging trước, nên không thể "vào 64-bit" mà chưa có bảng trang. Limine làm sẵn cả hai. Đọc sâu: Long Mode.
  • Higher-half kernel — kernel chạy ở địa chỉ ảo rất cao (0xffffffff80000000, 2 GiB cuối của không gian 64-bit), để nửa thấp dành cho chương trình người dùng. Đọc sâu: Higher-Half Kernel.
  • Limine protocol — "hợp đồng" giữa Limine và kernel. Kernel đặt trong file những struct request có số nhận dạng (magic); Limine tìm thấy thì điền con trỏ response. Đọc sâu: Boot Protocol & Limine, Request-Response Mechanism.

Chuỗi boot: từ nút nguồn tới _start

Bản thiết kế: link.ld

link.ld là linker script: file chỉ cho linker ld biết xếp các phần của kernel vào địa chỉ nào và gom chúng thành segment ra sao. Trích từ src/kernel/link.ld:

ld
OUTPUT_FORMAT(elf64-x86-64)
OUTPUT_ARCH(i386:x86-64)
ENTRY(_start)

PHDRS
{
    text    PT_LOAD    FLAGS((1 << 0) | (1 << 2)) ; /* Execute + Read */
    rodata  PT_LOAD    FLAGS((1 << 2)) ;            /* Read only */
    data    PT_LOAD    FLAGS((1 << 1) | (1 << 2)) ; /* Write + Read */
    dynamic PT_DYNAMIC FLAGS((1 << 1) | (1 << 2)) ; /* Dynamic PHDR for relocations */
}

SECTIONS
{
    . = 0xffffffff80000000;
    kernel_start = .;
    kernel_text_start = .;
    .text : { *(.text .text.*) } :text
    kernel_text_end = .;

    . += CONSTANT(MAXPAGESIZE);          /* nhảy sang trang mới cho .rodata */
    kernel_rodata_start = .;
    .rodata : { *(.rodata .rodata.*) } :rodata
    kernel_rodata_end = .;

    . += CONSTANT(MAXPAGESIZE);          /* nhảy sang trang mới cho .data */
    kernel_data_start = .;
    .data : { *(.data .data.*) } :data
    .dynamic : { *(.dynamic) } :data :dynamic
    .bss : { *(.bss .bss.*) *(COMMON) } :data
    kernel_data_end = .;
    ...
}
  • ENTRY(_start) ghi địa chỉ hàm _start vào ELF header (trường e_entry). Limine nhảy tới đó.
  • . = 0xffffffff80000000 đặt kernel ở nửa cao, đúng chỗ Limine protocol yêu cầu.
  • . += CONSTANT(MAXPAGESIZE) đẩy con trỏ địa chỉ thêm một trang (cavOS link với -z max-page-size=0x1000, tức 4 KiB). Nhờ vậy .text, .rodata, .data không bao giờ dùng chung một trang. Lý do: quyền đọc/ghi/chạy được gán theo trang (xem Paging ý #3, W^X).
  • Các nhãn kernel_text_start, kernel_rodata_end... là symbol trống chỉ đánh dấu địa chỉ. include/bootloader.h khai chúng là extern; memory/paging.c dùng chúng ở Bài 6 để map lại kernel đúng quyền.
  • .bss (biến chưa khởi tạo) đứng cuối segment data: chỉ chiếm chỗ trong RAM, không chiếm chỗ trong file.

PHDRS: tên chỉ là nhãn, quyền nằm ở FLAGS

text, rodata, data trong khối PHDRS là tên tự đặt; đổi thành foo, bar, baz vẫn chạy y hệt. Thứ ld thật sự hiểu là loại segment (PT_LOAD = "nạp vào RAM", PT_DYNAMIC = "bảng relocation ở đây") và số trong FLAGS(...). Số đó đi thẳng vào trường p_flags của ELF, theo quy ước bit: bit 0 = Execute, bit 1 = Write, bit 2 = Read. Vậy text = 5 (R+X), rodata = 4 (R), data = 6 (R+W).

Hai điều đáng để ý. Segment R bắt đầu ở …8008f4c0, không tròn trang, nhưng vẫn nằm ở trang khác với cuối .text (…8008e4a4): . += chỉ cần đẩy sang trang sau, không cần căn đúng biên. Segment RW có MemSiz lớn hơn FileSiz khá nhiều: phần chênh chính là .bss, Limine sẽ điền số 0.

Limine nạp ELF thế nào

Limine có sẵn bộ nạp ELF64. Việc này xảy ra lúc boot, khi Limine còn nắm quyền, trước khi kernel chạy dòng nào. Trình tự:

  1. ELF header — kiểm magic 7f 45 4c 46 ("\x7fELF"), kiểm là ELF64, lấy e_entry (= ENTRY(_start)).
  2. Program headers (không phải section headers) — chỉ xử lý segment PT_LOAD. Với mỗi segment: cấp RAM vật lý, chép p_filesz byte từ vị trí p_offset trong file, điền 0 cho phần p_memsz - p_filesz (chính là .bss), rồi map p_vaddr tới vùng RAM đó với quyền lấy từ p_flags.
  3. PT_DYNAMIC — nơi chứa bảng relocation, dùng khi kernel được nạp ở địa chỉ khác địa chỉ link (xem PIE, relocation và KASLR ở Đọc thêm, và KASLR & PIE Kernel).
  4. Chuẩn bị môi trường (Long Mode, paging, HHDM, stack), điền các response, rồi nhảy vào _start.

Kernel "đặt hàng" thông tin: request và response

Kernel muốn biết RAM ở đâu, có mấy CPU... nhưng chưa có cách nào tự hỏi phần cứng. Nên nó để sẵn trong file các biến static volatile struct limine_..._request, mỗi biến có trường .id là một dãy số magic. Limine quét file kernel tìm các magic đó, và trước khi nhảy vào _start thì ghi con trỏ tới câu trả lời vào trường .response. volatile báo compiler: giá trị này bị thay đổi từ bên ngoài chương trình, đừng tối ưu bỏ đi. Sáu request của cavOS nằm ở entry/bootloader.c; việc đọc chúng là Bài 3.

Điểm vào: _start()

Trích src/kernel/entry/kernel.c:

c
static volatile LIMINE_BASE_REVISION(2);
void _start(void) {
  systemDiskInit = false;

  if (LIMINE_BASE_REVISION_SUPPORTED == false)
    panic();

  initiateSerial();             // Bài 2
  initialiseBootloaderParser(); // Bài 3

  // Framebuffer doesn't depend on paging, limine prepares it anyways
  initiateVGA();                // Bài 4
  ...
  • LIMINE_BASE_REVISION(2) (trong include/limine.h) tạo mảng limine_base_revision[3] = hai số magic + số 2. Limine nào hiểu revision 2 sẽ ghi 0 vào phần tử cuối. LIMINE_BASE_REVISION_SUPPORTED chỉ là phép so limine_base_revision[2] == 0. Không được ghi 0 nghĩa là Limine quá cũ, kernel dừng ngay. Chi tiết: Limine Protocol §4.
  • Sau đó _start gọi lần lượt từng hệ con. Mỗi bài tiếp theo đọc một dòng trong danh sách này; thứ tự đầy đủ ở Bắt đầu.

Tự kiểm tra

Bấm vào câu hỏi để xem đáp án.

Đổi tên segment text trong PHDRS thành foo thì quyền của code có đổi không?

Không. Tên chỉ là nhãn để các dòng :text trong SECTIONS trỏ tới. Quyền nằm ở FLAGS(...), được ghi thẳng vào p_flags.

Vì sao .text và .rodata không được nằm chung một trang 4 KiB?

Quyền đọc/ghi/chạy được gán cho cả trang. Nếu chung trang thì hoặc .rodata chạy được, hoặc .text không chạy được. . += CONSTANT(MAXPAGESIZE) đẩy .rodata sang trang sau.

Limine đọc section headers hay program headers để nạp kernel?

Program headers. Loader chỉ cần biết khối nào chép vào đâu với quyền gì (PT_LOAD); section là thông tin cho linker và debugger.

Vì sao link.ld đặt .bss cuối cùng trong segment data?

.bss toàn số 0 nên không cần nằm trong file: loader điền 0 cho phần MemSiz - FileSiz ở cuối segment. Nếu có section khác đứng sau .bss, các số 0 đó phải được ghi thật vào file.

Limine quá cũ, không hiểu base revision 2. Bạn sẽ thấy log gì trên serial?

Không thấy gì. _start gọi panic() ngay ở dòng kiểm revision, trước cả initiateSerial().

Phía firmware UEFI

Ô "Firmware" trong sơ đồ chuỗi boot được giải thích ở các trang khái niệm sau:

  • ESP và UEFI boot — firmware tìm file .efi trên phân vùng nào và theo thứ tự nào (đĩa thật của cavOS: mục dưới).
  • UEFI Runtime Services và biến — dịch vụ nào của firmware còn dùng được sau khi kernel đã chạy.
  • Secure Boot — firmware kiểm chữ ký bootloader thế nào (cavOS khi bật nó: mục dưới).
  • PE, ELF và quy ước gọi hàm — vì sao Limine là file PE còn kernel là ELF, và hai bên gọi hàm theo quy ước nào.
  • Limine hay tự viết loader UEFI — tự viết loader thì phải làm thêm những việc gì Limine đang làm hộ.

Trên disk.img của cavOS có gì, và UEFI tìm Limine thế nào

Khái niệm chung: ESP và UEFI boot. Ảnh đĩa cavOS không phải GPT, và phân vùng boot cũng không mang nhãn ESP, nhưng vẫn boot được trên OVMF.

Không ghi FLAGS thì ld tự suy quyền

Nhiều kernel hobby (và linker.ld của lab) bỏ FLAGS(...). Khi đó ld lấy quyền segment bằng phép OR flag của các section bên trong. Flag của section lại do tên section chuẩn quyết định khi compile:

SegmentSectionFlag sectionp_flags
:text.textAX (alloc + exec)PF_R | PF_X → R+X
:rodata.rodata, .limine_requestsA (alloc)PF_R → R
:data.data, .bssWA (alloc + write)PF_R | PF_W → R+W

Quy tắc: section được nạp vào RAM thì luôn có R; có section ghi được thì thêm W; có section chạy được thì thêm X. Ghi tường minh như cavOS (FLAGS(5), FLAGS(4), FLAGS(6)) thì ld dùng đúng số bạn ghi, không suy nữa. Xem flag section của một file .o: readelf -S kernel.o.

Trạng thái máy lúc vào _start

Khái niệm chung: Long Mode. Binary Limine mà cavOS thật sự boot là Limine 10.8.5 (src/bootloader/limine/BOOTX64.EFI tự báo như vậy; assert.sh ghim "10.1.1" nhưng clone đầu nhánh v10.x-binary). Từ Limine 9, spec của protocol nằm ở repo riêng limine-protocol; Limine 10.8.5 ghim commit e42d010 của PROTOCOL.md. Mục "Machine State at Entry → x86-64" viết:

text
PE is enabled (cr0), ET is enabled (cr0), WP is enabled (cr0), PG is enabled (cr0),
PAE is enabled (cr4), LME and LMA are enabled (EFER). NX is enabled (EFER)
(if it is available).
  • Mọi segment register đã nạp segment 64-bit; GDTR trỏ tới một GDT của Limine (null, code/data 16-bit, 32-bit, 64-bit).
  • IDT ở trạng thái không xác định: kernel phải tự nạp IDT của mình.
  • Cờ IF, VM, DF bị xoá. A20 đã mở. PIC cũ bị mask hết; ở IO APIC, các entry delivery mode Fixed hoặc Lowest Priority bị mask.
  • rsp trỏ tới đỉnh một stack ít nhất 64 KiB; các thanh ghi đa dụng khác bằng 0.
  • Base revision 5 hứa thêm (IDTR, LDTR, TR rỗng; mọi bit khác của CR0/CR4/EFER bằng 0; Local APIC ở trạng thái xác định; IOMMU tắt). cavOS xin base revision 2 nên không được hứa những điều đó.

Vì vậy _start là một hàm C bình thường: không mov cr0, không wrmsr EFER, không far jump. Về sau cavOS chỉ thêm bit, không đổi chế độ: EFER.SCE cho syscall (cpu/fastSyscall.c), mấy bit CR0/CR4 cho FPU/SSE (cpu/system.c, cpu/sse.asm). Thanh ghi CPU 0 khi cavOS đã boot xong (QEMU monitor info registers, máy 2, KVM, -smp 2):

text
RIP=ffffffff8008e368 RFL=00000046 [---Z-P-] CPL=0 II=0 A20=1 SMM=0 HLT=0
CS =0028 0000000000000000 00000000 00209b00 DPL=0 CS64 [-RA]
CR0=80010033 CR2=00005ffffffff000 CR3=000000000212b000 CR4=00000620
EFER=0000000000000d01
  • EFER=0xd01 = SCE (bit 0) + LME (bit 8) + LMA (bit 10) + NXE (bit 11).
  • CR0=0x80010033 = PG + WP + PE, cộng MP/ET/NE cho FPU.
  • CR4=0x620 = PAE (bit 5) + OSFXSR/OSXMMEXCPT (bit 9, 10) cho SSE. LA57 = 0: paging 4 cấp.
  • Thuộc tính CS 00209b00 có bit 21 của dword cao (= bit 53 của descriptor) bằng 1: L = 1. QEMU ghi luôn là CS64.

PIE, relocation và KASLR trong cavOS

Khái niệm chung: KASLR & PIE Kernel. Lab thì ngược lại cavOS: -no-pie -mcmodel=kernel.

Cờ build. src/kernel/Makefile compile với -fPIE và link với:

make
LDFLAGS = -m elf_x86_64 \
		-nostdlib \
    -static \
    -pie \
    --no-dynamic-linker \
    -z text \
    -z max-page-size=0x1000 -T link.ld

link.ld có thêm segment dynamic (PHDRS { ... dynamic PT_DYNAMIC FLAGS(...); }, .dynamic : { *(.dynamic) } :data :dynamic) để loader tìm bảng relocation. Kết quả trên kernel.bin (bản build 2ba0edb), readelf -dW:

text
 0x0000000000000007 (RELA)               0xffffffff800a05a8
 0x0000000000000008 (RELASZ)             46416 (bytes)
 0x0000000000000009 (RELAENT)            24 (bytes)
 0x000000006ffffffb (FLAGS_1)            Flags: PIE
 0x000000006ffffff9 (RELACOUNT)          1934
text
Relocation section '.rela.dyn' at offset 0xa05a8 contains 1934 entries:
   1934 R_X86_64_RELATIVE

1934 mục × 24 byte = 46416 byte, khớp RELASZ. Tất cả đều là RELATIVE. Mục đầu tiên: offset ffffffff800acb50 (trong .data), addend -7fffe8ef = 0xffffffff80001711, một địa chỉ trong .text. Limine (common/lib/elf.c, elf64_apply_relocations) ghi *ptr = slide + r_addend; slide = 0 thì giá trị giữ nguyên.

CFLAGS của kernel (src/kernel/Makefile): -fPIE, không FPU/SIMD, không red zone (lý do: PE, ELF và ABI):

make
CFLAGS = -m64 -g -c -ffreestanding -Wall -Werror -fcommon -Iinclude/ -Inetworking/lwip/include/ -fPIE -mno-80387 \
    -mno-mmx \
    -mno-sse \
		-nostartfiles \
		-nostdlib \
    -mno-sse2 \
    -mno-red-zone -fno-stack-protector \
    -fno-stack-check \
    -fno-lto

Địa chỉ thật do Limine báo. initialiseBootloaderParser() đọc bootloader.kernelVirtBase / kernelPhysBase từ request limine_kernel_address_request (Bài 3). Trong PROTOCOL.md hiện hành tính năng này tên "Executable Address Feature", nhưng ID request giữ nguyên (0x71ba76863cc55f63, 0xb2644a48c516a487).

KASLR có chạy không? Không. target/boot/limine/limine.conf ghi (comment chép từ mẫu cũ của Limine 8.x; với Limine 10.8.5 chính dòng yes mới bật KASLR):

text
    # Disable KASLR (it is enabled by default for relocatable kernels)
    kaslr: yes

Nhưng Limine chỉ ngẫu nhiên hoá kernel relocatable: elf64_is_relocatable trả false ngay nếu kiểu ELF không phải ET_DYN, và protos/limine.c làm kaslr = kaslr && is_reloc;, nên HHDM cũng không bị ngẫu nhiên. Kernel cavOS lại là EXEC:

text
$ readelf -h ~/cavOS/target/boot/kernel.bin
  Type:                              EXEC (Executable file)
  Entry point address:               0xffffffff8002a548

Link lại cùng các file .o, cùng cờ, chỉ đổi . = 0xffffffff80000000; thành . = 0; trong một bản sao link.ld thì ra DYN (Position-Independent Executable file), entry 0x2a548. GNU ld 2.38 của cavOS (và ld 2.46 của Ubuntu) ghi PIE thành EXEC khi link ở base khác 0. PROTOCOL.md có tính đến cách link ở 0 ("a minimum slide of 0xffffffff80000000 is applied"); bản link ở 0 này chưa được boot thử. Hai lần boot thật (QEMU, KVM, -snapshot, monitor info mem và gva2gpa 0xffffffff80000000) cho cùng kết quả:

Lần 1Lần 2
Base ảo kernelffffffff80000000ffffffff80000000
Base vật lý kernel0xbfbbf0000xbfbbf000
HHDMffff800000000000ffff800000000000

Thêm nữa, cavOS in nhiều địa chỉ kernel ra serial và màn hình (vd fb{ffff8000fd000000} lộ base HHDM), nên kể cả khi KASLR chạy, một dòng log là đủ biết slide.

Limine 10.8.5 ngẫu nhiên hoá gì (đọc trong source) khi KASLR bật: base ảo của kernel (elf.c: slide = rand32() & ~(max_align - 1), thử lại tới khi kernel còn nằm gọn trên 0xffffffff80000000; bước 4 KiB trong 2 GiB, tối đa khoảng 219 vị trí) và base HHDM (set_paging_mode(): bước 1 GiB trong một phần tư nửa cao, khoảng 215 vị trí với 4 cấp; theo CONFIG.md, randomise_hhdm_base mặc định bật khi KASLR bật). Địa chỉ vật lý thì không ngẫu nhiên. Từ Limine 10.0.0 KASLR mặc định tắt (Limine 8.x ngược lại).

Vì sao cavOS ở −2 GiB dù build PIE

-mcmodel=kernel là lý do thường gặp để đặt kernel ở 0xffffffff80000000 (Higher-Half Kernel). cavOS không dùng nó: src/kernel/Makefile build với -fPIE, link với -pie, và cross compiler của cavOS từ chối ghép hai cờ:

text
$ x86_64-cavos-gcc -ffreestanding -c -O2 -fPIE -mcmodel=kernel t.c
cc1: error: code model kernel does not support PIC mode

Đếm relocation trong phần .text của entry/kernel.o chỉ thấy loại tương đối: R_X86_64_PC32 (14), R_X86_64_PLT32 (38), R_X86_64_REX_GOTPCRELX (4). Kernel cavOS chỉ khoảng 1 MiB, nên điều kiện "code và dữ liệu cách nhau ≤ 2 GiB" luôn thoả, đặt ở đâu cũng được. Vậy địa chỉ −2 GiB không do compiler đòi, mà do Limine đòi: mục "Memory Layout at Entry" của PROTOCOL.md (bản Limine 10.8.5 mà binary cavOS boot) viết kernel phải nạp ở hoặc trên 0xffffffff80000000 và "Lower half executables are not supported". link.ld chép theo mẫu của Limine.
