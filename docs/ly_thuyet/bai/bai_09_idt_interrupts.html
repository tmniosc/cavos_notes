Bài 9 - IDT & Interrupts

Status doneTags step, cpu, interrupt

Mục đích

Cho CPU biết phải chạy hàm nào khi có lỗi hoặc khi thiết bị cần kernel.

Bài này dựng IDT: bảng 256 ô, mỗi ô trỏ tới một handler. Không có nó, mọi lỗi CPU (#PF, #GP, chia cho 0…) hay ngắt thiết bị (bàn phím, timer) đều làm máy treo hoặc reset. Đây là cách kernel giành lại quyền điều khiển từ code đang chạy: nền cho timer (Bài 10 - APIC & Timer), cho scheduler cắt ngang task (Bài 12 - Multitasking & Scheduler) và cho việc xử lý page fault.

Nói thật đơn giản

Hãy hình dung CPU là một người đang làm việc, và IDT là tờ danh bạ khẩn cấp dán trên bàn, có 256 dòng. Khi có chuyện, CPU chỉ biết một con số (số vector): "chuyện số 14" là truy cập trang nhớ không có, "chuyện số 33" có thể là bàn phím. CPU tra dòng đó và gọi ngay người phụ trách.

Trước khi đi xử lý, phải ghi lại mình đang làm dở cái gì. CPU tự ghi vài thứ quan trọng nhất (đang ở lệnh nào, cờ, stack). Phần còn lại, tức các thanh ghi chung, do một đoạn mã nhỏ gọi là stub ghi giúp. Xử lý xong, đọc lại tờ ghi chú và quay về đúng chỗ cũ bằng lệnh iretq.

Cần biết trước

Năm ý về ngắt trên x86-64; GDT và TSS đã học ở Bài 7.

  • Interrupt và exception. Exception do chính lệnh đang chạy gây ra (chia cho 0, đọc trang không có). Interrupt đến từ bên ngoài (thiết bị gửi IRQ) hoặc từ lệnh int n. Exception chia ba loại: fault lưu RIP của chính lệnh lỗi để chạy lại được (#PF, #DE, #UD, #GP); trap lưu RIP của lệnh kế tiếp (int3); abort không bảo đảm quay lại được (#DF, #MC). Đọc sâu: Intel SDM Vol.3 §6.5.
  • Vector và IDT. Mỗi nguồn ngắt có một số 0–255. Vector 0–31 dành cho exception của CPU, từ 32 trở lên tuỳ OS. IDT là mảng 256 cổng (gate), mỗi cổng 16 byte ở 64-bit: địa chỉ handler, selector CS (0x28), số IST, và một byte P | DPL | type. Thanh ghi IDTR giữ địa chỉ + kích thước bảng, nạp bằng lidt.
  • Interrupt gate và trap gate. Hai loại cổng chỉ khác một điều: vào qua interrupt gate (type 0xE) thì CPU xoá cờ IF, nên không ngắt nào chen vào giữa handler; trap gate (type 0xF) giữ nguyên IF. cavOS chỉ dùng interrupt gate.
  • Error code. Một số exception (8, 10–14, 17, 21, 29, 30) đẩy thêm một số 8 byte mô tả lỗi; các vector khác thì không. Để mọi handler thấy cùng một bố cục stack, stub tự đẩy số 0 giả cho vector không có error code. Với #PF, địa chỉ gây lỗi nằm ở thanh ghi CR2.
  • PIC 8259. Chip ngắt cũ của PC, gom 16 đường IRQ thành vector. Mặc định BIOS cho IRQ 0–7 vào vector 8–15, trùng exception của CPU, nên OS phải remap (đổi vector gốc) trước khi dùng. cavOS remap rồi che hết, vì nó dùng APIC thay thế (Bài 10).
  • Đã gặp ở Bài 7: selector kernel code 0x28 (ghi trong mỗi cổng), TSS với RSP0 (stack khi từ ring 3 vào ring 0) và IST (7 stack dự phòng mà cổng có thể chọn).

Đọc code cavOS

Một hàm initiateISR() dựng mọi thứ; một hàm handle_interrupt() nhận mọi ngắt.

File: cpu/idt.c, include/idt.h, cpu/isr.asm, cpu/isr.c, include/isr.h (cavOS 2ba0edb). Không có hàm initiateIDT(): IDT được điền bên trong initiateISR().

1. Vị trí trong _start()

c
// entry/kernel.c:_start()
  initiatePMM();
  initiateVMM();

  initiateGDT();                                     // Bài 7
  LinkedListInit(&dsIrqHandler, sizeof(irqHandler)); // danh sách IRQ handler rỗng
  initiateACPI(); // needed for APIC setup           // Bài 8
  initiateISR();                                     // bài này
  initiatePaging();

IDT cần GDT có trước (cổng ghi selector 0x28). initiateISR() gọi initiateAPIC() ở cuối, mà APIC đọc bảng MADT của ACPI, nên ACPI phải đứng trước.

2. Cấu trúc bảng (idt.h, idt.c)

c
typedef struct {
  uint16_t isr_low;      // offset handler 15:0
  uint16_t kernel_cs;    // selector CS khi vào handler
  uint8_t  ist;          // 0 = không đổi stack, 1..7 = TSS.istN
  uint8_t  attributes;   // P | DPL | 0 | type
  uint16_t isr_mid;      // offset 31:16
  uint32_t isr_high;     // offset 63:32
  uint32_t reserved;
} __attribute__((packed)) idt_gate_t;   // 16 byte

#define IDT_ENTRIES 256
static idt_gate_t     idt[IDT_ENTRIES] = {0};
static idt_register_t idt_reg;          // { uint16_t limit; uint64_t base; }

void set_idt_gate(int n, uint64_t handler, uint8_t flags) {
  idt[n].isr_low = (uint16_t)handler;
  idt[n].kernel_cs = GDT_KERNEL_CODE;   // 0x28
  idt[n].ist = 0;                       // không bao giờ dùng IST
  idt[n].reserved = 0;
  idt[n].attributes = flags;
  idt[n].isr_mid = (uint16_t)(handler >> 16);
  idt[n].isr_high = (uint32_t)(handler >> 32);
}

void set_idt() {
  idt_reg.base = (size_t)&idt;
  idt_reg.limit = IDT_ENTRIES * sizeof(idt_gate_t) - 1;   // 4095
  asm volatile("lidt %0" ::"m"(idt_reg) : "memory");
}

Địa chỉ handler 64-bit bị chia làm 3 mảnh vì định dạng cổng được nới rộng từ cổng 32-bit cũ. Hai giá trị flags cavOS dùng:

flagsbitnghĩadùng cho
0x8E1 00 0 1110P=1, DPL=0, interrupt gatemọi cổng kernel
0xEE1 11 0 1110P=1, DPL=3, interrupt gatevector 3 (int3) và 0x80 (syscall): ring 3 được gọi bằng int n

DPL của cổng chỉ được kiểm khi ngắt do lệnh int n/int3 gây ra. IRQ và exception thật thì vào được mọi cổng có P=1, bất kể ring đang chạy.

3. Điền IDT (initiateISR)

c
void initiateISR() {
  // IRQs 0 - 15 -> 32 - 48
  remap_pic();

  // ISR exceptions 0 - 31
  for (int i = 0; i < 48; i++) {
    set_idt_gate(i, (uint64_t)asm_isr_redirect_table[i], 0x8E);
  }

  // Allow userspace to use breakpoints (like int3)
  set_idt_gate(3, (uint64_t)asm_isr_redirect_table[3], 0xEE);

  // APIC Spurious Interrupts
  set_idt_gate(0xff, (uint64_t)isr255, 0x8E);

  // Syscalls having DPL 3
  set_idt_gate(0x80, (uint64_t)isr128, 0xEE);

  // Finalize
  set_idt();
  initiateAPIC();
  asm volatile("sti");
}

remap_pic() gửi chuỗi 4 "ICW" (initialization command word) cho hai chip PIC: master ở cổng I/O 0x20/0x21, slave ở 0xA0/0xA1.

ICW10x20 ← 0x110xA0 ← 0x11bắt đầu khởi tạo, sẽ có ICW4
ICW20x21 ← 0x200xA1 ← 0x28vector gốc: IRQ 0–7 → 0x20–0x27, IRQ 8–15 → 0x28–0x2F
ICW30x21 ← 0x040xA1 ← 0x02slave nối vào chân IRQ2 của master

Remap rồi che ngay nghe có vẻ thừa, nhưng nếu PIC còn gửi gì tới CPU (ví dụ một IRQ đến ngay trước khi che, hoặc ngắt "spurious" ở IRQ 7/15 khi yêu cầu biến mất giữa chừng), nó sẽ rơi vào 0x20–0x2F, cổng IRQ có handler, thay vì bị hiểu nhầm là exception 8–15 của CPU.

initiateAPIC() (chi tiết ở Bài 10) tìm bảng MADT qua uACPI, ghi lại các I/O APIC, rồi bật Local APIC bằng apicWrite(0xF0, apicRead(0xF0) | 0x1FF): thanh ghi 0xF0 là Spurious Interrupt Vector, 0x1FF = bit 8 (bật APIC) + vector 0xFF. Đó là lý do có cổng 0xFF. Cuối cùng sti bật IF: từ đây CPU nhận IRQ.

4. Stub và isr_common (isr.asm)

Mỗi vector có một stub vài lệnh, sinh bằng macro NASM. Stub đưa stack về cùng một hình rồi nhảy vào phần chung:

asm
%macro ISR_ERROR_CODE 1
global isr%1
isr%1:
    push %1   ; interrupt number       (error code CPU đã đẩy sẵn)
    jmp isr_common
%endmacro

%macro ISR_NO_ERROR_CODE 1
global isr%1
isr%1:
    push 0    ; dummy error code to align with TrapFrame
    push %1   ; interrupt number
    jmp isr_common
%endmacro

ISR_NO_ERROR_CODE 0 ... 7,  ISR_ERROR_CODE 8,  ISR_NO_ERROR_CODE 9,
ISR_ERROR_CODE 10 ... 14,   ISR_NO_ERROR_CODE 15 ... 47,  ISR_NO_ERROR_CODE 128

asm_isr_redirect_table:      ; 48 con trỏ isr0..isr47 cho vòng for trong initiateISR
%assign i 0
%rep 48
  dq isr%+i
%assign i i+1
%endrep
asm
isr_common:
    push rax / rbx / rcx / rdx / rsi / rdi / rbp / r8 ... r15   ; 15 thanh ghi
    mov rbp, ds
    push rbp                 ; DS cũ
    mov bx, 0x30             ; kernel data 64
    mov ds, bx
    mov es, bx
    mov ss, bx
    mov rdi, rsp             ; tham số 1 = địa chỉ khung
    call handle_interrupt
asm_isr_exit:
    pop rbp
    mov es, ebp              ; dòng "mov ds, ebp" bị comment
    pop r15 ... rax
    add rsp, 16              ; bỏ vector + error code
    iretq                    ; pop RIP, CS, RFLAGS, RSP, SS

Khi handle_interrupt chạy, rdi trỏ vào một khối 184 byte trên stack. include/isr.h mô tả đúng khối đó bằng struct AsmPassedInterrupt; thứ tự trường là thứ tự ngược của các lệnh push:

5. Một hàm nhận mọi ngắt (handle_interrupt)

c
void handle_interrupt(uint64_t rsp) {
  AsmPassedInterrupt *cpu = (AsmPassedInterrupt *)rsp;
  if (cpu->interrupt >= 32 && cpu->interrupt <= 47) { // IRQ
    if (cpu->interrupt >= 40) outportb(0xA0, 0x20);   // EOI cho PIC slave
    outportb(0x20, 0x20);                             // EOI cho PIC master
    apicWrite(0xB0, 0);                               // EOI cho Local APIC
    /* duyệt dsIrqHandler, gọi mọi handler có id == vector */
  } else if (cpu->interrupt >= 0 && cpu->interrupt <= 31) { // exception
    /* (a) page fault "cố ý" của scheduler -> schedule() */
    /* (b) lỗi trong task user -> handleTaskFault()       */
    /* (c) lỗi trong kernel -> in CR2 nếu #PF, registerDump, panic() */
  } else if (cpu->interrupt == 0x80) {
    syscallHandler(cpu);
  }
}
  • IRQ (32–47). Báo "xong" (EOI, end of interrupt) cho cả PIC lẫn Local APIC, rồi gọi các handler đã đăng ký cho vector đó. Nếu handler đăng ký kèm argument, nó nhận argument thay vì khung ngắt.
  • (a) Page fault cố ý. Khi currentTask->schedPageFault bật và CR2 == SCHED_PAGE_FAULT_MAGIC_ADDRESS (0x5FFFFFFFF000, include/paging.h), handler tăng RIP rồi gọi schedule(). Đó là cách một đoạn code tự nhường CPU cho scheduler (Bài 12).
  • (b) Lỗi trong task user (đã có task, task không phải kernel, không đang ở giữa syscall): handleTaskFault(). Với int3 nó bật tín hiệu SIGTRAP cho task; với lỗi khác nó in thanh ghi rồi taskKill(id, 139). Kernel sống tiếp.
  • (c) Lỗi trong kernel: in [isr] Page fault occured at cr2{…} rip{…} nếu là #PF, registerDump() in toàn bộ khung, in [isr] Kernel panic: <tên>! lấy từ mảng exceptions[], rồi panic() = cli + vòng hlt.
  • Vector 0xFF (spurious) không rơi vào nhánh nào: handler không làm gì. Đúng theo Intel: ngắt spurious của APIC không cần EOI.

6. Ai đăng ký IRQ handler

registerIRQhandler(id, handler) thêm một phần tử vào linked list dsIrqHandler. Số id là vector, cấp động bởi irqPerCoreAllocate() trong cpu/apic.c: lần lượt 32 + 0, 32 + 1… cho từng GSI mới, không theo số IRQ của PIC. Những chỗ gọi: cpu/timer.c (PIT rồi APIC timer), drivers/kb.c, drivers/mouse.c, drivers/ahci.c, các NIC (e1000.c, rtl8139.c, rtl8169.c) và acpi/uacpi_glue.c. Cách I/O APIC đưa IRQ tới vector đó là chuyện của Bài 10 và Bài 11.

Tự kiểm tra

Năm câu kiểm tra hiểu, không phải nhớ.

Vì sao stub của vector không có error code phải đẩy thêm số 0?

Để khung stack của mọi vector có cùng bố cục. Nhờ vậy một isr_common, một struct AsmPassedInterrupt và một lệnh add rsp, 16 dùng được cho tất cả.

Handler #PF trả về mà không sửa gì. Chuyện gì xảy ra?

#PF là fault, RIP đã lưu trỏ đúng lệnh lỗi. iretq chạy lại lệnh đó, trang vẫn chưa map, lại #PF: vòng lặp vô tận. Handler phải map trang, đổi RIP, hoặc dừng.

Vì sao cổng 3 và 0x80 có DPL 3, còn các cổng khác DPL 0?

DPL của cổng quyết định ring nào được gọi nó bằng int n. Chương trình user cần int3 (debugger) và int 0x80 (syscall), nhưng không được tự gọi handler page fault hay IRQ.

Vì sao cavOS phải remap PIC dù sau đó che hết IRQ của nó?

Mặc định IRQ 0–7 rơi vào vector 8–15, trùng exception của CPU. Nếu PIC còn gửi ngắt nào (trước lúc che, hoặc spurious), remap bảo đảm nó rơi vào 0x20–0x2F chứ không bị hiểu nhầm thành #DF hay #GP.

Stack kernel của cavOS bị tràn và gây #PF. Vì sao máy reset thay vì in "Kernel panic"?

Mọi cổng có ist = 0, nên CPU đẩy khung #PF vào chính stack hỏng, lỗi tiếp thành #DF, rồi đẩy khung #DF cũng vào đó, lỗi lần ba thành triple fault và CPU reset. IST cho #DF sẽ tránh được, như Lab 0x04 cho thấy.

Câu hỏi mở của dàn ý cũ, các điểm yếu tìm thấy trong source, và ánh xạ spec.

Câu hỏi mở (đã trả lời)

  • Interrupt gate và trap gate khác nhau ở đâu (cờ IF)? Vào qua interrupt gate (type 0xE) thì CPU xoá IF trước khi chạy handler; trap gate (type 0xF) giữ IF. Cả hai đều lưu RFLAGS cũ trong khung, nên iretq trả IF về như trước. cavOS dùng 0x8E/0xEE cho mọi cổng, tức chỉ interrupt gate: handler không bao giờ bị IRQ chen ngang.
  • Liên hệ IST trong Bài 7 - GDT & TSS? Byte ist của cổng chọn một trong 7 con trỏ TSS.ist1..7; khác 0 thì CPU luôn nạp RSP từ đó trước khi đẩy khung, kể cả khi không đổi ring. cavOS ghi ist = 0 ở mọi cổng, nên chỉ có RSP0 (khi từ ring 3 vào) và không có stack dự phòng cho #DF/NMI/#MC.

Điểm yếu tìm thấy trong source

  • Bốn vector có error code bị khai là không có. isr.asm dùng ISR_NO_ERROR_CODE cho 17 (#AC), 21 (#CP), 29 (#VC), 30 (#SX), trong khi chúng có error code: 17 và 21 theo Intel SDM Vol.3 bảng 6-1, 29 và 30 theo AMD APM Vol.2 (hai vector này chỉ AMD định nghĩa). Nếu xảy ra, stub đẩy thêm số 0 nên khung lệch 8 byte: cpu->rip đọc phải error code. Hiện chưa xảy ra được: #AC chỉ có khi bật CR0.AM + RFLAGS.AC ở ring 3, #CP cần CET, #VC/#SX chỉ có trong máy ảo AMD SEV.
  • Không IST, nên tràn stack kernel = triple fault. Lab 0x04 tái hiện: với ist = 0, log QEMU -d int ghi check_exception old: 0xe new 0xe → old: 0x8 new 0xe → Triple fault; với IST1 thì handler #DF chạy được.
  • Vector IRQ cấp tới MAX_IRQ = 256, nhưng chỉ 32–47 có cổng. irqPerCoreAllocate() trả 32 + chỉ số với chỉ số tới 255, trong khi initiateISR() chỉ điền 48 cổng đầu và handle_interrupt() chỉ coi 32–47 là IRQ. GSI thứ 17 trở đi sẽ nhận vector 48+, cổng trống, và thiết bị ngắt lần đầu là #GP. Với số thiết bị hiện có thì chưa chạm tới.
  • Gọi C khi stack chưa căn 16. Tính cả 5 qword CPU đẩy, khung có 23 qword (lẻ), nên lúc call handle_interrupt RSP lệch 8 so với yêu cầu của System V ABI. Không gây lỗi vì kernel biên dịch với -mno-sse -mno-sse2 (src/kernel/Makefile), không có lệnh nào đòi căn 16. Lab 0x04 thêm sub $8, %rsp.
  • Chỉ khôi phục ES. asm_isr_exit comment dòng mov ds, ebp, và isr_common không nạp FS/GS. Đó là lý do dump cavOS ở Bài 7 thấy FS=0000 GS=0000 dù gdt_reload đã nạp 0x30.
  • Tên trong exceptions[] theo kiểu cũ: vector 15 là "Unknown Interrupt", 16 là "Coprocessor Fault" (#MF), 19–31 đều "Reserved" (19 thật ra là #XM, lỗi SIMD).
