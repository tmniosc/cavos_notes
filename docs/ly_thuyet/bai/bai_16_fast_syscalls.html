Bài 16 - Fast Syscalls

Status doneTags step, syscall, sysret, msr, star, lstar, fmask, swapgs, int 0x80

Hàm: initiateSyscallInst() (cpu/fastSyscall.c), syscall_entry (cpu/isr.asm), syscallHandler(), registerSyscall() (syscalls/syscalls.c), initiateSyscalls() · Phụ thuộc: selector GDT và TSS từ Bài 7 - GDT & TSS, task, stack và schedule() từ Bài 12 - Multitasking & Scheduler, file và VFS từ Bài 15.

Mục đích

Cho chương trình ring 3 một cánh cửa nhanh vào kernel.

Chương trình userspace không được chạm phần cứng hay bộ nhớ kernel. Muốn đọc file, in chữ, tạo tiến trình, nó phải nhờ kernel bằng một syscall. x86-64 có hai cửa: lệnh int 0x80 (đi qua IDT như một ngắt) và lệnh syscall (đi thẳng tới một địa chỉ ghi sẵn trong MSR). cavOS cài cả hai, nhưng chương trình của nó (biên dịch với musl, như trên Linux) dùng syscall. Bài này đọc cách cavOS dựng cửa syscall, đường vào và ra, và bảng hàm syscall kiểu Linux. Bài 18 chạy chương trình thật qua cửa này.

Nói thật đơn giản

Ngắt giống gọi tổng đài: tổng đài tra danh bạ (IDT), kiểm tra bạn có quyền gọi số đó không, ghi lại cuộc gọi lên sổ (đẩy 5 thứ lên stack), rồi mới nối máy. syscall giống một đường dây nóng: chỉ có một số, nối thẳng tới một người trực đã biết trước (LSTAR), không tra cứu, không ghi sổ. CPU chỉ nhét địa chỉ quay về vào RCX và cờ vào R11, rồi nhảy.

Vì CPU không ghi sổ, người trực phải tự lo: tự đổi sang bàn làm việc của mình (stack kernel), tự chép lại mọi thứ cần nhớ. Để tìm bàn của mình khi tay đang không cầm gì, cavOS dùng một "ngăn kéo bí mật" mà lệnh swapgs mở ra: thanh ghi GS trỏ tới threadInfo, trong đó ghi sẵn địa chỉ stack.

Cần biết trước

Ba ý về lệnh syscall; GDT, TSS và khung ngắt đã có ở Bài 7, 9, 12.

  • MSR. Model Specific Register: thanh ghi đặc biệt đọc/ghi bằng rdmsr/wrmsr với số trong ECX. Bốn cái cho syscall: EFER (bit SCE bật lệnh), STAR (selector), LSTAR (địa chỉ vào), FMASK (bit RFLAGS cần xoá).
  • syscall làm gì, và không làm gì. Làm: RCX ← RIP kế tiếp, R11 ← RFLAGS, RFLAGS &= ~FMASK, CS/SS ← từ STAR, RIP ← LSTAR, CPL = 0. Không làm: không đổi RSP, không đẩy gì lên stack, không đọc TSS. sysret làm ngược lại: RIP ← RCX, RFLAGS ← R11, CS/SS user từ STAR.
  • GS base và swapgs. Trong long mode, GS chỉ còn là một địa chỉ nền (MSR GS_BASE). swapgs tráo GS_BASE với KERNEL_GS_BASE. Kernel dùng nó để có ngay một con trỏ tới dữ liệu riêng của CPU mà không cần thanh ghi nào.
  • ABI syscall của Linux (cavOS theo đúng): số syscall trong RAX, tham số RDI, RSI, RDX, R10, R8, R9 (R10 thay RCX vì syscall đè RCX), kết quả trả về trong RAX, lỗi là số âm -errno.
  • Đã gặp: selector 0x28/0x30/0x48/0x50 và lý do data user đứng trước code user ở Bài 7; khung AsmPassedInterrupt ở Bài 9; whileTssRsp, schedule() ở Bài 12.

Đọc code cavOS

Ghi bốn MSR, viết đường vào bằng asm, tra bảng hàm theo số trong RAX, và cho scheduler cập nhật stack syscall mỗi lần đổi task.

Syscall được dựng sau filesystem (nhiều syscall là thao tác file) và trước khi chạy chương trình đầu tiên. Log cavOS: [syscalls] System calls are ready to fire: 99/450, tức 99 số syscall có hàm xử lý trong bảng 450 ô.

2. initiateSyscallInst(): bốn MSR

c
bool checkSyscallInst() {
  uint32_t eax = 0x80000001, ebx = 0, ecx = 0, edx = 0;
  cpuid(&eax, &ebx, &ecx, &edx);
  return (edx >> 11) & 1;
}

void initiateSyscallInst() {
  if (!checkSyscallInst()) { ... panic(); }

  // setup this core's thread info structure
  threadInfo.syscall_stack = 0;
  threadInfo.lapic_id = bootloader.smp[bootloader.smpBspIndex].bsp_lapic_id;
  wrmsr(MSRID_KERNEL_GSBASE, (size_t)&threadInfo);

  uint64_t star_reg = rdmsr(MSRID_STAR);
  star_reg &= 0x00000000ffffffff;
  star_reg |= ((uint64_t)GDT_USER_CODE - 16) << 48;
  star_reg |= ((uint64_t)GDT_KERNEL_CODE) << 32;
  wrmsr(MSRID_STAR, star_reg);

  // entry defined in isr.asm
  wrmsr(MSRID_LSTAR, (uint64_t)syscall_entry);

  uint64_t efer_reg = rdmsr(MSRID_EFER);
  efer_reg |= 1 << 0;                    // SCE
  wrmsr(MSRID_EFER, efer_reg);

  wrmsr(MSRID_FMASK, RFLAGS_IF | RFLAGS_DF);
}
  • KERNEL_GS_BASE = &threadInfo: chỗ syscall_entry sẽ đọc stack kernel. threadInfo chỉ có hai trường: syscall_stack (ở gs:0) và lapic_id.
  • FMASK = IF | DF: kernel vào với ngắt tắt, nên không ngắt nào rơi vào lúc RSP còn là stack user.

3. syscall_entry: tự đổi stack, tự dựng khung

asm
; cpu/isr.asm (NASM)
syscall_entry:
  swapgs
  mov cr2, rax ; use cr2 as an extra register
  mov rax, qword [gs:0] ; thread pointer
  xchg rsp, rax ; switch stack ptrs
  push rax                 ; the user's RSP
  mov rax, cr2

  ; mimic: interrupt stuff
  push qword 0  ; x5: ss, rsp, rflags, cs, rip
  ...
  push qword 0 ; error
  push qword 0 ; interrupt

  push rax
  push rbx
  push rcx                 ; user RIP
  ...
  push r11                 ; user RFLAGS
  ...
  mov rbp, ds
  push rbp

  mov rdi, rsp
  call syscallHandler
  cli ; important to avoid race conditions

  pop rbp
  mov ds, ebp
  mov es, ebp
  pop r15
  ...
  pop rax
  add rsp, 16      ; pop error code and interrupt number
  add rsp, 40      ; pop other interrupt stuff
  pop rsp ; reset rsp
  o64 sysret
  • swapgs trước tiên: lúc này mọi thanh ghi đa dụng đều là của user, chỉ có %gs:0 là đọc được mà không phá gì.
  • Cần một thanh ghi tạm để đổi stack mà RAX đang giữ số syscall, nên cavOS cất RAX vào CR2 (thanh ghi địa chỉ page fault) trong ba lệnh. Hợp lệ ở ring 0 vì ngắt đang tắt; cách thường gặp hơn là cất RSP user vào một ô trong threadInfo.
  • Khung dựng có cùng hình AsmPassedInterrupt với khung ngắt (5 ô CPU đẩy, nhưng để 0), nên syscallHandler và code signal dùng chung struct. RSP của user nằm ngay sau khung.
  • Đường ra không có swapgs. Mục 6 và Đọc thêm nói hệ quả.

4. syscallHandler() và bảng syscall

c
size_t   syscalls[MAX_SYSCALLS] = {0};        // MAX_SYSCALLS = 450

void registerSyscall(uint32_t id, void *handler) {
  if (id > MAX_SYSCALLS) { ... panic(); }
  if (syscalls[id]) { ... panic(); }          // duplicate
  syscalls[id] = (size_t)handler;
  syscallCnt++;
}

void syscallHandler(AsmPassedInterrupt *regs) {
  wrmsr(MSRID_KERNEL_GSBASE, (size_t)&threadInfo);
  uint64_t *rspPtr = (uint64_t *)((size_t)regs + sizeof(AsmPassedInterrupt));
  uint64_t  rsp = *rspPtr;
  currentTask->systemCallInProgress = true;
  currentTask->syscallRegs = regs;
  currentTask->syscallRsp = rsp;

  asm volatile("sti"); // do other task stuff while we're here!

  uint64_t id = regs->rax;
  if (id > MAX_SYSCALLS) { regs->rax = -1; goto cleanup; }
  size_t handler = syscalls[id];
  if (!handler) { regs->rax = ERR(ENOSYS); ... goto cleanup; }

  long int ret = ((SyscallHandler)(handler))(regs->rdi, regs->rsi, regs->rdx,
                                             regs->r10, regs->r8, regs->r9);
  ...
  regs->rax = ret;
cleanup:
  currentTask->systemCallInProgress = false;
  // now safely handle whatever signal is left
  signalsPendingHandleSys(currentTask, rspPtr, regs);
}

// syscalls/linux/syscalls_fs.c (one of many files)
#define SYSCALL_WRITE 1
...
  registerSyscall(SYSCALL_WRITE, syscallWrite);
  • Số syscall giống Linux x86-64 (1 write, 39 getpid, 60 exit...), để chương trình biên dịch cho Linux với musl chạy được. Số chưa có hàm trả -ENOSYS; vài số được "giả vờ thành công" (trả 0) cho chương trình khỏi dừng.
  • sti ngay đầu handler: syscall có thể chạy lâu (đọc đĩa, chờ phím), và timer vẫn đổi task trong lúc đó. Task đang trong syscall bị cắt ở ring 0, trên stack syscall của nó.
  • Kết quả ghi đè regs->rax trong khung; đường ra pop khung, nên RAX của user nhận kết quả.

5. Stack syscall riêng cho mỗi task

c
// multitasking/task.c (taskCreate)
  target->whileSyscallRsp = (uint64_t)syscalltssRsp + syscalltssRspSize;

// multitasking/schedule.c
  // Change TSS rsp0 (software multitasking)
  tssPtr->rsp0 = next->whileTssRsp;
  threadInfo.syscall_stack = next->whileSyscallRsp;

  // Apply new MSRIDs
  wrmsr(MSRID_FSBASE, next->fsbase);
  wrmsr(MSRID_GSBASE, next->gsbase);
  wrmsr(MSRID_KERNEL_GSBASE, (size_t)&threadInfo);

Mỗi task có hai stack kernel: stack TSS (whileTssRsp, CPU dùng khi có ngắt từ ring 3) và stack syscall (whileSyscallRsp, syscall_entry dùng). Mỗi lần đổi task, scheduler ghi đỉnh stack syscall của task mới vào threadInfo, nên %gs:0 luôn là stack của task đang chạy. Scheduler cũng nạp FS/GS base của task mới (musl dùng FS cho thread-local storage).

6. Cửa cũ: int 0x80

c
// cpu/isr.c (initiateISR)
  set_idt_gate(0x80, (uint64_t)isr128, 0xEE);   // DPL 3: ring 3 may use "int 0x80"

// cpu/isr.c (handle_interrupt)
  } else if (cpu->interrupt == 0x80) {
    syscallHandler(cpu);
  }

int 0x80 đi qua IDT như mọi ngắt: CPU đổi sang RSP0 của TSS, đẩy 5 qword, stub dựng khung. cavOS gọi cùng syscallHandler. Cổng có DPL 3 để ring 3 được phép dùng lệnh int với số này; các cổng khác DPL 0, ring 3 gọi sẽ bị #GP.

Tự kiểm tra

Năm câu.

GDT_USER_CODE = 0x50, GDT_KERNEL_CODE = 0x28. Tính STAR và CS/SS mà syscall, sysret nạp.

STAR[63:48] = 0x50 - 16 = 0x40, STAR[47:32] = 0x28: STAR = 0x0040002800000000. syscall: CS = 0x28, SS = 0x30. sysret: CS = (0x40 + 16) | 3 = 0x53, SS = (0x40 + 8) | 3 = 0x4b.

Vì sao tham số thứ tư của syscall nằm ở R10 chứ không ở RCX như hàm C thường?

syscall ghi đè RCX bằng địa chỉ quay về (và R11 bằng RFLAGS). Giá trị chương trình để trong RCX bị mất trước khi kernel kịp đọc, nên ABI chuyển tham số thứ tư sang R10.

Vì sao mỗi task cần stack syscall riêng, thay vì một stack syscall chung cho cả kernel?

Handler sti và có thể bị cắt giữa chừng; task khác chạy và cũng gọi syscall. Nếu dùng chung một stack, syscall của task thứ hai đè lên khung và biến cục bộ của syscall đang dở của task thứ nhất.

syscall_entry đọc %gs:0. Nếu chương trình user tự đặt GS base của nó (ví dụ qua arch_prctl), lần syscall sau còn đúng không?

Vẫn đúng: swapgs tráo GS của user (giá trị mới) với KERNEL_GS_BASE (= &threadInfo), nên kernel vẫn có threadInfo. Cái mất là GS của user: sau syscall nó thành &threadInfo (không swap lại), tới lần đổi task kế tiếp scheduler mới nạp lại gsbase của task.

Trong syscall_entry, bỏ lệnh cli trước đoạn pop. Chuyện gì có thể xảy ra?

Một ngắt có thể tới giữa lúc đang pop hoặc ngay sau pop rsp, khi RSP đã là stack user mà CPU còn ở ring 0: khung ngắt bị đẩy lên stack user. sysret tự bật lại IF từ R11 khi đã ở ring 3.

Đọc thêm

Câu hỏi của dàn ý cũ, những chỗ nguy hiểm trong đường syscall của cavOS (có lab chạy thật làm bằng chứng), và chỗ tra trong spec.

Câu hỏi mở (đã trả lời)

  • SYSCALL hay SYSENTER? syscall/sysret (chuẩn của AMD64, CPU Intel 64-bit đều có). sysenter là lệnh 32-bit của Intel; cavOS không dùng.
  • Có còn int 0x80? Có, cổng DPL 3 gọi cùng syscallHandler.
  • Bảng syscall theo số nào? Theo số của Linux x86-64; 99 trên 450 số có hàm.

Những chỗ nguy hiểm

  • GS không được trả lại. Đường ra thiếu swapgs, và handler ghi KERNEL_GS_BASE = &threadInfo. Sau syscall đầu tiên, GS base của chương trình user là địa chỉ của threadInfo (Lab 0x0a đo được: CR2 = &threadInfo). User không đọc được nội dung (trang kernel), nhưng biết được địa chỉ kernel, điều KASLR muốn giấu, và mất GS của mình.
  • int 0x80 với sti. Đường int 0x80 chạy trên stack TSS; khi handler sti và bị cắt, lần chạy lại schedule() chép khung đã lưu lên đỉnh stack TSS, đè khung int 0x80 của user. Lab 0x0a bản INT80_STI treo đúng ở đó. Chương trình musl không dùng int 0x80 nên cavOS ít khi gặp.
  • Kiểm số syscall lệch một. id > MAX_SYSCALLS cho qua id == 450, rồi đọc syscalls[450], ô nằm ngay sau bảng 450 phần tử, và gọi giá trị đó như một hàm.
  • RCX từ sigreturn không được kiểm. syscalls/signals.c chép RCX từ khung trên stack user (passed->rcx = ucontext->rcx) rồi về bằng sysret. Trên CPU Intel, RCX không canonical làm sysret gây #GP khi còn ở ring 0 nhưng RSP đã là của user (CVE-2012-0217). Lab 0x0a bản BAD_SYSRET: QEMU TCG báo #GP ở ring 3, nên trên QEMU không thấy được.
  • Với int 0x80, syscallHandler vẫn đọc "RSP user" ở ngay sau khung, nơi không có RSP nào cả (khung ngắt đã chứa RSP thật ở usermode_rsp).
