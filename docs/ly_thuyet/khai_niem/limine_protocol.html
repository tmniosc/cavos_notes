Boot Protocol & Limine

Tags concept, boot, spec

Boot protocol là hợp đồng giữa bootloader và kernel: kernel phải trông thế nào để được nạp, máy ở trạng thái nào lúc vào kernel, và thông tin phần cứng được giao qua đâu. Multiboot, Linux boot protocol và Limine protocol là ba hợp đồng như vậy. Trang này dùng Limine làm ví dụ chính. Liên quan: Request-Response Mechanism, Limine và loader tự viết.

Chuỗi boot

Ba chương trình chạy nối nhau, mỗi chương trình giao máy cho chương trình sau.

text
[power] → firmware (UEFI / BIOS) → bootloader (GRUB, Limine, ...) → kernel entry point
  • Firmware: chạy đầu, khởi tạo phần cứng cơ bản, dựng memory map và bảng ACPI, nạp bootloader.
  • Bootloader: đọc file kernel, đặt nó vào bộ nhớ, đưa CPU vào trạng thái đã hứa, nhảy vào điểm vào của kernel.
  • Kernel: từ đây mọi thứ là của nó.

Một hợp đồng phải ghi gì

Bootloader và kernel do hai người viết, nên cần một hợp đồng ghi rõ ai đưa gì cho ai.

  1. Nhận diện kernel: file định dạng gì (ELF, PE, ảnh thô), và dấu hiệu gì cho biết nó theo protocol này.
  2. Trạng thái máy lúc vào: CPU ở chế độ nào, paging bật chưa, kernel ở địa chỉ nào, stack ra sao, ngắt bật hay tắt.
  3. Đường giao thông tin: memory map, framebuffer, ACPI, dòng lệnh, module (initrd) được đưa tới đâu.
  4. Cách kernel xin tính năng: muốn framebuffer, muốn paging 5 cấp, muốn khởi động các CPU phụ thì nói bằng cách nào.
  5. Phiên bản: protocol đổi theo thời gian; hai bên phải biết bên kia hiểu tới đâu.

Còn một đường nữa là không dùng protocol nào: kernel tự là một ứng dụng UEFI (file PE), firmware chạy thẳng nó và giao EFI_SYSTEM_TABLE. Xem Limine và loader tự viết.

Limine: request và response

Kernel gửi phiếu yêu cầu dán nhãn; Limine tìm nhãn và điền câu trả lời.

Kernel để sẵn "phong bì có nhãn" (struct request, nhãn là dãy magic) trong file nhị phân; Limine quét tìm nhãn rồi điền con trỏ response trước khi nhảy vào kernel. Không có request thì không có response, và Limine không làm tính năng đó. Chi tiết: Request-Response Mechanism.

Các request hay dùng: paging_mode (chọn 4 hay 5 cấp), hhdm (offset của direct map), executable_address (địa chỉ thật của kernel), memmap, framebuffer, rsdp (bảng ACPI), smp (các CPU phụ), module (file nạp kèm), executable_cmdline.

Base revision: bắt tay phiên bản

Kernel nói nó hiểu phiên bản giao thức nào; Limine trả lời có đáp ứng được hay không.

c
#define LIMINE_BASE_REVISION(N) \
    uint64_t limine_base_revision[3] = { 0xf9562b2d5c95a6c8, 0x6a7b384944536bdc, (N) };
#define LIMINE_BASE_REVISION_SUPPORTED (limine_base_revision[2] == 0)

Kernel khai {magic1, magic2, N}. Nếu Limine hỗ trợ revision N, nó ghi phần tử thứ 3 thành 0. Kernel kiểm ngay ở dòng đầu:

c
static volatile LIMINE_BASE_REVISION(N);

void kernel_entry(void) {
    if (!LIMINE_BASE_REVISION_SUPPORTED)
        halt();                 // the loader is too old for what this kernel expects
    ...

Mỗi revision đổi vài lời hứa, nên đọc mục "Base Revision Changes" trước khi chọn N. Ví dụ revision 5 hứa thêm IDTR, LDTR, TR rỗng và mọi bit khác của CR0/CR4/EFER bằng 0; revision thấp hơn không hứa.

Limine làm gì trước khi vào kernel

Lúc vào kernel, CPU đã ở 64 bit, paging đã bật, kernel đã ở nửa cao.

Những gì Limine không hứa thì kernel phải tự lo: IDT (trạng thái không xác định), GDT và TSS của riêng mình, bảng trang của riêng mình nếu muốn đổi quyền.

Bootloader không làm gì (dễ hiểu nhầm)

Bootloader là người đưa thư: nó đọc lại thông tin firmware đã có, không tự cấu hình phần cứng.

Các vùng FRAMEBUFFER/RESERVED/MMIO thấy trong memory map là di sản của firmware, có trước khi bootloader chạy. Triết lý chung của bootloader: làm ít nhất có thể, chỉ đủ để kernel tự chủ. Mọi việc điều khiển thiết bị là của kernel.

Tóm tắt một câu

Kernel đặt hàng, bootloader giao hàng trước khi nhảy vào kernel.

Boot protocol nói kernel phải trông thế nào, máy ở trạng thái nào lúc vào, và thông tin giao qua đâu. Với Limine, kernel "đặt hàng" qua struct request; Limine "giao hàng" bằng cách điền response, đồng thời đặt CPU vào long mode + paging + nửa cao.
