KASLR & PIE Kernel

Tags concept, boot, security

Kernel cavOS là ELF64 PIE (Position-Independent Executable) → Limine có thể nạp nó ở địa chỉ vật lý/ảo ngẫu nhiên (KASLR) rồi tự sửa (relocate) các con trỏ.

Đo thật trên bản build hiện tại: file kernel mang kiểu ET_EXEC, nên Limine 10.8.5 (binary cavOS thật sự boot) coi nó là không relocatable và tắt KASLR, dù limine.conf ghi kaslr: yes. Chi tiết ở mục bên dưới.

PIE là gì?

Một chương trình chạy đúng dù bị đặt ở địa chỉ nào, miễn loader sửa giúp vài con trỏ.

Mã không phụ thuộc địa chỉ nạp cố định. Các tham chiếu tuyệt đối được liệt kê trong bảng relocation, và section .dynamic chỉ cho loader biết bảng đó nằm đâu. Khi nạp ở base mới, loader cộng "slide" vào từng mục.

Code PIE có hai loại tham chiếu:

  • Tương đối — code gọi hàm hay đọc biến bằng độ lệch so với RIP (lea x(%rip)). Cả khối dời đi thì độ lệch không đổi → không cần sửa gì. Đây là phần lớn code cavOS, xem phần so sánh -fPIE ở Higher-Half Kernel.
  • Tuyệt đối — một con trỏ được lưu trong bộ nhớ: bảng con trỏ hàm, mảng con trỏ chuỗi, biến global khởi tạo bằng &x. Giá trị 64-bit đó được ghi lúc link, nên phải sửa khi kernel bị dời. Mỗi chỗ như vậy là một relocation.

"Slide" là khoảng dời: địa chỉ nạp thật trừ địa chỉ lúc link. Với loại relocation duy nhất cavOS có, R_X86_64_RELATIVE, Limine (common/lib/elf.c, hàm elf64_apply_relocations) làm đúng một phép gán:

c
*ptr = slide + relocation->r_addend;

r_addend là giá trị con trỏ lúc link. Ví dụ mục đầu tiên trong bảng của cavOS: offset ffffffff800acb50 (nằm trong .data), addend -7fffe8ef = 0xffffffff80001711, tức là một địa chỉ trong .text. Slide = 0 thì giá trị giữ nguyên.

Trong link.ld

Linker script dành riêng một segment cho thông tin relocation, và Makefile bật PIE.

ld
PHDRS { ... dynamic PT_DYNAMIC FLAGS(...); }
.dynamic : { *(.dynamic) } :data :dynamic

PT_DYNAMIC cho Limine biết chỗ chứa relocation (kiểu phổ biến: R_X86_64_RELATIVE).

Cờ build trong src/kernel/Makefile: compile với -fPIE, link với

make
LDFLAGS = -m elf_x86_64 \
		-nostdlib \
    -static \
    -pie \
    --no-dynamic-linker \
    -z text \
    -z max-page-size=0x1000 -T link.ld

-static -pie --no-dynamic-linker = "static PIE": không cần thư viện động, nhưng vẫn giữ bảng relocation để ai nạp thì tự sửa. -z text bắt linker báo lỗi nếu có relocation nào phải sửa trong section chỉ đọc (như .text) — chỉ dữ liệu được sửa.

Kết quả trên ~/cavOS/target/boot/kernel.bin (bản build 2ba0edb), readelf -dW:

text
 0x0000000000000007 (RELA)               0xffffffff800a05a8
 0x0000000000000008 (RELASZ)             46416 (bytes)
 0x0000000000000009 (RELAENT)            24 (bytes)
 0x000000006ffffffb (FLAGS_1)            Flags: PIE
 0x000000006ffffff9 (RELACOUNT)          1934

Và readelf -rW đếm theo loại:

text
Relocation section '.rela.dyn' at offset 0xa05a8 contains 1934 entries:
   1934 R_X86_64_RELATIVE

1934 mục × 24 byte = 46416 byte, khớp RELASZ. Tất cả đều là RELATIVE: không có symbol nào phải tra, chỉ cộng slide.

KASLR = Kernel Address Space Layout Randomization

Mỗi lần boot đặt kernel ở chỗ khác, để kẻ tấn công không biết trước địa chỉ của nó.

Nạp kernel ở base ngẫu nhiên mỗi lần boot → khó khai thác lỗ hổng. Vì base đổi, kernel cần biết base thực qua request kernel_address của Limine:

c
bootloader.kernelVirtBase = limineKrnres->virtual_base;
bootloader.kernelPhysBase = limineKrnres->physical_base;

Hai dòng này nằm trong initialiseBootloaderParser() (entry/bootloader.c), sau request:

c
static volatile struct limine_kernel_address_request limineKrnreq = {
    .id = LIMINE_KERNEL_ADDRESS_REQUEST, .revision = 0};

Trong PROTOCOL.md hiện hành (bản Limine 10.8.5 ghim, repo limine-protocol) tính năng này tên là "Executable Address Feature" (limine_executable_address_request), nhưng ID request giữ nguyên (0x71ba76863cc55f63, 0xb2644a48c516a487 trong cả limine.h của cavOS lẫn limine.h của limine-protocol). Xem cách cavOS đọc mọi response ở Bài 3 - Bootloader Parser.

Limine 10.8.5 ngẫu nhiên hoá hai thứ (đọc trong source Limine):

Cái gìCách chọnSố vị trí
Base ảo của kernelelf.c: slide = rand32() & ~(max_align - 1), thử lại tới khi kernel còn nằm gọn trên 0xffffffff80000000bước 4 KiB (align của cavOS) trong 2 GiB → tối đa khoảng 219
Base HHDMprotos/limine.c, set_paging_mode(): cộng một số ngẫu nhiên bước 1 GiB, trong một phần tư nửa caokhoảng 215 với 4-level

Từ Limine 10.0.0, KASLR mặc định tắt: protos/limine.c chỉ bật khi limine.conf ghi đúng kaslr: yes (Limine 8.x thì ngược lại: mặc định bật, chỉ tắt khi ghi no). Base HHDM được ngẫu nhiên khi randomise_hhdm_base bật; theo CONFIG.md, mặc định nó bật nếu KASLR được hỗ trợ và đang bật. Đó là lý do comment trong bootloader.c ghi "HHDM (randomized kernel positionings)": cavOS đọc offset từ Limine chứ không hard-code. Địa chỉ vật lý của kernel thì elf.c chỉ xin một vùng nhớ (ext_mem_alloc_type_aligned), không gọi hàm ngẫu nhiên nào.

Liên quan: Higher-Half Kernel, Bài 1 - Boot & Limine, Bài 3 - Bootloader Parser.

KASLR có chạy với cavOS không?

Không. Cấu hình xin KASLR, nhưng file kernel không qua được phép kiểm tra của Limine.

target/boot/limine/limine.conf ghi (comment "Disable … enabled by default" là chép từ mẫu cũ, đúng với Limine 8.x; với Limine 10.8.5 thì chính dòng yes này mới bật KASLR):

text
    # Disable KASLR (it is enabled by default for relocatable kernels)
    kaslr: yes

Nhưng Limine chỉ ngẫu nhiên hoá kernel relocatable, và hàm quyết định điều đó (elf64_is_relocatable trong common/lib/elf.c) trả false ngay nếu kiểu ELF không phải ET_DYN. Rồi protos/limine.c làm kaslr = kaslr && is_reloc;, nên HHDM cũng không bị ngẫu nhiên. Kernel cavOS lại là:

text
$ readelf -h ~/cavOS/target/boot/kernel.bin
  Type:                              EXEC (Executable file)
  Entry point address:               0xffffffff8002a548

Dù có FLAGS_1: PIE và đủ 1934 relocation, file vẫn là EXEC. Thử link lại cùng file .o với cùng cờ, chỉ đổi . = 0xffffffff80000000; thành . = 0; trong một bản sao của link.ld (ra file tạm, không đụng cavOS):

text
  Type:                              DYN (Position-Independent Executable file)
  Entry point address:               0x2a548

Vậy GNU ld 2.38 của cavOS ghi PIE thành EXEC khi link ở base khác 0 (ld 2.46 của Ubuntu cũng cho EXEC với link.ld gốc). PROTOCOL.md đã tính đến cách link ở 0: "For relocatable executables asking to be loaded at address 0, a minimum slide of 0xffffffff80000000 is applied". Bản kernel link ở 0 này chưa được boot thử.

Kiểm chứng bằng hai lần boot thật (QEMU, KVM, -snapshot, monitor info mem và gva2gpa 0xffffffff80000000):

Base vật lý kernel0xbfbbf0000xbfbbf000

Hai lần giống hệt nhau, đúng như source Limine dự đoán. Muốn tự lặp lại: boot QEMU với -monitor unix:/tmp/cavmon.sock,server,nowait, đợi cavOS boot xong, gửi info mem và so dòng bắt đầu bằng ffffffff8 giữa các lần.

KASLR bảo vệ gì, và giới hạn

KASLR không vá lỗi nào; nó chỉ bắt kẻ tấn công phải biết thêm một bí mật.

Nhiều kiểu khai thác kernel cần biết trước địa chỉ: nhảy tới một hàm có sẵn, ghép các mẩu code (ROP), hay ghi đè một biến global đã biết. Nếu địa chỉ đổi mỗi lần boot, khai thác phải đoán, và đoán sai thường làm kernel crash thay vì bị chiếm. Giới hạn:

  • Rò rỉ thông tin (info leak). Chỉ cần lộ một con trỏ kernel là biết slide, vì cả ảnh kernel dời cùng một khoảng. cavOS in nhiều địa chỉ ra serial và màn hình, ví dụ fb{ffff8000fd000000} lộ luôn base HHDM.
  • Kênh kề (side channel). Đo thời gian truy cập, TLB hay prefetch có thể cho biết trang nào đang được map, kể cả từ user mode. Các lỗ kiểu Meltdown đọc được thẳng bộ nhớ kernel.
  • Ít entropy. Tối đa khoảng 219 vị trí trong 2 GiB. Mỗi lần đoán sai thường chỉ làm crash một lần boot, nhưng con số này nhỏ so với địa chỉ 64-bit.
  • Dễ tắt mà không ai biết. Như mục trên: cấu hình bật mà kernel không đủ điều kiện thì không có gì báo lỗi, chỉ đo mới biết.
