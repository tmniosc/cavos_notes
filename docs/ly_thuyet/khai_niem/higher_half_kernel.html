Higher-Half Kernel

Tags concept, memory

Kernel được nạp ở nửa cao của không gian địa chỉ ảo. cavOS: 0xffffffff80000000 (xem link.ld).

Vì sao nửa cao?

Chia đôi không gian địa chỉ: nửa dưới cho chương trình người dùng, nửa trên cho kernel.

  • Không gian ảo x86_64 (4-level) là 48-bit có dấu, sign-extend lên 64-bit → địa chỉ hợp lệ ("canonical") chỉ ở 2 đầu: nửa thấp 0x0..00–0x0000_7fff_ffff_ffff và nửa cao 0xffff_8000_..–0xffff_ffff_... Khoảng giữa là "lỗ" không dùng được. → xem Long Mode.
  • Quy ước: kernel ở nửa cao, userspace ở nửa thấp → mỗi tiến trình dùng chung mapping kernel, tách bạch rõ ràng, dễ bảo vệ.

"Sign-extend" nghĩa là: bit 63..48 phải chép y hệt bit 47. Bit 47 = 0 cho nửa thấp, bit 47 = 1 cho nửa cao. Mỗi nửa rộng 128 TiB. Dùng địa chỉ nằm trong lỗ thì CPU báo lỗi #GP ngay, không cần tra bảng trang.

Ba lợi ích cụ thể của việc đặt kernel ở nửa cao:

  • Một nửa trên dùng chung. Mỗi tiến trình có bảng trang riêng (CR3 riêng). Chỉ cần chép các entry PML4 của nửa cao (entry 256–511) sang bảng mới là tiến trình nào cũng thấy kernel ở cùng địa chỉ. Khi có syscall hay ngắt, không phải đổi CR3.
  • Nửa dưới để trọn cho user. Chương trình user có thể link ở địa chỉ thấp quen thuộc mà không đụng kernel.
  • Dễ kiểm tra con trỏ. Con trỏ user đưa vào syscall mà có bit 63 = 1 là chắc chắn trỏ vào kernel → từ chối được bằng một phép so sánh.

Với cavOS còn một lý do đơn giản hơn: Limine bắt buộc. Mục "Memory Layout at Entry" của PROTOCOL.md (bản Limine 10.8.5 dùng — binary cavOS thật sự boot) viết kernel phải nạp ở hoặc trên 0xffffffff80000000 và "Lower half executables are not supported".

Vì sao đúng 0xffffffff80000000 (= −2GiB)?

Lý do gốc là code model của GCC; với cavOS thì lý do thật là luật của Limine.

0xffffffff80000000 là −2 GiB nếu đọc như số có dấu: chỉ còn 2 GiB tới đỉnh không gian địa chỉ. Đây là chỗ duy nhất ở nửa cao mà một số 32-bit có dấu, khi sign-extend lên 64-bit, trỏ tới được.

GCC có -mcmodel=kernel dựa đúng vào điều đó. Mọi địa chỉ tuyệt đối của biến/hàm được nhúng thẳng vào lệnh dưới dạng số 32-bit có dấu (relocation R_X86_64_32S) → lệnh ngắn và nhanh hơn, nhưng kernel bắt buộc nằm trong 2 GiB cuối. Đó là lý do Linux và hầu hết hobby kernel chọn địa chỉ này.

cavOS không dùng -mcmodel=kernel. src/kernel/Makefile build với -fPIE và link với -pie. Hai thứ này còn không đi cùng được — thử với cross compiler của cavOS:

text
$ x86_64-cavos-gcc -ffreestanding -c -O2 -fPIE -mcmodel=kernel t.c
cc1: error: code model kernel does not support PIC mode

So sánh cùng một hàm int g(long i){ return a[i]; } ở hai chế độ (objdump + readelf thật):

text
### -fno-pic -mcmodel=kernel
   0:	mov    0x0(,%rdi,4),%eax          ; địa chỉ a nhúng thẳng, 32-bit có dấu
0000000000000003  ...  R_X86_64_32S    a + 0
### -fPIE
   0:	lea    0x0(%rip),%rax             ; địa chỉ a = RIP + độ lệch
   7:	mov    (%rax,%rdi,4),%eax
0000000000000003  ...  R_X86_64_PC32   a - 4

Với -fPIE, code tham chiếu dữ liệu bằng độ lệch so với RIP (thanh ghi con trỏ lệnh). Điều kiện duy nhất là code và dữ liệu cách nhau không quá ±2 GiB — kernel cavOS chỉ khoảng 1 MiB nên luôn thoả, đặt ở đâu cũng được. Đếm relocation trong phần .text của entry/kernel.o chỉ thấy loại tương đối: R_X86_64_PC32 (14), R_X86_64_PLT32 (38), R_X86_64_REX_GOTPCRELX (4). Vậy với cavOS, địa chỉ −2 GiB không phải do compiler đòi, mà do Limine đòi (và do link.ld chép theo mẫu của Limine).

Trong code (link.ld)

link.ld đặt địa chỉ bắt đầu và chia kernel thành 3 segment có quyền khác nhau.

ld
. = 0xffffffff80000000;
kernel_start = .;
.text : { *(.text .text.*) } :text

Phần còn lại của src/kernel/link.ld làm ba việc:

  • PHDRS khai 3 segment text (R+X), rodata (R), data (R+W) và 1 segment dynamic. Limine đọc cờ của từng segment để map trang với quyền tương ứng. Segment dynamic chứa thông tin relocation → xem KASLR & PIE Kernel.
  • Giữa các section có . += CONSTANT(MAXPAGESIZE); để mỗi segment bắt đầu ở trang 4 KiB mới. Hai segment khác quyền không bao giờ chung một trang.
  • Các symbol kernel_start, kernel_text_start/end, kernel_rodata_start/end, kernel_data_start/end, kernel_end được khai extern trong include/bootloader.h để C biết ranh giới từng phần. nm trên bản build: kernel_start = ffffffff80000000, _start = ffffffff8002a548, kernel_end = ffffffff80101378.

Liên quan: HHDM (cũng ở nửa cao, vùng khác), KASLR & PIE Kernel, Bài 1 - Boot & Limine.

Kernel mapping vs HHDM

Cùng một byte của kernel có hai địa chỉ ảo: một để chạy, một để đọc/ghi như dữ liệu.

Limine tạo hai vùng ở nửa cao, và kernel cần biết cả hai. entry/bootloader.c, hàm initialiseBootloaderParser(), lưu chúng vào struct bootloader (đọc kỹ ở Bài 3 - Bootloader Parser):

c
  // HHDM (randomized kernel positionings)
  struct limine_hhdm_response *limineHHDMres = limineHHDMreq.response;
  bootloader.hhdmOffset = limineHHDMres->offset;

  // Kernel address
  struct limine_kernel_address_response *limineKrnres = limineKrnreq.response;
  bootloader.kernelVirtBase = limineKrnres->virtual_base;
  bootloader.kernelPhysBase = limineKrnres->physical_base;

Vì HHDM phủ mọi RAM, khung vật lý của kernel cũng hiện ra lần nữa trong HHDM: 0xffff800000000000 + 0xbfbbf000 = 0xffff8000bfbbf000. Hai địa chỉ ảo, một khung vật lý — đó là aliasing, giải thích kỹ ở HHDM.

cavOS dùng cả hai vùng làm "vùng cấm" trong cpu/system.c, hàm isProtectedMemory(). Vùng kernel được coi là 256 MiB (268435456) tính từ kernelVirtBase, rộng hơn nhiều so với 1 MiB thật:

c
bool isProtectedMemory(uint64_t virt) {
  if (virt > bootloader.hhdmOffset &&
      virt < (bootloader.hhdmOffset + bootloader.mmTotal))
    return true;
  else if (virt > bootloader.kernelVirtBase &&
           virt < bootloader.kernelVirtBase + 268435456) {
    return true;
  }

  return false;
}

Khi cavOS tự quản bảng trang (Bài 6 - Virtual Memory & Paging), nó dùng lại bảng của Limine, nên hai vùng này giữ nguyên địa chỉ suốt quá trình chạy.
