Request-Response Mechanism

Tags concept, boot

Một cách để kernel xin thông tin từ bootloader: kernel đặt sẵn các struct "yêu cầu" có nhãn trong file nhị phân của mình, bootloader tìm các nhãn đó và điền câu trả lời vào trước khi nhảy vào kernel. Limine dùng cách này; Multiboot dùng một nửa của nó. Xem Boot Protocol & Limine.

Ẩn dụ

Phong bì có nhãn trong file kernel, bootloader tìm nhãn và nhét câu trả lời vào.

Kernel để sẵn các "phong bì có nhãn" trong file nhị phân ("tôi muốn biết X"). Nhãn là một dãy số magic 64-bit, gần như không thể trùng tình cờ. Bootloader quét nhị phân kernel, tìm nhãn, rồi nhét "tờ trả lời" (response) vào phong bì. Kernel chạy thì mở ra đọc.

Ví dụ: yêu cầu direct map trong limine.h

Một nhãn bốn số và một con trỏ chờ được điền.

c
#define LIMINE_COMMON_MAGIC 0xc7b1dd30df4c8b88, 0x0a82e883a194f07b
#define LIMINE_HHDM_REQUEST { LIMINE_COMMON_MAGIC, 0x48dcf1cb8ad2b852, 0x63984e959a98244b }

struct limine_hhdm_request {
    uint64_t id[4];        // the label: 2 common magics + 2 for this feature
    uint64_t revision;
    struct limine_hhdm_response *response;  // NULL in the file; the loader fills it in
};
struct limine_hhdm_response { uint64_t revision; uint64_t offset; };

Phía kernel:

c
__attribute__((used, section(".limine_requests")))
static volatile struct limine_hhdm_request hhdm_req = {
    .id = LIMINE_HHDM_REQUEST, .revision = 0 };     // response is still NULL here

void kernel_entry(void) {
    if (hhdm_req.response == NULL)                  // the loader did not (or could not) answer
        halt();
    uint64_t hhdm_offset = hhdm_req.response->offset;
    ...

Dòng thời gian

Ba thời điểm: lúc biên dịch, lúc bootloader nạp, lúc kernel chạy.

text
build time : the request (id = magic, response = NULL) sits in the kernel binary
load time  : the loader finds the magic, builds the response, stores its address in request.response
run time   : request.response points to real data; the kernel reads it

Vì sao static volatile, used và section riêng

Mấy từ khoá giữ cho phong bì còn trong file, tìm được, và câu trả lời được đọc thật.

  • volatile: báo compiler biến bị bên ngoài (bootloader) sửa. Không có nó, compiler thấy response luôn bằng NULL lúc build và có thể bỏ luôn code đọc nó.
  • static + __attribute__((used)): biến phải nằm trong file dù không ai trong C nhắc tới nó; với -ffunction-sections / --gc-sections linker sẽ xoá biến "không dùng" nếu thiếu used.
  • Section riêng (vd .limine_requests, kẹp giữa hai marker LIMINE_REQUESTS_START_MARKER / END_MARKER): cho bootloader biết chỗ để quét, khỏi quét cả file, và giữ request ở vùng ghi được (response phải ghi vào được).

Cùng cơ chế này dùng cho base revision: ở đó bootloader "trả lời" bằng cách ghi 0 vào phần tử thứ ba.

So với cách khác

Câu hỏi luôn nằm trong file kernel; khác nhau ở chỗ câu trả lời được giao tới đâu.

ProtocolKernel hỏi bằngBootloader trả lời bằng
Liminecác struct request rải trong fileghi con trỏ vào chính từng request
Multiboot2các tag trong một header ở đầu filemột khối thông tin chung, địa chỉ trong EBX
Linux boot protocoltrường trong setup headerstruct boot_params, địa chỉ trong RSI

Cách của Limine có một điểm tiện: mỗi tính năng là một struct độc lập, kernel chỉ khai cái mình cần, và đọc câu trả lời qua biến của chính mình, không phải lần theo một khối thông tin chung.
