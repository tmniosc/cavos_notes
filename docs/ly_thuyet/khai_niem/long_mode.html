Long Mode (64-bit)

Tags concept, cpu

Chế độ hoạt động 64-bit của CPU x86_64. Khi Limine nhảy vào _start, CPU đã ở long mode và paging đã bật — kernel không phải tự chuyển chế độ.

Các chế độ x86 (lịch sử)

CPU x86 nào cũng thức dậy ở chế độ 16-bit cũ, rồi phải leo từng nấc lên 64-bit.

Gỡ rối đầy đủ "segment + 3 chế độ": x86 Segmentation.

Vì phải chạy được phần mềm của 40 năm trước, CPU x86_64 vẫn giữ cả ba chế độ. Mỗi chế độ là một "luật chơi" khác nhau cho địa chỉ và thanh ghi:

  • Real mode (16-bit): chế độ lúc bật nguồn. Địa chỉ = segment × 16 + offset, chỉ với tới khoảng 1 MiB. Không có bảo vệ bộ nhớ.
  • Protected mode (32-bit): có GDT, có privilege level (ring 0–3), paging là tuỳ chọn. Với tới 4 GiB.
  • Long mode — Intel gọi là IA-32e mode. Nó có hai chế độ con (submode):
    • 64-bit mode: thanh ghi 64-bit, địa chỉ ảo 64-bit. Kernel cavOS chạy ở đây.
    • Compatibility mode: vẫn trong long mode (paging 4-level vẫn chạy), nhưng code 32-bit cũ chạy được như ở protected mode. Dùng cho chương trình 32-bit trên OS 64-bit.

Chế độ con nào đang chạy do bit L của code segment hiện tại (CS) quyết định: L = 1 là 64-bit mode, L = 0 là compatibility mode. Vì thế mỗi lần nạp CS là một lần có thể đổi chế độ con.

Bình thường bootloader phải đi qua từng nấc (bật A20, dựng GDT, bật PAE, set EFER.LME, bật paging, set CR0.PG...). Limine làm hết → cavOS bỏ qua phần asm phức tạp này.

Bit/MSR liên quan (để tra khi cần)

Một nhóm nhỏ bit trong CR0, CR4, EFER và CS quyết định CPU đang ở chế độ nào.

CR0, CR4 là control register, đọc/ghi bằng mov. EFER (Extended Feature Enable Register) là một MSR (model-specific register) số 0xC0000080, đọc/ghi bằng rdmsr/wrmsr.

BitVị tríÝ nghĩaAi bật cho cavOS
CR0.PEbit 0Protection Enable — rời real mode, vào protected modeLimine
CR0.WPbit 16Write Protect — ring 0 cũng không ghi được trang read-onlyLimine
CR0.PGbit 31Paging. Bật khi LME = 1 thì CPU vào long modeLimine
CR4.PAEbit 5Physical Address Extension — entry bảng trang 64-bit. Bắt buộc trước khi vào long modeLimine
CR4.LA57bit 12Paging 5-level. cavOS xin 4-level nên bit này = 0không bật
EFER.SCEbit 0cho phép lệnh syscall/sysretcavOS, cpu/fastSyscall.c (Bài 16)
EFER.LMEbit 8Long Mode Enable — "xin" vào long modeLimine
EFER.LMAbit 10Long Mode Active — chỉ đọc; CPU tự set khi LME = 1 và PG = 1CPU
EFER.NXEbit 11cho phép bit NX (không thực thi) trong entry bảng trangLimine (nếu CPU có)

Thứ tự trong bảng không tuỳ ý. Intel SDM yêu cầu: bật PAE và nạp CR3 trước, set LME, rồi mới bật PG. Bật PG khi PAE = 0 mà LME = 1 sẽ gây #GP.

Ai chuyển chế độ cho cavOS?

Limine. Nó hứa trạng thái máy cụ thể lúc vào _start, và cavOS dựa hẳn vào lời hứa đó.

Binary Limine mà cavOS thật sự boot là Limine 10.8.5 (src/bootloader/limine/BOOTX64.EFI tự báo như vậy; assert.sh ghim "10.1.1" nhưng clone đầu nhánh v10.x-binary). Từ Limine 9, spec của protocol nằm ở repo riêng limine-protocol; Limine 10.8.5 ghim commit e42d010 của PROTOCOL.md. Mục "Machine State at Entry → x86-64" ở đó viết:

text
PE is enabled (cr0), ET is enabled (cr0), WP is enabled (cr0), PG is enabled (cr0),
PAE is enabled (cr4), LME and LMA are enabled (EFER). NX is enabled (EFER)
(if it is available).

Cùng mục đó còn hứa thêm:

  • Mọi segment register đã nạp segment 64-bit; GDTR trỏ tới một GDT của Limine (null, code/data 16-bit, 32-bit, 64-bit).
  • IDT ở trạng thái không xác định — kernel phải tự nạp IDT của mình.
  • Cờ IF (ngắt), VM, DF bị xoá. A20 đã mở. PIC cũ bị mask hết; ở IO APIC, các entry có delivery mode Fixed hoặc Lowest Priority bị mask.
  • rsp trỏ tới đỉnh một stack ít nhất 64 KiB; các thanh ghi đa dụng khác bằng 0.

Base revision 5 hứa thêm (IDTR, LDTR, TR rỗng; mọi bit khác của CR0/CR4/EFER bằng 0; Local APIC ở trạng thái xác định; IOMMU bị tắt). cavOS xin base revision 2 nên không được hứa những điều đó.

Hệ quả cho code cavOS: _start (entry/kernel.c) là một hàm C bình thường. Không có mov cr0, không có wrmsr EFER, không có far jump nào trước nó. Dòng đầu tiên chỉ kiểm tra Limine có hiểu base revision mà kernel yêu cầu không:

c
static volatile LIMINE_BASE_REVISION(2);
void _start(void) {
  systemDiskInit = false;

  if (LIMINE_BASE_REVISION_SUPPORTED == false)
    panic();

  initiateSerial();
  initialiseBootloaderParser();

Toàn bộ đường từ _start đọc ở Bài 1 - Boot & Limine. Về sau cavOS chỉ thêm bit, không đổi chế độ: EFER.SCE cho syscall, và mấy bit CR0/CR4 cho FPU/SSE (cpu/system.c, cpu/sse.asm).

Đọc thanh ghi CPU 0 (BSP — bootstrap processor, CPU chạy _start) bằng QEMU monitor info registers khi cavOS đã boot xong (máy 2, KVM, -smp 2):

text
RIP=ffffffff8008e368 RFL=00000046 [---Z-P-] CPL=0 II=0 A20=1 SMM=0 HLT=0
CS =0028 0000000000000000 00000000 00209b00 DPL=0 CS64 [-RA]
CR0=80010033 CR2=00005ffffffff000 CR3=000000000212b000 CR4=00000620
EFER=0000000000000d01
  • EFER=0xd01 = SCE (bit 0) + LME (bit 8) + LMA (bit 10) + NXE (bit 11).
  • CR0=0x80010033 = PG + WP + PE, cộng MP/ET/NE cho FPU.
  • CR4=0x620 = PAE (bit 5) + OSFXSR/OSXMMEXCPT (bit 9, 10) cho SSE. LA57 = 0 → 4-level.
  • Thuộc tính CS 00209b00 có bit 21 của dword cao (= bit 53 của descriptor) bằng 1 → L = 1. QEMU ghi luôn là CS64.

Đặc điểm long mode (liên quan code cavOS)

Bốn điều của long mode mà bạn sẽ gặp lại trong code cavOS.

  • Địa chỉ ảo canonical 48-bit sign-extended → xem Higher-Half Kernel.
  • Paging luôn bật, dùng PAE 4-level (PML4) hoặc 5-level → xem Bài 6 - Virtual Memory & Paging. Tắt PG nghĩa là rời long mode, nên kernel không bao giờ làm vậy.
  • Segmentation gần như "phẳng": base/limit bị bỏ qua cho hầu hết segment → ảnh hưởng Bài 7 - GDT & TSS. GDT vẫn cần, vì CS mang bit L và mức đặc quyền (CPL).
  • Thanh ghi 64-bit (RAX...R15); calling convention theo x86-64 psABI.

CPU phụ (AP) leo thang thế nào?

cavOS không có trampoline riêng: Limine tự đưa từng CPU phụ lên long mode rồi cho nó ngồi chờ.

Máy nhiều nhân có một BSP và các AP (application processor). Mỗi AP thức dậy bằng tín hiệu INIT-SIPI và bắt đầu ở real mode, giống lúc bật máy. Vì vậy ai khởi động AP thì phải có một đoạn code "trampoline" leo lại cả cái thang ở trên cho AP đó.

Trong cavOS không có đoạn đó. Grep trampoline, goto_address trong ~/cavOS/src/kernel không ra code nào; entry/bootloader.c chỉ gửi limine_smp_request và lưu kết quả. Theo PROTOCOL.md, chỉ cần request này có mặt là Limine sẽ tự bootstrap các AP. Trampoline nằm trong Limine (common/sys/smp_trampoline.asm_x86, bản 10.8.5), và leo đúng thứ tự trong sơ đồ:

BướcLệnh trong trampolineKết quả
1lidt (IDT rỗng), lgdt, mov cr0, 0x11, far jmp selector 0x18PE = 1 (và ET), nhảy vào code 32-bit → protected mode
2xoá CR4, ghi MSR PAT (0x277) nếu CPU có PAT, chép MSR APIC base (0x1b) của BSPAP bắt đầu từ trạng thái sạch, cùng kiểu APIC với BSP
3bts bit 5 của CR4PAE = 1
4wrmsr MSR 0xc0000080 = 0x100, thêm bit 11 nếu CPU có NXEFER.LME = 1 (và NXE)
5mov cr3; CR0 set bit 16 (nếu được yêu cầu) và bit 31WP = 1, PG = 1 → CPU set LMA (compatibility mode)
6push 0x28, retfCS = code 64-bit (L = 1) → 64-bit mode
7nạp segment 0x30, lgdt lại bằng địa chỉ HHDM, ltr 0x38, nhảy tới parking64 qua HHDMAP chạy ở nửa cao, có TSS của Limine

Sau đó AP đứng chờ trong vòng lặp "parking" của Limine (dùng monitor/mwait nếu CPU có, không thì vòng pause). Nó chỉ chạy tiếp khi kernel ghi một địa chỉ hàm vào trường goto_address của nó; lúc đó Limine đổi sang stack của AP và iretq vào hàm đó. cavOS không bao giờ ghi trường này, và cpu/apic.c còn để for (size_t i = 0; i < 1; i++) { // todo: bootloader.smp->cpu_count. Kết quả: cavOS chỉ chạy trên BSP; các AP đã ở long mode nhưng ngồi yên.

Đo thật cùng lần boot ở trên, chuyển monitor sang CPU 1 (cpu 1, info registers):

text
RIP=ffff8000000601ac RFL=00000046 [---Z-P-] CPL=0 II=0 A20=1 SMM=0 HLT=0
CS =0028 0000000000000000 00000000 00209b00 DPL=0 CS64 [-RA]
CR0=80010011 CR2=0000000000000000 CR3=00000000bff8a000 CR4=00000020
EFER=0000000000000d00
  • AP cũng ở 64-bit mode (CS64, EFER=0xd00 = LME + LMA + NXE).
  • Không có SCE, CR4 chỉ có PAE: đúng những gì trampoline của Limine bật, không có bit nào của cavOS.
  • RIP nằm trong HHDM (0xffff8000…): AP đang chạy vòng lặp parking ở vùng nhớ thấp, gọi qua HHDM.
