ESP và cách UEFI tìm Limine

Tags concept, boot, uefi, disk

Firmware UEFI không biết kernel là gì. Nó chỉ biết chạy một file .efi nằm trên một phân vùng FAT: hoặc file được ghi sẵn trong biến NVRAM Boot####, hoặc file ở đường dẫn dự phòng \EFI\BOOT\BOOTX64.EFI. Với cavOS, file đó là Limine; Limine tự đọc limine.conf và kernel.bin rồi mới nhảy vào kernel. Bố cục ảnh đĩa nói chung: Cấu trúc os.img; phần Limine giao cho kernel: Limine Protocol.

GPT và EFI System Partition

ESP là "ngăn kéo dành riêng cho firmware": một phân vùng FAT có đánh dấu đặc biệt để firmware biết chỗ tìm bootloader.

  • GPT (GUID Partition Table) là bảng phân vùng chuẩn của UEFI. Header nằm ở LBA 1 với chữ ký EFI PART, có bản sao ở cuối đĩa. Mỗi phân vùng có một type GUID (loại) và một GUID riêng. Sector 0 vẫn chứa một MBR "bảo vệ" (protective MBR, type 0xEE) để công cụ cũ không ghi đè.
  • ESP (EFI System Partition) là phân vùng có type GUID C12A7328-F81F-11D2-BA4B-00A0C93EC93B, định dạng FAT (thường FAT32). Trên đĩa MBR, spec gọi ESP là phân vùng có OS type 0xEF.
  • Firmware có sẵn driver FAT, nên nó đọc được file trên ESP mà không cần hệ điều hành nào.

BootOrder, Boot#### và đường dẫn dự phòng

Firmware có một danh sách "thử boot cái gì trước" lưu trong NVRAM; nếu mục trong danh sách chỉ trỏ tới cả ổ đĩa thì nó tự đi tìm file theo tên quy ước.

  • Boot#### (#### là 4 chữ số hex) là một biến UEFI chứa một EFI_LOAD_OPTION: cờ thuộc tính, tên hiển thị, và một device path (đường dẫn thiết bị: PCI → SATA → phân vùng → file).
  • BootOrder là mảng số 16-bit, liệt kê thứ tự thử các Boot####.
  • Khi device path chỉ tới thiết bị chứ không tới file (đĩa rời, đĩa mới cắm), boot manager tìm \EFI\BOOT\BOOT{arch}.EFI trên phân vùng FAT của thiết bị đó. Với x86-64 là BOOTX64.EFI. Đây là removable media boot path, thường gọi là fallback path.

Cài OS thật thì installer gọi SetVariable để thêm một Boot#### trỏ thẳng tới file của nó (ví dụ \EFI\ubuntu\shimx64.efi). cavOS không có installer, nên nó dựa hoàn toàn vào fallback path.

Đã kiểm thật: boot một bản overlay của disk.img trên OVMF (OVMF_CODE_4M.fd + bản chép của OVMF_VARS_4M.fd), rồi đọc lại kho biến NVRAM bằng một script Python nhỏ:

Trên disk.img của cavOS có gì

Ảnh đĩa cavOS không phải GPT và phân vùng boot cũng không mang nhãn ESP. Nó vẫn boot được trên OVMF.

tools/kernel/make_disk.sh dựng ảnh bằng parted ... mklabel msdos (tức MBR), hai phân vùng, rồi mkdosfs -F32 cho phân vùng 1, mke2fs -L "cavOS" cho phân vùng 2, fatlabel ... LIMINE. Phân vùng 1 được mount vào /boot của phân vùng 2 khi chép file, nên trong FAT các file nằm ở gốc:

text
$ fdisk -l disk.img
Disk disk.img: 1.75 GiB, 1881310208 bytes, 3674434 sectors
Disklabel type: dos
Device     Boot  Start     End Sectors  Size Id Type
disk.img1  *      2048  133120  131073   64M 83 Linux
disk.img2       266240 3674111 3407872  1.6G 83 Linux

$ xxd -s 512 -l 16 disk.img          # LBA 1: không có chữ ký "EFI PART"
00000200: fc30 c0bf ff0a 0700 b9ff 0a07 0081 e9ff  .0..............

$ mlabel -i disk.img@@1M -s ::
 Volume label is LIMINE

$ mdir -i disk.img@@1M -/ -b ::
::/limine/
::/EFI/
::/kernel.bin
::/limine/limine-bios.sys
::/limine/limine.conf
::/EFI/BOOT/
::/EFI/BOOT/BOOTX64.EFI
::/EFI/BOOT/BOOTIA32.EFI
  • Phân vùng 1 có type 0x83 (Linux), không phải 0xEF. Theo spec nó không phải ESP. OVMF vẫn boot được vì driver FAT của nó gắn vào mọi phân vùng FAT, không xét type. Firmware máy thật có thể khắt khe hơn; điều này chưa được thử.
  • BOOTX64.EFI trên đĩa trùng byte với src/bootloader/limine/BOOTX64.EFI (Limine 10.1.1, theo src/bootloader/assert.sh), kernel.bin trùng với target/boot/kernel.bin (kiểm bằng cmp).
  • make qemu của cavOS không truyền firmware UEFI nào cho QEMU, nên mặc định nó boot qua SeaBIOS (đường BIOS: MBR → limine-bios.sys). Đường UEFI chỉ chạy khi bạn tự thêm OVMF như ở trên.
text
# /limine/limine.conf trên phân vùng FAT
timeout: 0
/cavOS
    protocol: limine
    kaslr: yes
    kernel_path: boot():/kernel.bin

boot(): là phân vùng chứa limine.conf, tức phân vùng FAT LIMINE.

Limine đọc kernel thế nào

Limine là một ứng dụng UEFI, nhưng nó không nhờ firmware đọc file. Nó chỉ mượn firmware để đọc từng sector, còn FAT thì tự hiểu.

  1. Firmware nạp BOOTX64.EFI (một file PE32+, xem PE, ELF và quy ước gọi hàm) vào RAM và gọi điểm vào với hai đối số: ImageHandle và con trỏ EFI_SYSTEM_TABLE.
  2. Limine liệt kê mọi handle có EFI_BLOCK_IO_PROTOCOL (gBS->LocateHandle(ByProtocol, ...) trong common/drivers/disk.s2.c) và đọc sector bằng ReadBlocks. Nó tự đọc bảng MBR/GPT và tự hiểu FAT (common/fs/fat32.s2.c). Trong mã nguồn 10.1.1 không có chỗ nào dùng EFI_SIMPLE_FILE_SYSTEM_PROTOCOL.
  3. Limine tìm file cấu hình trên từng phân vùng theo thứ tự trong common/lib/config.c: /limine.conf, /limine/limine.conf, /boot/limine.conf, /boot/limine/limine.conf, rồi (chỉ bản UEFI) /EFI/BOOT/limine.conf, /EFI/limine/limine.conf. cavOS trúng đường thứ hai.
  4. Limine đọc kernel.bin theo kernel_path, nạp các segment ELF, dựng page table, lấy memory map lần cuối, gọi ExitBootServices (efi_exit_boot_services() trong common/lib/misc.c), rồi nhảy vào _start.

Vì Limine tự làm phần đọc file, cùng một mã FAT chạy cho cả đường BIOS (đọc sector bằng int 13h) lẫn UEFI.
