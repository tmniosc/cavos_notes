Lab 0x09 - AHCI & Filesystems

Status doneTags lab, hands-on, ahci, sata, dma, prdt, mbr, fat32, ext2, vfs

Đi cùng bài: Bài 15 - AHCI & Filesystems. Kernel tìm controller SATA AHCI trong vòng quét PCI, bật nó theo đúng thứ tự initiateAHCI() của cavOS, rồi đọc chính ổ đĩa nó vừa boot lên: bảng phân vùng MBR, một phân vùng FAT32 (Limine + kernel, cavOS mount ở /boot/) và một phân vùng ext2 (cavOS mount ở /). Đọc file từ cả hai và so checksum với giá trị tính trên máy host.

Vị trí: ~/oskernel-lab/09-ahci-fs/ (chép từ 08-pci-nic/) · Limine base revision 2. Chạy: make image && make run. Source lưu ở lab/src/oskernel-lab/09-ahci-fs/, log đầy đủ (2 lần chạy) ở lab/outputs/lab-0x09-run.txt.

Lab làm gì

Từ "có một controller ở 00:1f.2" tới "đây là nội dung /etc/motd", qua bốn tầng.

Chạy

Script dựng ổ đĩa giống disk.img của cavOS, không cần quyền root.

bash
cd ~/oskernel-lab/09-ahci-fs
make image          # scripts/mkimage_fs.sh: in cả checksum FNV-1a mong đợi
make run            # QEMU -M q35, ổ if=ide = controller AHCI ICH9

make clean && make image DEMO=-DPRDT_CAVOS && make run   # PRDT như cavOS
bash scripts/run_all.sh lab-0x09-run.txt                # cả hai, ghi log

Cờ QEMU: -M q35 -m 256M -serial stdio -no-reboot -no-shutdown -nic none -drive file=os.img,format=raw,if=ide. Trên máy q35, ổ if=ide nằm trên controller AHCI có sẵn (00:1f.2), nên không cần thêm -device ahci. Mọi output dưới đây là thật: QEMU 10.2.1, cross gcc x86_64-cavos-gcc -O2, Limine 8.7.0, SeaBIOS, TCG, chạy ngày 2026-10-03.

Kết quả 1: ổ đĩa phía host

Script in ra checksum mong đợi trước khi boot, để so với số kernel tự tính.

text
[1/6] create 96 MiB raw image -> os.img
[2/6] MBR: partition 1 FAT32 (boot flag) 1..40 MiB, partition 2 Linux (0x83) 40 MiB..end
[3/6] limine bios-install
[4/6] FAT32 on partition 1, same layout as cavOS: /kernel.bin, /limine/, /EFI/BOOT/
[5/6] ext2 on partition 2 (block size 1024, files from rootfs/)
[6/6] expected FNV-1a (computed on the host)
  kernel.bin       389480 bytes  FNV-1a 0x66d00670
  big.bin          307200 bytes  FNV-1a 0x4fa57155
  note.txt             22 bytes  FNV-1a 0x1afe5128

big.bin 300 KiB được chọn có chủ ý: với block 1 KiB, nó cần 12 block trực tiếp, cả 256 block của block gián tiếp 1 cấp, và thêm 32 block qua block gián tiếp 2 cấp.

Kết quả 2: bật controller AHCI

Sáu cổng, hai cổng có thiết bị; chỉ một cái là ổ cứng.

text
[pci] 00:1f.2  8086:2922  class 01/06/01  hdr 80  cmd 0107  IRQ line 10 pin A  SATA controller (AHCI)
[pci]          BAR5 MMIO32  0xfebf1000  size 4 KiB   (read 0xfebf1000, after writing 0xffffffff read 0xfffff000)
[pci]          -> class 0x01 sub 0x06: initiateAHCI()
[pci::ahci] Detected controller! name{Intel ICH9}
[pci::ahci] PCI command 0x107 -> 0x107 (bus master, memory space)
[pci::ahci] ABAR (BAR5) PA 0xfebf1000 -> VA 0xfffffe8000100000; CAP 0xc0141f05 -> 6 ports, 32 command slots, 64-bit DMA yes; version 1.00; PI 0x3f
[pci::ahci] HBA reset (GHC.HR) done in 0 ms; BOHC 0x0, CAP2 0x0 (CAP2.BOH = 0: no BIOS/OS handoff on this controller)
[pci::ahci] GHC 0x80000000 (AE=1)
[pci::ahci] port 0: SSTS 0x113 SIG 0xffffffff -> SATA disk (cavOS's classification)
[pci::ahci]   port 0 rebased: command list PA 0x6d000, received FIS PA 0x6e000, command tables PA 0x6f000 + 0x70000, CMD 0xc017 (ST=1 FRE=1)
[pci::ahci]   after FRE=1: SIG 0x101 (after 0 ms) -> SATA disk
[pci::ahci]   IDENTIFY: model "QEMU HARDDISK", LBA48 yes, 196608 sectors x 512 B = 96 MiB
[pci::ahci] port 1: SSTS 0x0 SIG 0xffffffff -> no device (DET != 3)
[pci::ahci] port 2: SSTS 0x113 SIG 0xffffffff -> SATA disk (cavOS's classification)
[pci::ahci]   port 2 rebased: command list PA 0x71000, received FIS PA 0x72000, command tables PA 0x73000 + 0x74000, CMD 0xc017 (ST=1 FRE=1)
[pci::ahci]   after FRE=1: SIG 0xeb140101 (after 0 ms) -> SATAPI (CD/DVD)
[pci::ahci]   not a SATA disk: engine stopped, port dropped
[pci::ahci] port 3: SSTS 0x0 SIG 0xffffffff -> no device (DET != 3)
...
  • PI 0x3f: cổng 0–5 có mặt. SSTS 0x113: DET = 3 (có thiết bị, đã nối), IPM = 1 (đang hoạt động), tốc độ Gen1.
  • CAP2 0x0: controller ICH9 của QEMU không có cơ chế BIOS/OS handoff, nên bước đó bỏ qua.
  • Cổng 2 là ổ CD mặc định của QEMU. Ngay sau khi reset HBA, thanh ghi SIG của mọi cổng là 0xffffffff: chữ ký chỉ có khi ổ gửi FIS đầu tiên, mà HBA chỉ nhận FIS khi FRE = 1. cavOS phân loại cổng trước khi bật FRE, nên rơi vào nhánh mặc định "SATA disk". Lab bật engine trước rồi đọc lại: 0x101 = ổ ATA, 0xeb140101 = ATAPI.
  • IDENTIFY trả 512 byte mô tả ổ: tên (chuỗi ATA, mỗi cặp byte đảo chỗ) và số sector LBA48 (196608 × 512 = 96 MiB, đúng cỡ os.img).

Kết quả 3: MBR và hai lần fsMount

Cùng hai lời gọi như _start() của cavOS, cùng thứ tự.

text

[disk]   partition 0: type 0xc (bootable)  first LBA 2048  sectors 79872 (39 MiB)
[disk]   partition 1: type 0x83             first LBA 81920  sectors 114688 (56 MiB)

[vfs] fsMount("/", CONNECTOR_AHCI, 0, 1)
[ext2] superblock at LBA 81922: magic 0xef53, volume "labroot", block size 1024, 57344 blocks, 14336 inodes, 7 block groups (8192 blocks, 2048 inodes each), inode size 256, incompat features 0x2 (= FILETYPE only: cavOS accepts it)
[ext2]   BGDT at block 2: inode table of group 0 at block 228, group 1 at block 8420
[vfs]   mounted as ext2
[vfs] fsMount("/boot/", CONNECTOR_AHCI, 0, 0)
[fat32] boot sector at LBA 2048: label "LABBOOT    ", 2 sectors/cluster, 32 reserved, 2 FATs x 754 sectors, root cluster 2
[fat32]   -> FAT at LBA 2080, cluster 2 at LBA 3588
[vfs]   mounted as FAT32

[vfs] fsDetermineMountPoint("/") -> "/"
[vfs] fsDetermineMountPoint("/boot/kernel.bin") -> "/boot/"
[vfs] fsDetermineMountPoint("/bootstrap.txt") -> "/"
[vfs] fsDetermineMountPoint("/etc/motd") -> "/"
  • Superblock của ext2 nằm ở byte 1024 của phân vùng = LBA 81920 + 2. Số 0xef53 là chữ ký của ext2.
  • FAT32: vùng dữ liệu bắt đầu sau 32 sector dự trữ và 2 bảng FAT: 2048 + 32 + 2 × 754 = 3588. Cluster đầu tiên mang số 2, không phải 0.
  • /bootstrap.txt thuộc /, không thuộc /boot/: so prefix phải kèm điều kiện ký tự kế tiếp là / hoặc hết chuỗi.

Kết quả 4: liệt kê thư mục

Hai cách lưu thư mục khác hẳn nhau, nhìn từ trên xuống thì như nhau.

    motd-link             inode   22  type 7 (link)  mode 0xa1ff  size 9
[vfs] ls /boot/  (mount "/boot/", path inside it "/")
    LIMINE                <DIR>       first cluster 3

  • ext2: thư mục gốc luôn là inode 2. Mỗi mục chỉ có số inode, kiểu và tên; cỡ file và quyền nằm trong inode (mode 0x81a4 = file thường, rw-r--r--). motd-link là symlink 9 byte ("/etc/motd").

[fat32]   /kernel.bin: 389480 B in a chain of 381 clusters starting at 6
[kernel] /boot/kernel.bin: 389480 bytes, FNV-1a 0x66d00670, 763 AHCI commands, 1145 sectors, 82 ms
[ext2]   /big.bin: inode 12, 307200 B = 300 blocks; block[0..11] = 754,755,756,757,758,759,760,761,762,763,764,765 block[12] (single indirect) = 766, block[13] (double) = 1023; indirect blocks read: 3

[ext2]   /docs/deep/nested/note.txt: inode 18, 22 B = 1 blocks; block[0..11] = 1438 block[12] (single indirect) = 0, block[13] (double) = 0; indirect blocks read: 0
[kernel] /docs/deep/nested/note.txt: 22 bytes, FNV-1a 0x1afe5128, 10 AHCI commands, 15 sectors, 2 ms
[kernel] /missing.txt: not found
  • Block gián tiếp: block[12] = 766 là một block chứa 256 số block (1024 / 4). block[13] = 1023 trỏ tới một block chứa số của các block chứa số. Đọc cả file cần đúng 3 block "danh sách": block 766, block 1023, và một block cấp 2.
  • FAT32 tốn hai lệnh mỗi cluster: 381 cluster cần 763 lệnh AHCI, vì mỗi lần tìm cluster kế tiếp lab đọc lại một sector của bảng FAT. cavOS có cache cho các sector FAT (fat32FATfetch), nên phần lớn lần tra không cần đọc đĩa.
  • Đường dẫn 4 cấp /docs/deep/nested/note.txt cần 10 lệnh: mỗi cấp đọc một inode và một block thư mục.

Kết quả 6: PRDT và buffer không liền về vật lý

Card ghi vào RAM bằng địa chỉ vật lý; hai trang liền nhau về VA chưa chắc liền nhau về PA.

Lab dựng một buffer 8 KiB: hai trang VA liền nhau, map vào hai frame không liền nhau (chen một frame ở giữa), rồi đọc 16 sector đầu ổ vào đó.

text
########## Run 1: make run
[prdt] buffer VA 0xfffffe8000800000: page 0 -> PA 0x75000, page 1 -> PA 0x77000 (frame 0x76000 in between)
[prdt] mode: one PRDT entry per page, each with its own PA
[prdt] sectors 0-7 in page 0: match; sectors 8-15 in page 1: match; frame in between written by the disk: no

########## Run 2: DEMO=-DPRDT_CAVOS (one PRDT entry for the whole buffer, like cavOS)
[prdt] buffer VA 0xfffffe8000800000: page 0 -> PA 0x75000, page 1 -> PA 0x77000 (frame 0x76000 in between)
[prdt] mode: PRDT_CAVOS, one PRDT entry = PA of page 0, 8192 bytes
[prdt] sectors 0-7 in page 0: match; sectors 8-15 in page 1: WRONG; frame in between written by the disk: YES
[kernel] /big.bin: 307200 bytes, FNV-1a 0x4fa57155, 306 AHCI commands, 610 sectors, 96 ms

Bản PRDT_CAVOS làm như ahciSetUpCmd của cavOS: lấy PA của trang đầu và cho một entry PRDT dài 8192 byte. Controller ghi 4 KiB sau vào 0x76000, tức frame đứng sau 0x75000 về vật lý, đè lên bộ nhớ của ai đó, còn trang thứ hai của buffer không nhận được gì. Các file vẫn đọc đúng trong lần chạy này, vì buffer tĩnh của lab nằm trong ảnh kernel mà Limine nạp liền một khối vật lý.

Tự kiểm tra

Đoán trước, rồi sửa code và chạy lại.

Bỏ dòng đặt GHC.AE. Driver còn chạy không?

Trên controller này vẫn chạy. CAP 0xc0141f05 có bit 18 (SAM, "chỉ hỗ trợ AHCI") bằng 1, và theo đặc tả AHCI khi đó GHC.AE luôn đọc ra 1, ghi không đổi được. Trên controller còn hỗ trợ chế độ IDE cũ (SAM = 0), thiếu bước đặt AE thì các thanh ghi cổng AHCI không có hiệu lực.

Với block 4 KiB thay vì 1 KiB, big.bin (300 KiB) cần block gián tiếp không?

Không. 300 KiB = 75 block 4 KiB. 12 block trực tiếp + 1024 block qua gián tiếp 1 cấp, nên chỉ cần block gián tiếp 1 cấp; gián tiếp 2 cấp chỉ cần khi file vượt 12 + 1024 block (≈ 4 MiB).

Vì sao KERNEL.BIN hiện chữ hoa còn limine.conf giữ chữ thường?

kernel.bin vừa khuôn 8.3, nên chỉ có một mục ngắn, và tên ngắn luôn lưu chữ hoa (lab không đọc cờ chữ thường của Windows NT ở byte 12). limine.conf có đuôi 4 chữ, nên mtools ghi thêm mục LFN mang tên gốc.

Trong bản PRDT_CAVOS, chuyện gì xảy ra với dữ liệu đang nằm ở frame 0x76000?

Bị controller ghi đè bằng 4 KiB đĩa, không qua CPU và không qua page table, nên không có page fault nào báo. Nếu frame đó là page table hay stack của task khác thì hỏng âm thầm, lỗi lộ ra rất xa chỗ gây ra.
