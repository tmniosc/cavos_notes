Lab 0x04 - GDT, TSS & IDT

Status doneTags lab, hands-on, cpu, interrupt

Lab làm gì

Đi đúng thứ tự cavOS _start(): PMM, VMM, rồi initiateGDT(), rồi initiateISR().

  1. GDT + TSS (gdt_init = initiateGDT): 11 descriptor cùng thứ tự, cùng byte access/granularity với cavOS; lgdt, đẩy 0x28 + địa chỉ nhãn rồi lretq để đổi CS, nạp 0x30 vào DS/ES/FS/GS/SS; xoá TSS về 0, điền base vào descriptor 0x58, ltr 0x58.
  2. PIC + IDT (isr_init = initiateISR bỏ phần APIC): remap PIC 8259 về vector 0x20–0x2F rồi che hết; cổng 0–47 = 0x8E, cổng 3 và 0x80 = 0xEE (DPL 3), cổng 0xFF; lidt. Không sti: chưa có APIC và timer (Bài 10).
  3. In trạng thái: sgdt, sidt, str, các selector, từng qword của GDT, TSS và một số cổng IDT.
  4. Demo lỗi: int3; chia cho 0; ud2; int $0x40 vào cổng trống; int $0x80; cuối cùng đọc một địa chỉ chưa map để có #PF thật → panic → cli; hlt.

Để tiếp tục sau một lỗi có chủ đích, kernel gọi isr_expect(mask_vector, số_byte) trước lệnh gây lỗi. Handler thấy vector khớp thì cộng số byte đó vào RIP đã lưu (bỏ qua lệnh lỗi) rồi iretq. Đây chỉ là công cụ cho demo, cavOS không có.

Chạy

Ba bản build: bản thường, bản gây double fault có IST, và bản double fault không IST như cavOS.

bash
cd ~/oskernel-lab/04-gdt-idt
make run                                   # demo chính, dừng ở panic do #PF
make clean && make run DEMO=-DDF_DEMO      # stack hỏng -> #DF chạy trên IST1
make clean && make run DEMO="-DDF_DEMO -DNO_IST" \
  QEMU_FLAGS="-M q35 -m 256M -serial stdio -no-reboot -no-shutdown -d int,cpu_reset -D /tmp/qint.log"
grep "check_exception\|Triple" /tmp/qint.log

Kernel kết thúc bằng cli; hlt, nên QEMU không tự thoát; bấm Ctrl+C (log ở trên được chạy trong timeout 8). Mọi output dưới đây là thật: QEMU 10.2.1, -M q35 -m 256M, TCG, cross gcc x86_64-cavos-gcc, chạy ngày 2026-10-03.

Kết quả 1: GDT và TSS

Bảng đã nạp khớp từng byte với bảng của cavOS trong Bài 7.

text
[gdt] before: CS=0x28 (Limine's GDT)
[gdt] lgdt + lretq + ltr done
[pic] remapped IRQ0-7 -> 0x20, IRQ8-15 -> 0x28; mask master=0xff slave=0xff (all masked, like cavOS)
[gdt] sgdt: base = 0xffffffff80005420  limit = 0x67 (104 bytes)
[gdt] selectors: CS=0x28 DS=0x30 ES=0x30 FS=0x30 GS=0x30 SS=0x30 TR=0x58
[gdt]   +0x0  0x0000000000000000  null
[gdt]   +0x8  0x00009a000000ffff  kernel code 16
[gdt]   +0x10 0x000092000000ffff  kernel data 16
[gdt]   +0x18 0x00cf9a000000ffff  kernel code 32
[gdt]   +0x20 0x00cf92000000ffff  kernel data 32
[gdt]   +0x28 0x00209a0000000000  kernel code 64
[gdt]   +0x30 0x0000930000000000  kernel data 64
[gdt]   +0x38 0x0000000000000000  (empty, SYSENTER)
[gdt]   +0x40 0x0000000000000000  (empty)
[gdt]   +0x48 0x0000f20000000000  user data 64
[gdt]   +0x50 0x0020fa0000000000  user code 64
[gdt]   +0x58 0x80008b0053a00068  TSS low
[gdt]   +0x60 0x00000000ffffffff  TSS high
[tss] base = 0xffffffff800053a0  size = 104  rsp0 = 0x0  ist1 = 0xffffffff8000a4c0  iomap base = 0x0
  • Trước lgdt, CS đã là 0x28. GDT của Limine cũng đặt code 64-bit ở 0x28 (Limine protocol quy định). cavOS chọn cùng chỗ nên selector không đổi, chỉ bảng phía sau đổi.
  • limit = 0x67 = 11 × 8 + 16 − 1. Bảng là biến static, nên base nằm trong ảnh kernel (0xffffffff8…).
  • Đọc một descriptor: 0x0020fa0000000000 ở +0x50 → byte 5 = fa = 1111 1010 (P=1, DPL=3, S=1, code, đọc được), nửa byte cờ = 2 = L=1. Đó là user code 64. Ngay trước nó, +0x48 là user data (f2): data đứng trước code vì sysret lấy SS = STAR[63:48] + 8 và CS = STAR[63:48] + 16.
  • Bit A (accessed): data 64 ở +0x30 là 93 (CPU đã bật bit 0 khi nạp DS/SS). Code 64 ở +0x28 vẫn là 9a dưới TCG. Chạy cùng ảnh với -enable-kvm thì dòng đó là 0x00209b0000000000 (CPU thật bật bit A khi lretq nạp CS), giống dump cavOS trong Bài 7. Khác biệt này đến từ trình giả lập, không phải từ code.
  • TSS descriptor 16 byte: 0x80008b0053a00068 + 0x00000000ffffffff → limit 0x0068, base = ffffffff‧80‧00‧53a0 = 0xffffffff800053a0, đúng dòng [tss] base. Byte type là 8b, dù code ghi 0x89: ltr tự đổi TSS sang trạng thái busy.
  • TSS: rsp0 = 0 như cavOS lúc boot (chưa có task user). ist1 là đỉnh stack 16 KiB riêng cho #DF, cải tiến của lab (xem mục Khác cavOS).

Kết quả 2: IDT

256 ô, nhưng chỉ 50 ô có handler; mỗi ô 16 byte.

text

[idt] present gates = 50 (0-47, 0x80, 0xff like cavOS; the rest P=0)
[idt]   vec 0x0  0x00000000ffffffff 0x80008e0000282234  off=0xffffffff80002234 sel=0x28 ist=0 P=1 DPL=0 interrupt-gate
[idt]   vec 0x3  0x00000000ffffffff 0x8000ee0000282246  off=0xffffffff80002246 sel=0x28 ist=0 P=1 DPL=3 interrupt-gate
[idt]   vec 0x8  0x00000000ffffffff 0x80008e0100282267  off=0xffffffff80002267 sel=0x28 ist=1 P=1 DPL=0 interrupt-gate
[idt]   vec 0xe  0x00000000ffffffff 0x80008e0000282293  off=0xffffffff80002293 sel=0x28 ist=0 P=1 DPL=0 interrupt-gate
[idt]   vec 0x20 0x00000000ffffffff 0x80008e000028232b  off=0xffffffff8000232b sel=0x28 ist=0 P=1 DPL=0 interrupt-gate
[idt]   vec 0x40 0x0000000000000000 0x0000000000000000  off=0x0000000000000000 sel=0x0 ist=0 P=0 DPL=0 (empty)
[idt]   vec 0x80 0x00000000ffffffff 0x8000ee00002823bb  off=0xffffffff800023bb sel=0x28 ist=0 P=1 DPL=3 interrupt-gate
[idt]   vec 0xff 0x00000000ffffffff 0x80008e00002823c7  off=0xffffffff800023c7 sel=0x28 ist=0 P=1 DPL=0 interrupt-gate

Tách qword thấp của cổng 8, 0x80008e0100282267, từ byte thấp lên:

bytegiá trịtrườngnghĩa
0–12267offset 15:03 mảnh offset ghép lại = 0xffffffff80002267 (isr8)
2–30028selectorCS khi vào handler = kernel code 64
401ISTdùng TSS.ist1 làm stack (cavOS: luôn 0)
58eP | DPL | typeP=1, DPL=0, type 1110 = interrupt gate 64-bit (CPU xoá IF khi vào)

Cổng 3 và 0x80 có byte ee = DPL 3: code ring 3 được phép gọi int3 và int $0x80. Các cổng khác DPL 0, nên user gọi int n vào đó sẽ bị #GP.

Kết quả 3: bắt lỗi

Bốn lỗi được báo rồi chạy tiếp, một lỗi cuối dừng máy, và mỗi lỗi để lại dấu vết khác nhau trên stack.

text
[isr] vector 0x3 #BP Breakpoint  err=0x0
      RIP=0xffffffff80000116 CS=0x28 RFLAGS=0x46 RSP=0xffff80000ff98fe0 SS=0x30
      handler running on RSP=0xffff80000ff98ef0
      -> trap: RIP already points past int3, just iretq
[demo] address right after int3 = 0xffffffff80000116
[demo] int3 returned -> back in kmain

[isr] vector 0x0 #DE Division By Zero  err=0x0
      RIP=0xffffffff80000166 CS=0x28 RFLAGS=0x10046 RSP=0xffff80000ff98fe0 SS=0x30
      handler running on RSP=0xffff80000ff98ef0
      -> expected fault: RIP += 2 (skip the faulting instruction), iretq
[demo] address of the div = 0xffffffff80000166
[demo] #DE reported -> back in kmain

[isr] vector 0x6 #UD Invalid Opcode  err=0x0
      RIP=0xffffffff800001a8 CS=0x28 RFLAGS=0x10046 RSP=0xffff80000ff98fe0 SS=0x30
      -> expected fault: RIP += 2 (skip the faulting instruction), iretq
[demo] address of the ud2 = 0xffffffff800001a8

[isr] vector 0xd #GP General Protection Fault  err=0x202
      RIP=0xffffffff800001e3 CS=0x28 RFLAGS=0x10046 RSP=0xffff80000ff98fe0 SS=0x30
      selector error code: EXT=0 IDT=1 TI=0 -> IDT vector 0x40
[demo] int 0x40 on an empty gate reported -> back in kmain

[isr] int 0x80 (syscall gate, DPL 3) rax=0x1234
[demo] int 0x80 returned

[demo] reading unmapped VA 0x0000500000000000 ...
[isr] vector 0xe #PF Page Fault  err=0x0
      RIP=0xffffffff8000022d CS=0x28 RFLAGS=0x10046 RSP=0xffff80000ff98fe0 SS=0x30
      handler running on RSP=0xffff80000ff98ef0
      CR2=0x0000500000000000  err bits: P=0 W=0 U=0 RSVD=0 I=0  (page not present)
      RAX=0x000000000000000a RBX=0x0000500000000000 RCX=0x00000000000003fd RDX=0x00000000000003f8
      RSI=0x0000000000000000 RDI=0xffffffff800031de RBP=0xffff80000ff98ff0 DS=0x30
[isr] Kernel panic: Page Fault!
[kernel] Kernel panic triggered! (cli; hlt)
  • Trap và fault lưu RIP khác nhau. int3 là trap: RIP đã lưu (…116) bằng đúng địa chỉ lệnh sau int3, nên chỉ cần iretq. div và ud2 là fault: RIP đã lưu bằng địa chỉ chính lệnh lỗi (…166, …1a8). Nếu handler không sửa RIP, iretq sẽ chạy lại lệnh đó và lỗi mãi.
  • RFLAGS 0x10046 ở fault, 0x46 ở trap. Bit 16 là RF (resume flag). CPU bật RF trong RFLAGS đã lưu khi xảy ra fault, để lệnh chạy lại không bị breakpoint lệnh bắt lần nữa.
  • Không đổi stack. Ngắt xảy ra ở ring 0 và cổng có ist = 0, nên CPU đẩy khung ngay trên stack đang dùng: RSP đã lưu …8fe0, handler chạy ở …8ef0, cùng một stack (Limine cấp, nằm trong HHDM).
  • Cổng trống cho #GP, không phải #NP. Error code 0x202 = 0x40 × 8 + 2: bit 1 (IDT) = 1 nghĩa là "chỉ số này là của IDT", chỉ số = 0x40. Cổng toàn số 0 có type 0, không phải interrupt/trap gate, và CPU kiểm type trước bit P. Chạy lại với -enable-kvm (lệnh chạy trên CPU thật) cũng ra vector 0xd … err=0x202.
  • #PF: CR2 giữ đúng địa chỉ đã đọc. Error code 0: P=0 (trang không có), W=0 (đọc), U=0 (từ ring 0). Không có isr_expect cho #PF, nên handler in thanh ghi rồi cli; hlt, giống cavOS panic(). RBX đang giữ địa chỉ lỗi vì compiler để con trỏ trong RBX.

Kết quả 4: double fault, có và không có IST

Khi chính stack hỏng, handler chỉ chạy được nếu CPU đổi sang một stack khác; đó là việc của IST.

Bản DF_DEMO đặt RSP vào một trang chưa map rồi gọi int3. CPU đẩy khung ngắt vào stack đó → #PF. Để vào handler #PF, CPU lại đẩy vào cùng stack → #PF lần hai trong lúc đang chuyển giao #PF → CPU biến thành #DF (vector 8).

text
[tss] ... ist1 = 0xffffffff800094c0
[demo] RSP = unmapped page, then int3
[isr] vector 0x8 #DF Double Fault  err=0x0
      RIP=0xffffffff800000c2 CS=0x28 RFLAGS=0x46 RSP=0x0000500000001000 SS=0x30
      handler running on RSP=0xffffffff800093d0
[isr] Kernel panic: Double Fault!
[kernel] Kernel panic triggered! (cli; hlt)

Khung lưu RSP hỏng 0x500000001000, còn handler chạy ở 0xffffffff800093d0, ngay dưới đỉnh ist1. #DF là loại abort: RIP đã lưu không bảo đảm trỏ đúng lệnh gây lỗi, nên handler chỉ báo cáo rồi dừng.

Bản -DNO_IST để cổng 8 có ist = 0 như cavOS. Serial dừng sau dòng [demo] RSP = unmapped page, then int3; log -d int của QEMU cho thấy chuỗi lỗi:

text
check_exception old: 0xffffffff new 0xe
check_exception old: 0xe new 0xe
check_exception old: 0x8 new 0xe
Triple fault

#PF → #PF trong lúc chuyển giao #PF (thành #DF) → #PF trong lúc chuyển giao #DF → triple fault: CPU reset, không còn handler nào chạy được.

Khác cavOS ở đâu

Lab chép cách làm của cavOS; mỗi chỗ khác đều có lý do và được ghi ra đây.

Một điều thấy được từ dòng iomap base = 0x0 (suy ra từ Intel SDM Vol.1, chương Input/Output, mục "I/O Permission Bit Map"; chưa thử bằng chương trình ring 3). cavOS và lab đều memset TSS về 0, nên trường I/O map base (2 byte ở offset 102) = 0, trong khi limit TSS là 0x68. SDM nói: base nhỏ hơn limit thì bitmap quyền I/O bắt đầu tại đó, tức tại byte 0 của chính TSS. Task user của cavOS có rflags = 0x200 (multitasking/task.c), tức IOPL = 0, nên CPU tra bitmap này cho mọi lệnh in/out từ ring 3. Bit 0 nghĩa là cho phép, mà phần lớn TSS là số 0 (rsp1, rsp2, ist1..7). Ví dụ cổng 0x60/0x64 (bàn phím PS/2) và 0x70/0x71 (CMOS) rơi vào byte của rsp1 = 0, nên chương trình user có thể đọc ghi trực tiếp. Cách chặn thường dùng: đặt I/O map base ≥ limit (ví dụ 104).

Tự kiểm tra

Sửa một dòng, đoán kết quả, rồi chạy để xem mình đoán đúng không.

Bỏ isr_expect(1ULL << 0, 2) trước phép chia cho 0. Chuyện gì xảy ra?

Handler không thấy vector 0 trong mask, nên in thanh ghi rồi panic ngay ở #DE; các demo sau không chạy.

Giữ isr_expect nhưng cho số byte bỏ qua là 0. Chuyện gì xảy ra?

RIP vẫn trỏ vào div, iretq chạy lại nó, lại #DE. Lần thứ hai mask đã bị xoá về 0 nên handler panic. Không sửa RIP thì fault lặp lại mãi.

Đổi byte attribute của cổng 0x40 thành 0x8E trỏ vào isr0. int $0x40 báo gì?

Không còn #GP. Handler chạy nhưng báo vector 0x0 #DE, vì số vector trong khung là do stub isr0 tự đẩy, CPU không đẩy số vector.

Vì sao bản NO_IST reset máy còn bản có IST thì in được báo cáo?

Không có IST, CPU đẩy khung #DF vào cùng stack hỏng, lại #PF, thành triple fault. Có IST, CPU nạp RSP = TSS.ist1 trước khi đẩy, nên khung #DF nằm trên stack tốt.

Bỏ sub $8, %rsp trong isr_common. Lab có hỏng không?

Gần như chắc là không: kernel biên dịch với -mno-sse, không có lệnh nào đòi stack căn 16 byte. Đó cũng là lý do cavOS chạy được dù gọi C khi RSP lệch.
