Lab 0x0a - Fast Syscalls

Status doneTags lab, hands-on, syscall, sysret, msr, swapgs, ring 3, int 0x80

Đi cùng bài: Bài 16 - Fast Syscalls. Kernel cài lệnh syscall đúng như initiateSyscallInst() của cavOS, chép nguyên đoạn syscall_entry của cavOS, rồi chạy vài chương trình ring 3 nhỏ. Chúng gọi write, getpid, exit, kể lại thanh ghi lúc vào và lúc ra kernel, đo 10000 lần syscall so với 10000 lần int 0x80, và chọc vào GS để thấy GS của ring 3 đang trỏ vào đâu.

Vị trí: ~/oskernel-lab/0a-fast-syscalls/ (chép từ 09-ahci-fs/) · Limine base revision 2. Chạy: make image && make run. Source lưu ở lab/src/oskernel-lab/0a-fast-syscalls/, log đầy đủ (3 bản build) ở lab/outputs/lab-0x0a-run.txt.

Chạy

Một bản thường và hai bản cố ý làm lại hai chỗ nguy hiểm của cavOS.

bash
cd ~/oskernel-lab/0a-fast-syscalls
make image && make run
make clean && make image DEMO=-DINT80_STI  && make run   # sti trong đường int 0x80, như cavOS
make clean && make image DEMO=-DBAD_SYSRET && make run   # RCX không canonical trước sysret
bash scripts/run_all.sh lab-0x0a-run.txt                  # cả ba, ghi log

Mọi output dưới đây là thật: QEMU 10.2.1 TCG (máy này không có KVM), cross gcc x86_64-cavos-gcc -O2, Limine 8.7.0, SeaBIOS, chạy ngày 2026-10-03.

Kết quả 1: bốn MSR

Trước và sau initiateSyscallInst().

text
[syscalls] MSRs before: EFER 0xd00 (SCE=0) STAR 0x0 (SYSCALL CS=0x0 SS=0x8; SYSRET CS=0x13 SS=0xb)
[syscalls]      LSTAR 0x0 (syscall_entry = 0xffffffff8000d0e0) FMASK 0x0 (IF|DF) GS_BASE 0x0 KERNEL_GS_BASE 0xffffffff8006d210 (&threadInfo = 0xffffffff8006d210)
[syscalls] CPUID 0x80000001 EDX = 0x2193fbfd, bit 11 (SYSCALL/SYSRET) = 1
[syscalls] MSRs after initiateSyscallInst(): EFER 0xd01 (SCE=1) STAR 0x40002800000000 (SYSCALL CS=0x28 SS=0x30; SYSRET CS=0x53 SS=0x4b)
[syscalls]      LSTAR 0xffffffff8000d0e0 (syscall_entry = 0xffffffff8000d0e0) FMASK 0x600 (IF|DF) GS_BASE 0x0 KERNEL_GS_BASE 0xffffffff8006d210 (&threadInfo = 0xffffffff8006d210)
  • STAR = 0x0040002800000000: bit 47:32 = 0x28 (code kernel; SS kernel = 0x28 + 8 = 0x30), bit 63:48 = 0x40 = GDT_USER_CODE - 16. SYSRET tính CS user = 0x40 + 16 và SS user = 0x40 + 8, cộng RPL 3: 0x53 và 0x4b. Đó là lý do GDT của cavOS đặt data user (0x48) trước code user (0x50), Bài 7.
  • FMASK = 0x600: khi syscall, CPU xoá IF (bit 9) và DF (bit 10) trong RFLAGS. Kernel vào với ngắt tắt.
  • EFER 0xd00 → 0xd01: bật SCE (bit 0). Bit 8, 10, 11 (LME, LMA, NXE) Limine đã bật sẵn.
  • Dòng "before" cho thấy KERNEL_GS_BASE đã là &threadInfo: scheduler của cavOS (và lab) ghi MSR này ở mỗi lần đổi task, từ trước khi có syscall.

Kết quả 2: vào và ra kernel

Chương trình ring 3 đo trước, kernel đo trong, rồi ring 3 đo lại sau sysret.

text
[kernel] task 3 (main): 231 bytes of code at VA 0x8000000000, CS=0x53 SS=0x4b RSP=0x800000000000, syscall stack top 0xfffffe8001013000
[t=  326] [3 main   ] write(1): hello from ring 3 (CPL 3) via SYSCALL
[t=  329] [3 main   ] in the kernel: CS=0x28 SS=0x30 RSP=0xfffffe8001012ed0 (syscall stack top 0xfffffe8001013000)
[t=  331] [3 main   ]   RCX=0x8000000032 = return address | R11=0x202 vs user RFLAGS 0x202 | saved user RSP=0x800000000000 (match)
[t=  332] [3 main   ]   at entry, after swapgs: GS_BASE=0xffffffff8006d210 KERNEL_GS_BASE=0xffffffff8006d210 (the user's GS); the handler then sets KERNEL_GS_BASE = &threadInfo
[t=  334] [3 main   ] back in ring 3 after sysret: CS=0x53 SS=0x4b RCX=0x8000000032 R11=0x202; GS_BASE seen by this syscall's entry 0xffffffff8006d210 (= GS in ring 3 just before it)
  • syscall không đổi stack: syscall_entry tự đổi sang stack syscall của task (đỉnh 0xfffffe8001013000, RSP trong handler cách đỉnh 0x130 byte: đúng 24 qword khung + phần hàm C).
  • RCX = địa chỉ ngay sau lệnh syscall (0x8000000032), R11 = RFLAGS của user. sysret dùng đúng hai thanh ghi đó để quay về, nên sau khi về ring 3 chúng vẫn mang giá trị ấy, và CS/SS là 0x53/0x4b như STAR đã tính.
  • GS của ring 3 là &threadInfo: syscall_entry làm swapgs lúc vào nhưng không làm lại lúc ra, và handler ghi KERNEL_GS_BASE = &threadInfo. Sau syscall đầu tiên, GS của chương trình là địa chỉ kernel. Ở lần vào này, cả hai MSR đều là &threadInfo.

Kết quả 4: GS trỏ vào kernel

Hai chương trình chỉ đọc %gs:0: một cái trước mọi syscall, một cái ngay sau một syscall.

text
[kernel] task 4 (gs0): 11 bytes of code at VA 0x8000000000, CS=0x53 SS=0x4b RSP=0x800000000000, syscall stack top 0xfffffe8001018000
[isr] vector 0xe #PF Page Fault  err=0x4
      RIP=0x0000008000000000 CS=0x53 RFLAGS=0x10202 RSP=0x0000800000000000 SS=0x4b
      CR2=0x0000000000000000  err bits: P=0 W=0 U=1 RSVD=0 I=0  (page not present)
      -> fault in ring 3 (CPL 3): kill task 4 (gs0), the kernel goes on

[kernel] task 5 (gs1): 18 bytes of code at VA 0x8000000000, CS=0x53 SS=0x4b RSP=0x800000000000, syscall stack top 0xfffffe800101d000
[isr] vector 0xe #PF Page Fault  err=0x5
      RIP=0x0000008000000007 CS=0x53 RFLAGS=0x10202 RSP=0x0000800000000000 SS=0x4b
      CR2=0xffffffff8006d210  err bits: P=1 W=0 U=1 RSVD=0 I=0  (protection violation)
      -> fault in ring 3 (CPL 3): kill task 5 (gs1), the kernel goes on
  • gs0: GS base = gsbase của task (0), nên %gs:0 là địa chỉ 0: trang không có (P = 0).
  • gs1: chỉ một getpid trước đó. CR2 = 0xffffffff8006d210 = &threadInfo, và P = 1: trang có, nhưng là trang kernel, ring 3 không được đọc. GS base của chương trình user thật sự đang là địa chỉ của một cấu trúc kernel. Không đọc được nội dung, nhưng biết được nó nằm ở đâu.
  • Lỗi ở ring 3 chỉ giết task đó; kernel chạy tiếp (mã thoát âm = số vector).

Kết quả 5: int 0x80 mà bật ngắt

Bản DEMO=-DINT80_STI làm như cavOS: sti ở mọi đường vào syscallHandler, kể cả int 0x80.

text
########## Run 2: DEMO=-DINT80_STI (sti in the int 0x80 path, like cavOS)
...
[t=  261] [3 main   ] back in ring 3 after sysret: CS=0x53 SS=0x4b RCX=0x8000000032 R11=0x202; GS_BASE seen by this syscall's entry 0xffffffff8006d210 (= GS in ring 3 just before it)

[sched] task 3 was preempted in ring 0 on its own TSS stack (RSP 0xffff800000076f20, TSS stack top 0xffff800000077000): copying its frame to the top overwrites the frame of the interrupt it was handling

Sau dòng đó máy không in thêm gì: vòng đo int 0x80 không bao giờ xong. Lý do:

  1. int 0x80 từ ring 3 đổi sang stack TSS của task (RSP0); khung ngắt nằm ở đỉnh stack đó.
  2. Handler sti. Timer bắn giữa chừng, ngay trên stack TSS (ring 0 không đổi stack); schedule() lưu khung của lần ngắt timer này rồi sang task khác.
  3. Khi quay lại, schedule() luôn chép khung đã lưu lên đỉnh stack TSS của task rồi iretq. Đỉnh đó đang chứa khung int 0x80 của user: bị đè. Handler chạy nốt rồi "trở về" bằng một khung kernel, không về ring 3 được nữa.

Đường syscall không bị, vì nó chạy trên stack syscall riêng. Bản thường của lab vì vậy chỉ sti cho đường syscall.

Kết quả 6: RCX không canonical

Bản DEMO=-DBAD_SYSRET: một syscall đặt địa chỉ trả về thành 0x800000000000, như sigreturn của cavOS lấy RCX từ stack user mà không kiểm.

text
[t=  417] [6 badret ] setting the return RIP (RCX) to 0x800000000000 without a canonical check, then sysret
[isr] vector 0xd #GP General Protection Fault  err=0x0
      RIP=0x0000800000000000 CS=0x53 RFLAGS=0x10202 RSP=0x0000800000000000 SS=0x4b
      -> fault in ring 3 (CPL 3): kill task 6 (badret), the kernel goes on

QEMU TCG báo #GP sau khi đã về ring 3 (CS = 0x53), nên chỉ task đó chết. Intel SDM mô tả khác cho CPU Intel: với RCX không canonical, sysret gây #GP khi CPU còn ở ring 0, nhưng RSP đã là RSP của user. Handler khi đó chạy ở ring 0 trên một stack do user chọn. Đó là lỗ hổng CVE-2012-0217 từng có ở nhiều hệ điều hành; cách tránh là kiểm RCX canonical trước sysret, hoặc về bằng iretq.

Tự kiểm tra

Đoán trước, rồi sửa code và chạy lại.

Đổi GDT cho code user đứng trước data user (code 0x48, data 0x50). sysret còn đúng không?

Không. SYSRET luôn lấy CS = STAR[63:48] + 16 và SS = STAR[63:48] + 8. Không có giá trị STAR nào cho CS = 0x48 và SS = 0x50 cùng lúc. Thứ tự "data trước, code sau" là bắt buộc.

Bỏ RFLAGS_IF khỏi FMASK. Có gì nguy hiểm?

Kernel vào với ngắt đang bật, ngay lúc RSP vẫn là stack user (trước xchg). Một ngắt rơi vào đúng mấy lệnh đầu sẽ đẩy khung lên stack user, ở ring 0 (không đổi stack vì CPL đã là 0).

Vì sao syscall_entry phải swapgs trước khi làm bất cứ gì khác?

Vì nó cần biết stack kernel của task, mà chỗ duy nhất đọc được mà không cần thanh ghi nào là %gs:0 sau khi đổi GS sang threadInfo. syscall không đổi RSP, và mọi thanh ghi đa dụng đều đang mang giá trị của user.

Lab đo int 0x80 chậm hơn syscall khoảng 2–4 lần. Con số đó có dùng được cho máy thật không?

Không. Đây là TCG: QEMU dịch và giả lập từng lệnh, nên chi phí của int/iretq so với syscall/sysret phụ thuộc cách QEMU viết phần giả lập. Kết luận "SYSCALL nhanh hơn" đúng trên CPU thật, nhưng tỉ lệ phải đo trên máy thật.
