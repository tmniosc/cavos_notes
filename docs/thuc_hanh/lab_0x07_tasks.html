Lab 0x07 - Multitasking & Scheduler

Status doneTags lab, hands-on, tasks, scheduler, context switch

Đi cùng bài: Bài 12 - Multitasking & Scheduler. Kernel chạy nhiều kernel thread cùng lúc trên một CPU, theo đúng cách cavOS làm: danh sách task liên kết đơn, mỗi task một PML4 và một stack riêng, tick LAPIC 1 ms gọi schedule(), và đổi task bằng cách dựng khung ngắt của task mới rồi iretq. Có ngủ theo tick, task idle, task thoát và được dọn, và một thread chờ phím được IRQ1 đánh thức.

Lab làm gì

Sau initiateMouse(), gọi initiateTasks() và initiateKernelThreads() đúng chỗ cavOS gọi, rồi tạo sáu thread để quan sát.

  1. initiateTasks(): luồng kmain đang chạy trở thành task 0 (id 0, tên kernel, PML4 = CR3 hiện tại, stack = stack boot của Limine). Tạo task dummy (state DUMMY): scheduler dùng nó khi không còn task nào READY. Lab cho dummy chạy hlt; cavOS chạy pause.
  2. initiateKernelThreads(): tạo thread helper, mỗi vòng gọi helperReaper() để dọn task đã chết.
  3. Sáu thread demo, tạo bằng taskCreateKernel(hàm, rdi):
    • A, B, C: vòng lặp bận, không bao giờ tự nhường CPU. Chỉ timer cắt được chúng. Mỗi vòng xong khi task đã nhận thêm 15 tick CPU. C return sau 2 vòng.
    • sleeper: taskSleepMs(50) bốn lần. Task chuyển sang BLOCKED, scheduler đánh thức khi tới giờ.
    • poller: sleep(50) hai lần, kiểu sleep() của cavOS: task vẫn READY, mỗi lượt chỉ nhường CPU rồi kiểm tra lại giờ.
    • kbd: chờ phím ở WAITING_INPUT. kbIrq (Lab 0x06) ghi ký tự vào ring tty_q rồi đổi task về READY. Gõ quit + Enter thì thread return.
  4. Task 0 ngủ từng 20 ms cho tới khi mọi thread xong và reaper đã dọn 4 thread đã return, rồi cli và in bảng tick CPU của từng task.

Kết quả 1: tạo task

Danh sách task ngay sau khi tạo, và khung iretq đầu tiên của một thread.

text
[tasks] task 0 = this kmain execution, PML4 at 0x56000, PML4[255] (stack slot) = 0x0 (empty)
[tasks] Current execution ready for multitasking
[tasks] 9 tasks in the list; each new one = 1 PML4 + 4 stack pages + 1 TSS stack page + PDPT/PD/PT; pmm free 65112 -> 65039
[tasks] task A first frame: RIP=0xffffffff80000570 RSP=0x7ffffffffff8 RFLAGS=0x200 CS=0x28 SS=0x30 RDI=0 [RSP]=0xffffffff80006d60 (taskKernelReturn)
[tasks] list right after creation (firstTask -> next -> ...):
  id  name     state          cpu ticks  switched in  wakeups  PML4       stack top PA
   0  kernel   READY                  0            0        0  0x56000  (Limine boot stack)
   1  dummy    DUMMY                  0            0        0  0x5b000  0x63000
   2  helper   READY                  0            0        0  0x64000  0x6c000
   3  A        READY                  0            0        0  0x6d000  0x75000
   4  B        READY                  0            0        0  0x76000  0x7e000
   5  C        READY                  0            0        0  0x7f000  0x87000
   6  sleeper  READY                  0            0        0  0x88000  0x90000
   7  poller   READY                  0            0        0  0x91000  0x99000
   8  kbd      READY                  0            0        0  0x9a000  0x103000
[tasks] sti: from now on every LAPIC tick calls schedule()
  • Thread chưa từng chạy cũng có "ngữ cảnh đã lưu". taskCreate điền sẵn một khung giống hệt khung mà ngắt để lại: RIP = hàm thread, CS=0x28/SS=0x30 (kernel, Bài 7), RFLAGS=0x200 (chỉ bit IF: thread chạy với ngắt bật), RDI = tham số. Lần đầu scheduler chọn nó, iretq "quay về" một chỗ nó chưa từng ở.
  • [RSP] = taskKernelReturn. stackGenerateKernel đẩy địa chỉ này lên đỉnh stack, nên RSP bắt đầu ở 0x7ffffffffff8. Hàm thread ret là nhảy vào taskKernelReturn → taskKill.
  • 8 task mới tốn 73 frame (65112 → 65039): mỗi task 1 PML4 + 4 trang stack + 1 trang TSS stack + 3 bảng (PDPT, PD, PT) cho ô 255 = 9 frame, cộng 1 trang TSS stack của task 0. cavOS cấp USER_STACK_PAGES = 2048 trang (8 MiB) cho mỗi stack.
  • Dummy đứng thứ hai trong danh sách nhưng state DUMMY, nên vòng tìm task READY không bao giờ chọn nó; chỉ nhánh "found no task" dùng nó.
  • Lab tạo mọi task trong cli để bảng trên là trạng thái ban đầu thật. cavOS tạo task khi ngắt đang bật.

Kết quả 2: preemption, stack và CR3 riêng

Ba vòng lặp bận không nhường CPU, vẫn chạy xen nhau từng 1 ms.

[t=  263] [5 C      ] round 1/2 done: own cpu ticks=15 switched in 17 times, loop spins=8449043

  • Cùng VA, khác PA. Biến cục bộ của mọi thread nằm ở 0x7fffffffffa8, nhưng mỗi thread trỏ tới một frame khác. Điều đó chỉ đúng vì CR3 đổi theo task: mỗi dòng đọc CR3 ngay trong thread và thấy đúng PML4 của mình.

Kết quả 3: hai cách ngủ

Ngủ bằng state BLOCKED thì scheduler bỏ qua task; ngủ kiểu sleep() của cavOS thì task vẫn được chọn mỗi vòng.

text
[t=  270] [6 sleeper] taskSleepMs(50) #1: BLOCKED at t=219, running again at t=270 (+51 ms), switched in 3 times so far
[t=  270] [7 poller ] sleep(50) #1: t=219 -> 270, but was switched in 17 times while 'sleeping' (stays READY)
[t=  321] [6 sleeper] taskSleepMs(50) #2: BLOCKED at t=270, running again at t=321 (+51 ms), switched in 4 times so far
[t=  321] [7 poller ] sleep(50) #2: t=270 -> 321, but was switched in 19 times while 'sleeping' (stays READY)
[t=  371] [6 sleeper] taskSleepMs(50) #3: BLOCKED at t=321, running again at t=371 (+50 ms), switched in 5 times so far
[t=  421] [6 sleeper] taskSleepMs(50) #4: BLOCKED at t=371, running again at t=421 (+50 ms), switched in 6 times so far
  • taskSleepMs làm như syscallNanosleep của cavOS: ghi giờ hẹn vào forcefulWakeupTimeUnsafe, đặt BLOCKED, nhường CPU. Mỗi lần ngủ chỉ tốn một lần được chọn: lúc schedule() thấy đã tới giờ, đổi nó về READY và chọn luôn.
  • sleep() của cavOS (cpu/timer.c) chỉ lặp handControl(). Task vẫn READY, nên trong 50 ms nó được chọn 17–19 lần, mỗi lần chỉ để thấy "chưa tới giờ" rồi nhường tiếp. Khi CPU nhàn thì không sao; khi có nhiều task như vậy, chúng chiếm lượt của nhau.
  • Trễ 50–51 ms: task tỉnh dậy ở tick đầu tiên sau giờ hẹn mà scheduler duyệt tới nó.

Kết quả 4: thread chờ phím, IRQ1 đánh thức

Thread kbd không tốn lượt nào khi chờ; phím tới thì nó chạy sau 1–3 ms.

text
##### harness: sendkey h
[t=  276] [8 kbd    ] key 'h' IRQ1 at t=273, task running at t=276 (3 ms later), woken by IRQ1
##### harness: sendkey e
[t=  436] [8 kbd    ] key 'e' IRQ1 at t=435, task running at t=436 (1 ms later), woken by IRQ1
##### harness: sendkey ret
[t= 1084] [8 kbd    ] key '\n' IRQ1 at t=1083, task running at t=1084 (1 ms later), woken by IRQ1
[t= 1084] [8 kbd    ] read() returns "hello" (5 chars, first key at t=273)
##### harness: sendkey ret
[t= 2539] [8 kbd    ] key '\n' IRQ1 at t=2538, task running at t=2539 (1 ms later), woken by IRQ1
[t= 2539] [8 kbd    ] read() returns "quit" (4 chars, first key at t=1891)
  • Phím h tới lúc ba worker còn bận: phải chờ 3 ms tới lượt. Sau khi worker xong, CPU gần như rảnh và độ trễ chỉ còn 1 ms (tick kế tiếp).
  • Cả demo, kbd được chọn 13 lần (bảng cuối): 11 lần do IRQ1 đánh thức (11 phím) cộng vài lần đầu. Lúc WAITING_INPUT, scheduler bỏ qua nó hoàn toàn.
  • cavOS làm tương tự trong readHandler() (syscalls/io.c): kbTaskRead đặt WAITING_INPUT, rồi while (state == WAITING_INPUT) handControl();. kbIrq gọi kbFinaliseStream() để đặt lại READY khi đủ dòng.

Kết quả 5: task thoát và reaper

Task chết không tự dọn được stack nó đang đứng; thread helper dọn hộ.

text
[t=  308] [5 C      ] returning -> taskKernelReturn() -> taskKill()
[t=  311] [2 helper ] reaper: task 5 (C) freed: 5 frames (4 stack + 1 TSS stack) + 4 page tables (PDPT, PD, PT, PML4); pmm free 65039 -> 65048
[t=  367] [3 A      ] returning -> taskKernelReturn() -> taskKill()
[t=  370] [2 helper ] reaper: task 3 (A) freed: 5 frames (4 stack + 1 TSS stack) + 4 page tables (PDPT, PD, PT, PML4); pmm free 65048 -> 65057
[t= 2540] [2 helper ] reaper: task 8 (kbd) freed: 5 frames (4 stack + 1 TSS stack) + 4 page tables (PDPT, PD, PT, PML4); pmm free 65066 -> 65075
  • Hàm thread ret → taskKernelReturn → taskKill: giao task cho reaper, đặt DEAD, sti, rồi lặp while (1) chờ tick. Như cavOS. State DEAD nên scheduler không bao giờ quay lại.
  • Thread helper (chạy ở ngữ cảnh khác, CR3 khác) trả 9 frame về PMM và gỡ task khỏi danh sách. Mỗi task trả đúng 9 frame đã cấp.

Race: thấy tận mắt, và vì sao vài chỗ không thể xảy ra

Một CPU vẫn có race, vì timer có thể đổi task giữa hai lệnh bất kỳ. Lab cố ý gây ra hai cái và đo một cái của cavOS.

1. Dòng in bị cắt (DEMO=-DNO_PRINT_LOCK)

Một dòng log là hàng chục lần serial_puts. Nếu tick tới giữa chừng, task khác in tiếp vào giữa dòng. Lab khoá mỗi dòng bằng spinlock kiểu cavOS (kout_begin/kout_end). Bỏ khoá, chạy dưới KVM:

text
[t=  615] [3 A      ] started: rdi=0 RSP=0x7ff[t=  616] [4 B      ] started: rdi=1 RSP=0x7fffffffffa0 [t=  617] [5 C      ] started: rdi=2 RSP=0x7fffffffffa0 [t=  618] [6 sleeper] started: rdi=3 RSP=0x7fffffffffa0 &[t=  619] [7 poller ] started: rdi=4 RSP=0x7fffffffffa0 [t=  620] [8 kbd    ] started: rdi=5 RSP=0x7fffffffff30 [t=  621] [0 kernel ] task 0 (kmain) blocks until allfffffffa0 &local=0x7fffffffffa8 -> PA 0x75fa8 CR3=0x6d000 IF&local=0x7fffffffffa8 -> PA 0x7efa8 CR3=0x76000 IF=1
[t=  672] [4 B      ] round 1/4 done: own cpu ticks=16 switched in 17 times, loo[t=  673] [5 C      ] round 1/2 done: own cpu[t=  674] [3 A      ] round 1/4 done: own cpu ticks=17 switchep spins=92535830

Cùng bản build đó chạy TCG thì không có dòng nào bị cắt: ở TCG một dòng in xong trong chưa tới một tick, nên race có nhưng hiếm tới mức 100 dòng không trúng lần nào. Dưới KVM mỗi outb ra cổng serial là một lần thoát VM, một dòng kéo dài qua vài tick, và race lộ ra ngay. Bản có khoá chạy dưới KVM: 0 dòng bị cắt. Bài học: không thấy lỗi chưa phải là không có lỗi. cavOS giải đúng như vậy cho log serial: debugf() (drivers/serial.c) lấy LOCK_DEBUGF quanh cả lời gọi, nhưng chỉ khi ngắt đang bật (trong IRQ thì bỏ khoá để khỏi chờ chính task bị ngắt). printf() ra console (putchar_ → printfch, graphical/console.c) thì không khoá.

2. Mất lần đánh thức (DEMO=-DLOST_WAKEUP)

Thread chờ phím làm hai bước: thấy ring rỗng, rồi đặt WAITING_INPUT. Nếu IRQ1 tới giữa hai bước, kbIrq thấy task chưa chờ nên không đánh thức; sau đó task đặt WAITING_INPUT và ngủ, với một phím nằm sẵn trong ring. Bản build này bỏ cli quanh hai bước và kéo khe hở ra 300 ms (chỉ lần chờ đầu) để phím rơi đúng vào đó:

text
[t=  217] [8 kbd    ] LOST_WAKEUP: ring empty, 300 ms gap before WAITING_INPUT
##### harness: key 'h' typed inside the 300 ms gap
##### harness: sendkey h
##### harness: key 'i' typed 1 s later
##### harness: sendkey i
[t= 1508] [8 kbd    ] key 'h' IRQ1 at t=321, task running at t=1508 (1187 ms later), woken by IRQ1
[t= 1508] [8 kbd    ] key 'i' IRQ1 at t=1507, task running at t=1508 (1 ms later), woken by IRQ1
[t= 1508] [8 kbd    ] 2 keys were waiting in the ring at this wakeup

Phím h nằm trong ring 1187 ms, tới khi phím i đánh thức thread. Bản thường làm hai bước trong cli/sti: IRQ1 chỉ có thể tới trước (ring không còn rỗng, task không ngủ) hoặc sau (task đã WAITING_INPUT, IRQ1 đánh thức nó). cavOS có cùng khe hở này trong kbTaskRead, xem Bài 12, Đọc thêm.

3. Tick tới giữa lúc đang đổi task: không thể

  • schedule() chỉ chạy bên trong một ngắt: IRQ timer, hoặc page fault của handControl. Cả hai cổng IDT là interrupt gate (type 0x8E, Bài 9): CPU tự xoá IF khi vào. Từ đầu schedule() tới iretq cuối asm_finalize, IF = 0, nên không tick nào chen vào được.
  • iretq nạp RFLAGS của task mới (IF = 1) cùng lúc với RIP, CS, RSP, SS: ngắt chỉ được nhận lại khi task mới đã đứng hẳn trên stack của nó.
  • asm_finalize đổi RSP trước rồi mới đổi CR3: khung iretq nằm trên TSS stack ở nửa cao, PML4 nào cũng thấy. Đổi CR3 trước thì stack cũ ở 0x7fff… (nửa thấp) không còn map, nhưng lúc đó RSP đã rời khỏi nó.
  • EOI gửi trước khi gọi handler (handle_interrupt, như cavOS), vì schedule() không return: gửi sau thì LAPIC không bao giờ nhận EOI và timer tắt.
  • Danh sách task: sửa trong irq_save/irq_restore nên schedule() (cũng chạy với IF = 0) không bao giờ thấy danh sách sửa dở. PMM của lab không có khoá, nên task 0 cấp frame và reaper trả frame cũng phải bọc như vậy.

4. Ring bàn phím dùng chung không khoá: an toàn

tty_q có đúng một người ghi (kbIrq) và một người đọc (thread kbd). Người ghi chỉ đổi w, người đọc chỉ đổi r, và mỗi bên ghi dữ liệu xong mới dời chỉ số (rào "memory"). Trên một CPU, IRQ chạy trọn vẹn giữa hai lệnh của thread, nên thread luôn thấy hoặc chỉ số cũ hoặc chỉ số mới cùng dữ liệu đầy đủ. Thêm người đọc thứ hai thì không còn đúng.

5. Task idle của cavOS gần như không bao giờ chạy (DEMO=-DHELPER_SPIN)

Thread helper của cavOS (kernelHelpEntry) lặp handControl() mãi, nên nó luôn READY: scheduler luôn có ít nhất một task READY và không bao giờ cần dummy. Lab mặc định cho helper ngủ 5 ms mỗi vòng. Bật HELPER_SPIN để làm y cavOS:

text
   1  dummy    DUMMY                  0            0        0  0x5b000  0x63000
   2  helper   READY               2141          184        0  0x64000  0x6c000

Dummy 0 tick; helper nhận 2141 tick, tức cả thời gian CPU nhàn được tiêu vào vòng "page fault, schedule, quay về helper". CPU không bao giờ hlt.

Tự kiểm tra

Đoán trước, rồi sửa code và chạy lại script để kiểm.

Đổi thứ tự trong handle_interrupt: gọi handler IRQ trước, gửi EOI sau. Demo chạy được bao lâu?

Tới tick đầu tiên sau initiateTasks(). timerTick gọi schedule(), hàm này iretq sang task khác và không bao giờ quay lại dòng EOI. LAPIC coi ngắt timer vẫn đang phục vụ nên không gửi tick mới cùng mức ưu tiên: không còn preemption, không còn đánh thức theo giờ.

Trong asm_finalize, đổi chỗ hai lệnh: mov %rsi,%cr3 trước, mov %rdi,%rsp sau. Có sao không?

Trong lab thì vẫn chạy: giữa hai lệnh đó không có lệnh nào dùng stack, và khung iretq ở nửa cao. Nhưng nếu có một lệnh push/call chen giữa, nó ghi vào stack ở 0x7fff… của task cũ, mà VA đó giờ là stack của task mới: hỏng dữ liệu task mới. Đổi RSP trước là cách an toàn.

Bỏ dòng tssPtr->rsp0 = next->whileTssRsp trong schedule(). Lab còn chạy không? cavOS thì sao?

Lab vẫn chạy: mọi task ở ring 0, ngắt từ ring 0 không đổi stack, nên CPU không đọc RSP0. cavOS thì hỏng ngay khi có task userspace: ngắt từ ring 3 sẽ đẩy khung lên stack của task trước đó, đè lên dữ liệu của nó.

Vì sao poller được chọn 40 lần mà vẫn 0 tick CPU?

Mỗi lần được chọn, nó chỉ so timerTicks với giờ hẹn rồi nhường CPU ngay, xong trước khi tick kế tiếp bắn. Tick chỉ cộng cho task đang chạy đúng lúc timer bắn, nên thời gian ngắn hơn một tick không được đếm.

Bỏ cli/sti trong kbWaitInput nhưng không thêm khe 300 ms. Demo có hỏng không?

Gần như không bao giờ thấy: khe hở chỉ vài lệnh, phím phải tới đúng trong vài nano giây đó. Nhưng race vẫn có, và khi trúng thì phím nằm trong ring cho tới phím kế tiếp. Bản LOST_WAKEUP chỉ kéo dài khe đó để thấy chắc chắn.
